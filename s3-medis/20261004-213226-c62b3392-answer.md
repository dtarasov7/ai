# 1. Факты, допущения, гипотезы

## 1.1. Факты из условия

1. Есть web‑приложение.
2. Есть клиентская часть в браузере.
3. Есть бекенд на серверах предприятия.
4. Пользователь может разместить сообщение.
5. Пользователь может оставить комментарий.
6. Пользователь может вставить фото или видео.
7. Медиа планируется хранить в Yandex Object Storage.
8. Yandex Object Storage рассматривается как S3‑совместимое хранилище.
9. Медиа планируется предварительно проверять.
10. Медиа планируется при необходимости перепаковывать/сжимать.
11. Требуется проработка информационной безопасности.
12. Требуется защита от DoS, в том числе:
    - переполнение хранилища;
    - огромный счет за хранение/запросы/egress/обработку.

## 1.2. Допущения

Для baseline threat model я исхожу из следующих допущений. Если что-то из этого неверно, модель нужно скорректировать.

1. Пользователи аутентифицированы.
2. Медиа принадлежат пользователям или организациям.
3. Медиа не являются публичными по умолчанию.
4. Медиа показываются внутри приложения, а не на публичном статическом сайте.
5. Браузер не имеет постоянного доступа к S3.
6. Браузер получает только:
   - кратковременный presigned URL, либо
   - отправляет файл через бекенд.
7. Бекенд управляет:
   - созданием jobs;
   - выдачей прав на загрузку;
   - валидацией;
   - обработкой;
   - хранением финальных объектов.
8. Обработка медиа выполняется отдельно от основного API, либо в выделенных worker‑процессах.
9. В обработке планируется использовать библиотеки типа:
   - FFmpeg;
   - ImageMagick;
   - libwebp;
   - другие transcode/resize-инструменты.
10. В приложении есть база данных, где хранятся:
    - сообщения;
    - комментарии;
    - привязка медиа к сообщениям;
    - пользователи;
    - состояние загрузки/обработки.
11. S3 bucket планируется приватным.
12. Медиа могут содержать персональные данные:
    - лица;
    - документы;
    - геоданные;
    - метаданные;
    - корпоративную информацию.

## 1.3. Гипотезы/основные риски

1. **Браузер — недоверенная сторона.**
   Любые client‑side проверки не являются границей безопасности.

2. **S3 не защищает бизнес от DoS самостоятельно.**
   S3 может принимать трафик, но счет может вырасти из-за объема, запросов, egress, multipart, незавершенных загрузок и орфанных объектов.

3. **Исходный пользовательский файл — потенциально вредоносный.**
   Его нельзя считать безопасным до серверной валидации и нормализации.

4. **Presigned URL — источник риска, если выдан слишком широко.**
   Нужно ограничивать:
   - время жизни;
   - метод;
   - key;
   - объем;
   - повторное использование.

5. **Обработка медиа — вычислительно expensive операция.**
   Злоупотребление ею может привести к:
   - CPU/RAM exhaustion;
   - очередь переполнению;
   - взрыву затрат на обработку;
   - эксплуатированию уязвимостей декодеров.

6. **Удаление медиа — деструктивная операция.**
   Нужны аудит, retention, защита от случайного удаления и четкая политика cleanup.

## 1.4. Что нужно уточнить

Чтобы threat model стал не baseline, а финальным, нужно знать:

1. Медиа публичные или приватные?
2. Планируется ли CDN?
3. Загрузка идет через бекенд или через presigned URL напрямую в S3?
4. Используются ли multipart uploads?
5. Какие форматы файлов разрешены?
6. Какие максимальные размеры?
7. Какова ожидаемая нагрузка:
   - DAU;
   - пиковые одновременные загрузки;
   - среднее число медиа в день;
   - средний размер;
   - максимальный размер.
8. Где выполняется обработка:
   - enterprise‑сервера;
   - Yandex Cloud;
   - контейнеры;
   - Kubernetes;
   - bare metal.
9. Есть ли WAF, API gateway, rate limiter?
10. Есть ли IAM service accounts или используются статические ключи?
11. Есть ли requirements:
    - персональные данные;
    - retention;
    - data residency;
    - аудит;
    - right to delete.
12. Есть ли возможность настроить budget alerts и monitoring в Yandex Cloud.

# 2. Активы и защищаемые ценности

## 2.1. Активы

| Актив | Почему важен |
|---|---|
| Идентичность пользователя | От него зависит право на создание/просмотр/удаление медиа |
| Сессия/токен | Используется для аутентификации и авторизации |
| Сообщения и комментарии | Бизнес‑данные приложения |
| Медиа-объекты | Пользовательский контент, потенциальные персональные данные |
| S3 bucket и префиксы | Место хранения медиа |
| Presigned URL | Временное право на доступ |
| Service account бекенда | Доступ к S3 и облачным ресурсам |
| Worker service account | Доступ к обработке медиа |
| База данных | Привязка медиа, состояния, квоты, аудит |
| Рабочие ресурсы серверов | CPU/RAM для обработки |
| Счет за Yandex Cloud | Финансовый риск |
| Журналы аудита | Необходимы для расследований и compliance |
| Инфраструктура CI/CD | Через нее может быть внедрен вредоносный код |
| Конфигурация IAM/сети | Определяет границы доступа |

## 2.2. Основные security invariants

Это инварианты, которые нужно поддерживать.

1. **Только аутентифицированный пользователь может создать upload job.**
2. **Только владелец job может использовать выданный upload token/presigned URL.**
3. **Браузер не имеет постоянного доступа к S3.**
4. **Каждый S3 key генерируется сервером и содержит случайный идентификатор.**
5. **Имя файла пользователя не используется как S3 key.**
6. **Каждый объект проверяется после загрузки на сервере.**
7. **Медиа публикуются только после успешной валидации и обработки.**
8. **Staging‑объекты имеют короткий TTL.**
9. **Orphan‑объекты удаляются автоматически.**
10. **Нет public access к bucket, если медиа приватные.**
11. **Нет List для браузеров и обычных user service accounts.**
12. **Нет user‑controlled command arguments в FFmpeg/ImageMagick.**
13. **Все действия по upload/delete/admin логируются.**
14. **Все финансовые метрики мониторятся: storage, requests, egress, multipart, processing.**
15. **Удаление медиа — управляемая, аудируемая операция.**

# 4. Целевой безопасный data flow

Ниже — рекомендуемый целевой поток, относительно которого строится threat model.

```text
1. Browser
   Пользователь выбрал файл.

2. Browser -> Backend API
   POST /media/uploads/request

3. Backend
   - проверяет аутентификацию;
   - проверяет права;
   - проверяет quota;
   - проверяет rate limit;
   - создает media object в БД со статусом PENDING_UPLOAD;
   - генерирует случайный key;
   - создает staging S3 key;
   - выдает кратковременный presigned URL либо принимает файл через API.

4. Browser -> S3 staging
   PUT исходный файл.

5. Backend -> S3
   HeadObject/GetObject
   - проверка реального размера;
   - проверка magic bytes;
   - проверка формата;
   - обновление состояния.

6. Backend -> Worker queue
   Задача на обработку.

7. Worker
   - скачивает staging object;
   - валидирует;
   - перекодирует;
   - создает финальный объект;
   - создает thumbnail/poster;
   - обновляет БД.

8. S3
   - staging object удаляется;
   - processed object сохраняется.

9. Browser -> Backend
   Получить URL или просмотреть медиа.

10. Backend
   - проверяет права;
   - выдает короткий signed GET
   - или stream через backend.
```

Ключевой принцип:

> **Безопасная граница — backend.**  
> Браузер и исходный файл считаются недоверенными до тех пор, пока сервер не валидировал и не нормализовал объект.

# 5. STRIDE-модель

STRIDE:

- **S** — Spoofing, подмена;
- **T** — Tampering, искажение;
- **R** — Repudiation, отрицание;
- **I** — Information Disclosure, раскрытие информации;
- **D** — Denial of Service, отказ в обслуживании;
- **E** — Elevation of Privilege, повышение привилегий.

Ниже — детальный threat register.

Оценка:

- **Impact** — возможный ущерб;
- **Likelihood** — вероятная частота;
- **Risk** — комбинация impact и likelihood;
- все оценки качественные: High / Medium / Low.

# 6. STRIDE: Spoofing — подмена

## 6.1. S-01: Подмена пользователя через подделку токена/сессии

| Поле | Значение |
|---|---|
| ID | S-01 |
| Актив | Идентичность пользователя |
| Сценарий | Атакующий получает чужой токен, cookie или session и от имени пользователя создает загрузки/читает медиа |
| Профиль атакующего | Внешний злоумышленник, фишинг, утечка токена |
| Impact | High |
| Likelihood | Medium |
| Baseline risk | High |
| Mitigations | Сильная аутентификация; подписанные токены; короткие сроки жизни; refresh rotation; привязка к user_id; проверка issuer/audience; запрет повторного использования отозванных токенов |
| Verification | Проверить использование токена другого пользователя; просроченного токена; токена с неверной подписью; отозванного refresh token |

## 6.2. S-02: CSRF — загрузка/удаление от имени пользователя со злоумышленной страницы

| Поле | Значение |
|---|---|
| ID | S-02 |
| Актив | Действия пользователя |
| Сценарий | Злоумышленная страница заставляет браузер пользователя отправить POST на создание upload, публикацию или удаление медиа |
| Профиль атакующего | Внешний атакующий |
| Impact | Medium |
| Likelihood | Medium |
| Baseline risk | Medium |
| Mitigations | SameSite cookie; CSRF token; проверка Origin/Referer; запрет изменяющих операций через GET; CORS без `*` |
| Verification | Попробовать выполнить запрос с другого origin; проверить отказ без CSRF token; проверить SameSite |

## 6.3. S-03: Подмена типа файла

| Поле | Значение |
|---|---|
| ID | S-03 |
| Актив | Содержимое медиа |
| Сценарий | Клиент заявляет `Content-Type: image/jpeg`, а фактически отправляет HTML, SVG, JS, EXE или другой недопустимый тип |
| Профиль атакующего | Внешний пользователь |
| Impact | High |
| Likelihood | High |
| Baseline risk | High |
| Mitigations | Magic bytes; allowlist форматов; серверная валидация; перекодирование; запрет недоверенных форматов; `nosniff` |
| Verification | Отправить SVG с `Content-Type: image/jpeg`; отправить HTML с `image/png`; отправить polyglot; убедиться, что сервер отклоняет или безопасно нормализует |

## 6.4. S-04: Подмена формата через polyglot-файл

| Поле | Значение |
|---|---|
| ID | S-04 |
| Актив | Безопасность обработки |
| Сценарий | Файл начинается как JPEG, а внутри/в конце содержит HTML/JS/скрипт или другой формат |
| Профиль атакующего | Внешний пользователь |
| Impact | High |
| Likelihood | Medium |
| Baseline risk | High |
| Mitigations | Строгая валидация; re-encode в безопасный формат; запрет SVG без санитизации; удаление метаданных; проверка magic bytes и структуры контейнера |
| Verification | Тесты polyglot-образцов; проверка, что финальный объект не содержит недоверенных секций |

## 6.5. S-05: Подмена upload job / idempotency key

| Поле | Значение |
|---|---|
| ID | S-05 |
| Актив | Job загрузки |
| Сценарий | Атакующий пытается использовать чужой job id, idempotency key или presigned URL не для своей загрузки |
| Профиль атакующего | Внешний пользователь |
| Impact | Medium |
| Likelihood | Medium |
| Baseline risk | Medium |
| Mitigations | Job привязан к user_id; presigned URL ограничен конкретным key; проверка владельца; одноразовые job; короткие сроки жизни |
| Verification | Попытка использовать job/presigned URL другого пользователя; попытка повторного использования после завершения |

## 6.6. S-06: Подмена source IP / user agent / origin

| Поле | Значение |
|---|---|
| ID | S-06 |
| Актив | Логирование и rate limit |
| Сценарий | Атакующий подделывает IP, UA или Origin, чтобы обойти rate limit, geo-ограничения или логирование |
| Профиль атакующего | Внешний пользователь |
| Impact | Low |
| Likelihood | Medium |
| Baseline risk | Low |
| Mitigations | Доводить доверия до trusted proxy; rate limit по пользовательской сущности, а не только IP; логировать trusted fields |
| Verification | Проверить, что rate limit работает по user_id, а не только по IP; проверить корректность парсинга X-Forwarded-For |

## 6.7. S-07: Подмена администратора / insider spoofing

| Поле | Значение |
|---|---|
| ID | S-07 |
| Актив | Админ‑права |
| Сценарий | Атакующий получает доступ к админской сессии или подделывает админские запросы |
| Профиль атакующего | Insider или внешний с украденными креденшелами |
| Impact | High |
| Likelihood | Low |
| Baseline risk | Medium |
| Mitigations | MFA; RBAC; минимальные права; аудит; временные elevated access; запрет постоянных admin-ключей |
| Verification | Проверить, что без MFA admin-действия блокируются; проверить аудит админских операций |

## 6.8. S-08: Компрометация service account / cloud identity spoofing

| Поле | Значение |
|---|---|
| ID | S-08 |
| Актив | Cloud identity |
| Сценарий | Утечка service account key или компрометация backend позволяет атакующему выполнять действия в S3 от имени сервиса |
| Профиль атакующего | Атакующий с доступом к backend или утечкой секрета |
| Impact | High |
| Likelihood | Low |
| Baseline risk | Medium |

| Verification | Проверить effective IAM permissions; проверить отсутствие прав List/Delete у API; проверить аудит S3-операций |

# 7. STRIDE: Tampering — искажение

## 7.1. T-01: Изменение объекта после загрузки и до валидации

| Поле | Значение |
|---|---|
| ID | T-01 |
| Актив | Содержимое медиа |
| Сценарий | После PUT в staging объект повторно загружается/меняется до того, как backend начал валидацию |
| Профиль атакующего | Пользователь с valid presigned URL |
| Impact | Medium |
| Likelihood | Medium |
| Baseline risk | Medium |
| Mitigations | Одноразовый upload; unique key; короткоживущий URL; state machine; после первой загрузки job считается completed; повторная валидация перед обработкой; проверка размера/типа перед запуском processing |
| Verification | Проверить повторный PUT по тому же URL; попытку использования старого URL после job completed; загрузку с другим размером |

## 7.2. T-02: Подмена ссылки на объект в базе данных

| Поле | Значение |
|---|---|
| ID | T-02 |
| Актив | Связь медиа с сообщением |
| Сценарий | Из-за SQLi, логической ошибки или инсайдерского доступа запись медиа указывает на чужой/вредоносный объект |
| Профиль атакующего | SQLi-атакующий или компрометированный backend |
| Impact | High |
| Likelihood | Low |
| Baseline risk | Medium |
| Mitigations | Parameterized queries; ORM; server-side ownership checks; проверка существования и владельца объекта при выдаче URL; минимальные права БД |
| Verification | Тесты SQLi; попытка получить URL на чужой объект; проверка, что backend не доверяет user-controlled object key |

## 7.3. T-03: Изменение параметров обработки медиа

| Поле | Значение |
|---|---|
| ID | T-03 |
| Актив | Worker / transcode pipeline |
| Сценарий | Пользовательские параметры попадают в FFmpeg/ImageMagick и позволяют изменить обработку или вызвать command injection |
| Профиль атакующего | Внешний пользователь |
| Impact | High |
| Likelihood | Medium |
| Baseline risk | High |
| Mitigations | Запрет пользовательских аргументов; фиксированные transcode-профили; process spawn без shell; whitelist флагов; строгие лимиты; container isolation |

# 12. Специфические угрозы для Yandex Object Storage / S3-совместимого хранилища

Ниже — не конкретные API-заявления, а **требования к проверке**.

## 12.1. Bucket policy

Нужно проверить:

1. Анонимный GET/PUT/DELETE/List — `403`.
2. Браузер не может List.
3. Обычный user identity не может List.
4. API service account не может Delete, если удаление делает cleanup service.
5. Worker service account не может писать вне назначенного prefix.
6. Cleanup service может удалять только staging/orphan/final по policy.
7. Public access denied.

## 12.2. Presigned URLs

Нужно проверить:

1. Presigned URL живет 3–15 минут.
2. URL привязан к конкретному key.
3. URL привязан к конкретному HTTP методу.
4. URL нельзя переиспользовать после завершения job, если это требуется.
5. URL нельзя изменить key и получить доступ.
6. URL нельзя использовать для List.
7. URL нельзя использовать для DELETE.
8. URL для PUT нельзя использовать для GET.

Точные возможности ограничения повторного использования и условий presigned URL нужно сверять с актуальной документацией Yandex Object Storage.

## 12.3. Encryption

Нужно проверить:

1. TLS в transit.
2. Server-side encryption at rest включено.
3. Ключи управляются централизованно.
4. Ключи не выдаются браузеру.
5. Если используется KMS/аналог — права минимальные.

## 12.4. Versioning

По умолчанию рекомендуется:

```text
Versioning: disabled
```

Если включать:

1. Нужно lifecycle для NoncurrentVersions.
2. Нужно алерт на рост versioned objects.
3. Нужно понимание стоимости.

## 12.5. Lifecycle

Обязательные правила:

1. Staging objects удаляются через 1–24 часа.
2. Unfinished multipart abort через 1–24 часа.
3. Orphan cleanup ежедневно.
4. Deleted media удаляются по retention.
5. Failed final objects удаляются сразу или через короткий TTL.
6. Нужно monitoring lifecycle transitions.

## 12.6. Monitoring / Billing

Нужно проверить доступность и настроить:

1. Storage size.
2. Object count.
3. PUT requests.
4. GET requests.
5. List requests.
6. 4xx/5xx.
7. 403/404.
8. Egress bytes.
9. Ingress bytes.
10. Multipart count.
11. Active multipart.
12. Lifecycle transitions.
13. Daily cost.
14. Budget threshold alerts.
15. Anomaly alerts.

Точные метрики и имена нужно сверять с актуальной документацией Yandex Cloud.

# 13. Критические инварианты для защиты от DoS и “огромного счета”

Это, пожалуй, самая важная часть для вашего требования.

## 13.1. Квоты

Нужны квоты на всех уровнях.

### Пользователь

Пример:

```text
max_files_per_user_day: 20
max_bytes_per_user_day: 5 GB
max_total_storage_per_user: 20 GB
max_concurrent_uploads_per_user: 2
max_processing_jobs_per_user: 3
max_download_bytes_per_user_day: 50 GB
```

### Организация, если есть

```text
max_bytes_per_org_day: 100 GB
max_total_storage_per_org: 1 TB
max_concurrent_processing_jobs_per_org: 20
```

### Глобально

```text
max_total_storage_feature: 5 TB
max_new_bytes_per_hour: 500 GB
max_global_concurrent_uploads: 500
max_global_processing_queue: 200
max_global_uploads_per_hour: 10000
```

Цифры нужно подбирать под тариф и продукт.

## 13.2. Pre-upload check

Перед выдачей presigned URL или принятием файла:

1. Проверить auth.
2. Проверить права.
3. Проверить declared size.
4. Проверить quota.
5. Проверить daily quota.
6. Проверить global quota.
7. Проверить rate limit.
8. Создать job.
9. Выдать URL или принять файл.

Важно:

> **Declared size — не истина. Финальная проверка — после загрузки.**

## 13.3. Post-upload check

После загрузки:

1. `HeadObject` / эквивалент.
2. Проверить реальный размер.
3. Проверить magic bytes.
4. Проверить формат.
5. Проверить, что key соответствует job.
6. Обновить БД.
7. Запустить processing.
8. Если размер больше лимита — удалить объект.
9. Если обработка не прошла — удалить объекты.

## 13.4. One-time upload

Если используется presigned PUT:

1. Job должен быть одноразовым.
2. После первой успешной загрузки job считается `UPLOADED`.
3. Повторное использование URL должно быть отклонено.
4. Если S3 позволяет повторный PUT до expiration, это нужно компенсировать application logic.

## 13.5. Multipart limits

Обязательно:

```text
max_part_size: например 64–512 MB
max_parts_per_upload: например 10–100
max_concurrent_multipart_per_user: 1
multipart_ttl: 1–24 hours
auto_abort: true
```

## 13.6. Processing limits

Для каждого worker job:

```text
max_input_size: 2 GB
max_duration_video: 5 min
max_resolution_video: 1920x1080
max_image_width: 4096
max_image_height: 4096
max_processing_time: 180 sec
max_cpu: 1–2 cores
max_memory: 1–2 GB
max_output_size: 500 MB
```

## 13.7. Budget guardrails

Нужны алерты:

```text
storage_size > threshold
storage_daily_growth > threshold
object_count > threshold
put_requests_per_hour > threshold
get_requests_per_hour > threshold
egress_bytes_per_hour > threshold
multipart_active > threshold
processing_queue_depth > threshold
failed_jobs_rate > threshold
daily_cost > threshold
weekly_cost > threshold
```

# 14. Рекомендуемая state machine для media object

## 14.1. Статусы

```text
PENDING_UPLOAD
UPLOADED
VALIDATING
PROCESSING
READY
FAILED
SOFT_DELETED
DELETED
```

## 14.2. Переходы

```text
PENDING_UPLOAD -> UPLOADED
   условие: объект успешно загружен и подтвержден backend

UPLOADED -> VALIDATING
   условие: backend начинает проверку

VALIDATING -> PROCESSING
   условие: проверка пройдена

VALIDATING -> FAILED
   условие: размер/тип/структура недопустимы

PROCESSING -> READY
   условие: финальный объект сохранен и валиден

PROCESSING -> FAILED
   условие: timeout, decoder error, output too large

READY -> SOFT_DELETED
   условие: сообщение/комментарий удален

SOFT_DELETED -> DELETED
   условие: retention истек, cleanup выполнен

FAILED -> DELETED
   условие: временные объекты удалены
```

## 14.3. Правила

1. Только backend и worker могут менять статус.
2. Браузер не может установить `READY`.
3. Если job `FAILED`, объекты удаляются.
4. Если `SOFT_DELETED`, signed URL больше не выдаются.
5. `DELETED` должно быть идемпотентным.
6. Каждый переход логируется.

# 18. Резidual risks после базовых мер

Даже после всех мер остаются риски:

1. **Zero-day в FFmpeg/ImageMagick.**
   Снижается изоляцией, sandboxing, обновлениями, но не исчезает полностью.

2. **Атака на enterprise network.**
   Если backend скомпрометирован, атакующий может создавать jobs. Нужны сегментация, IAM, audit.

3. **Атака на cloud identity.**
   Если service account key украден, возможны действия в S3. Нужны минимальные права, ротация, audit.

4. **Billing anomaly из-за легитимной нагрузки.**
   Реальные пользователи могут создать большой трафик. Нужны budget alerts и capacity planning.
