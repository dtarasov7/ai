Ниже — инженерная проработка по информационной безопасности и защите от DoS/неконтролируемых затрат для сценария: веб‑приложение, пользовательские фото/видео, хранение в S3‑совместимом объектном хранилище Yandex Cloud, предварительная проверка и перепаковка/сжатие.

Я отдельно выделяю:

- **факты/заявления из условия**;
- **допущения**;
- **гипотезы/риски**;
- **предлагаемые меры**;
- **конкретные шаги проверки**.

---

## 1. Исходные факты, допущения и гипотезы

### Факты из условия

1. Есть веб‑приложение:
   - клиентская часть в браузере пользователя;
   - бекенд на серверах предприятия.
2. Пользователь может:
   - создать сообщение;
   - оставить комментарий;
   - вставить фото или видео.
3. Планируется хранение медиа в объектном хранилище Yandex, S3‑совместимое.
4. Фото и видео планируется:
   - проверить;
   - при необходимости перепаковать/сжать.
5. Требуется проработать ИБ, в том числе защиту от DoS:
   - переполнение хранилища;
   - огромный счет за хранение/запросы/egress/обработку.

### Допущения

Ниже я исхожу из следующих технических допущений. Если что-то не совпадает — нужно скорректировать проект.

1. Пользователи аутентифицированы.
2. Медиа связаны с сообщениями/комментариями в базе данных.
3. Бекенд имеет доступ к Yandex Object Storage.
4. Браузер не должен иметь постоянного доступа к S3.
5. Обработка медиа выполняется на сервере предприятия или в выделенных worker‑процессах.
6. Hranение нужно, скорее всего, приватное: медиа показывается в рамках приложения, а не как публичный сайт.
7. Yandex Object Storage используется как S3‑совместимое API.

### Гипотезы/главные риски

1. **Клиентская валидация не может считаться безопасной.**
   Браузер можно обойти, изменив заголовки, тип, размер, содержимое файла.

2. **Прямой загрузочный доступ браузера в S3 может создать риск обхода бекенда.**
   Если выдать браузеру слишком широкий presigned URL, злоумышленник может загрузить мусор, занять хранилище или вызвать обработку.

3. **Необработанный исходный файл — потенциальный вектор атаки.**
   Форматы изображений и видео могут использоваться для:
   - decoder exploit;
   - zip bomb / dimension bomb;
   - перегрузки CPU/RAM при перекоде;
   - загрузки скрытых скриптов/метаданных;
   - обхода типизации.

4. **Хранилище S3 само по себе не защищает от бизнес‑DoS.**
   S3 может масштабироваться, но счет может вырасти из-за:
   - объема хранения;
   - количества объектов;
   - количества PUT/GET/List;
   - egress;
   - незавершенных multipart‑загрузок;
   - “сиротских” объектов без привязки к сообщению.

5. **Медиа могут содержать персональные данные.**
   Фото и видео могут содержать лица, документы, геоданные, метаданные. Это влияет на retention, удаление, аудит и compliance.

## 2. Ключевой принцип

**Безопасный upload‑пайплайн должен быть полностью контролируемым бекендом.**

Браузер может только:

- показать пользователю предварительный размер;
- сделать UI‑валидацию;
- отправить запрос на получение права на загрузку.

Бекенд обязан:

- проверить пользователя;
- проверить квоты;
- выдать ограниченный право на загрузку;
- создать объект в своей базе;
- проверить финальный объект;
- обработать его;
- сохранить только безопасную финальную версию;
- удалить временный объект.

Коротко:

> Клиент — недоверенный.  
> Бекенд — доверенная точка контроля.  
> S3 — не место хранения недоверенных временных файлов без strict lifecycle.

## 3. Рекомендуемая целевая архитектура

## 3.1. Обобщенный поток

```text
Browser
  |
  | 1. Пользователь выбрал файл
  | 2. Запрос к API: POST /media/uploads/request
  |
Backend API
  |
  | 3. Проверка auth, quota, rate limit, file type/size
  | 4. Создает запись media_object со статусом UPLOAD_PENDING
  | 5. Создает S3 key: media/staging/{user_id}/{uuid}
  | 6. Выдает кратковременный presigned URL
  |
Browser
  |
  | 7. PUT файл в S3 staging bucket
  |
Yandex Object Storage
  |
  | 8. Backend проверяет объект через S3 API
  | 9. Запускает проверку/обработку
  |10. Worker валидирует, реэнкодирует, создает финальный объект
  |11. Backend обновляет media_object: PROCESS_OK
  |12. Связывает объект с сообщением/комментарием
  |13. Удаляет staging‑объект
```

Если приложение небольшое, можно делать проще:

```text
Browser -> Backend API -> Backend принимает файл -> S3
```

То есть бекенд сам принимает upload через HTTP, а затем сохраняет в S3.

Это безопаснее и проще, но требует, чтобы API/бекенд выдерживал трафик загрузок.

## 4. Варианты реализации загрузки

## Вариант A: Загрузка через бекенд

### Схема

```text
Browser -> Backend /api/media/upload -> S3
```

### Плюсы

- Максимальный контроль.
- Легче реализовать квоты.
- Легче проверять `Content-Length` до попадания в S3.
- Не нужно выдавать браузеру presigned URLs.
- Проще блокировать недопустимые типы.
- Легче интегрировать с rate limiter и WAF.

### Минусы

- Через бекенд проходит весь медиа‑трафик.
- Нужны выделенные upload‑ноды/воркеры, если трафик большой.

### Когда выбирать

Если ожидаемый размер файлов умеренный:

- фото до 10–20 МБ;
- видео до 100–300 МБ после обработки;
- количество одновременных загрузок не экстремальное.

Это **самый безопасный и простой вариант** для корпоративного web‑приложения.

---

## Вариант B: Presigned URL в S3

### Схема

```text
Browser -> Backend: получить presigned URL
Browser -> S3: PUT объект
Backend: проверить S3 объект и обработать
```

### Плюсы

- Меньше нагрузка на бекенд.
- Хорошо масштабируется.
- Подходит для больших видео.

### Риски

- Presigned URL должен быть:
  - короткоживущим;
  - ограниченным по key;
  - ограниченным по HTTP‑методу;
  - связанным с конкретным user/job;
  - не выдаваться повторно для повторной загрузки того же key.

### Рекомендуемые ограничения

- Время жизни presigned URL: **3–15 минут**, максимум 30 минут.
- Один URL — один объект.
- Один URL — один HTTP PUT.
- После первой успешной загрузки URL больше не используется.
- Бекенд обязательно проверяет объект после загрузки.
- Запретить браузеру List/Get/Delete.
- Запретить браузеру писать в произвольные key.

### Важно

Presigned URL для PUT обычно не гарантирует, что файл будет именно того размера, который вы ожидаете, если клиент может отправить произвольное тело. Поэтому после загрузки нужно выполнить `HeadObject`/эквивалент и проверить реальный размер.

---

## Вариант C: Multipart upload

Для больших видео можно использовать multipart:

```text
Browser -> Backend: начать multipart
Backend: создает multipart upload, выдает presigned URL на части
Browser: выгружает части
Browser/Backend: завершает multipart
Backend: проверяет итоговый объект и обрабатывает
```

### Обязательные ограничения

- Максимальный размер итогового файла.
- Максимальное число частей.
- Размер каждой части.
- Максимальное количество одновременных multipart‑сессий на пользователя.
- Максимальное время жизни multipart.
- Автоматический abort незавершенных multipart.
- Ограничение числа multipart‑запросов на пользователя/IP.

### Причина

Multipart сам по себе может стать источником расходов:

- много PUT part;
- незавершенные сессии;
- много abort/complete;
- много мелких объектов/запросов.

## 5. Хранение: структура S3 и ключи

## 5.1. Рекомендуемые зоны

Лучше разделить данные по bucket/prefix.

### Вариант с одним bucket и префиксами

```text
media-staging/
  {user_id}/
    {uuid}-raw

media-processed/
  {user_id}/
    {uuid}-final

media-thumbnails/
  {user_id}/
    {uuid}-thumb

media-posters/
  {user_id}/
    {uuid}-poster

media-logs/
  ...
```

### Вариант с отдельными buckets

```text
media-staging-private
media-processed-private
media-thumbnails-private
media-logs
```

Отдельные buckets предпочтительнее, если нужно разное IAM/retention/lifecycle.

---

## 5.2. Naming объектов

Никогда не использовать user‑controlled имена файлов как S3 key.

Плохо:

```text
uploads/photo.jpg
uploads/{user_name}/{original_filename}
```

Хорошо:

```text
media/staging/{user_id}/{uuid4}.bin
media/final/{user_id}/{uuid4}.mp4
```

### Почему

- защита от path traversal;
- защита от перезаписи чужих объектов;
- защита от конфликта имен;
- защита от раскрытия внутреннего имени файла;
- упрощение аудит.

Исходное имя файла можно хранить в метаданных/БД, но не использовать в S3 key.

## 6. Проверка файлов

## 6.1. Что проверять

### 6.1.1. Тип по magic bytes

Не доверять:

- `Content-Type` из браузера;
- расширению файла;
- MIME из заголовка.

Определять тип по содержимому.

Примеры:

```text
JPEG: FF D8 FF
PNG:  89 50 4E 47 0D 0A 1A 0A
MP4:  ftyp box в заголовке
WebM: EBML header
```

Нужен allowlist, а не blocklist.

### 6.1.2. Рекомендуемый allowlist

#### Изображения

Если нет бизнес‑необходимости:

```text
JPEG
PNG
WebP
```

Можно добавить:

```text
HEIC/HEIF
```

только если ваша обработка реально поддерживает и безопасно транскодирует эти форматы.

Если есть риск XSS, **не разрешать SVG** без мощной санитизации.

Лучше:

```text
SVG запрещен
```

Если SVG обязателен:

- отдельный пайплайн;
- строгая санитизация;
- запрет внешних ссылок;
- запрет JavaScript;
- отдельный Content-Type;
- отдельная проверка;
- запрет использования SVG как аватарки/миниатюры без полной безопасности.

#### Видео

Рекомендуемый безопасный набор:

```text
MP4:
  - H.264/AVC
  - AAC

WebM:
  - VP8/VP9
  - Vorbis/Opus
```

После обработки лучше сохранять в канонический формат:

```text
MP4 H.264 + AAC
```

или, если нужен современный кодировщик:

```text
MP4 H.264/AAC для совместимости
```

Если приложение внутреннее и все клиенты поддерживают HEVC/AV1 — можно обсуждать, но с точки зрения совместимости H.264/AAC обычно проще.

## 6.2. Лимиты для изображений

Примеры. Значения нужно подгонять под продукт и стоимость.

| Параметр | Примерный лимит | Комментарий |
|---|---:|---|
| Максимальный исходный файл | 20–50 МБ | до обработки |
| Максимальный финальный файл | 2–10 МБ | после сжатия |
| Максимальные размеры | 4096x4096 | защита от memory bomb |
| Максимальное число кадров для GIF | 100 | если разрешаете GIF |
| Максимальная глубина цвета | 8/16 bit | по необходимости |
| Метаданные | удалить EXIF/XMP/GPS | privacy |
| Финальный формат | WebP/JPEG/PNG | нормализация |

### Опасности

- изображение с заявленными размерами `100000x100000`;
- PNG с огромным числом пикселей;
- GIF с большим числом кадров;
- EXIF с вложенными данными;
- вредоносный SVG со скриптом;
- полифайл: JPEG с вложенным HTML/JS.

### Рекомендуемая обработка

1. Проверить magic bytes.
2. Проверить реальные размеры/количество кадров.
3. Ограничить CPU/RAM/time.
4. Перекодировать в безопасный формат.
5. Удалить метаданные.
6. Сохранить финальный объект.
7. Создать thumbnail/poster.

---

## 6.3. Лимиты для видео

Примерные лимиты.

| Параметр | Примерный лимит | Комментарий |
|---|---:|---|
| Максимальный исходный файл | 500 МБ–2 ГБ | до обработки |
| Максимальный финальный файл | 100–500 МБ | зависит от продукта |
| Максимальная длительность | 1–5 минут | для комментариев обычно достаточно |
| Максимальное разрешение | 1920x1080 или 1280x720 | защита от перегрузки |
| Максимальный FPS | 30 или 60 | по продукту |
| Аудио | AAC 128–192 kbps | нормализация |
| Видео битрейт | 1.5–4 Мбит/с | зависит от разрешения |
| Максимальное время обработки | 60–180 секунд | hard timeout |
| CPU/на задачу | ограничить | cgroup/ulimit |
| RAM/на задачу | ограничить | cgroup/ulimit |
| Число трек | видео 1, аудио 1 | отклонить сложные контейнеры |

### Опасности

- очень длинное видео;
- очень высокое разрешение;
- высокий битрейт;
- битый MP4;
- много аудио/подписей/трков;
- вредоносный контейнер;
- FFmpeg/ImageMagick vulnerabilities;
- бесконечная обработка;
- очередь переполняется;
- процессоры рабочих серверов заняты.

## 7. Обработка медиа: безопасность пайплайна

## 7.1. Обработка должна быть изолированной

Не обрабатывать медиа в основном API‑процессе, если это возможно.

Нужны отдельные воркеры:

```text
API process:
  - auth
  - quota
  - create job
  - schedule job

Worker process:
  - download from staging
  - validate
  - transcode
  - upload final
  - cleanup
```

### Требования к worker

- отдельный процесс/контейнер;
- ограничение CPU;
- ограничение RAM;
- ограничение времени;
- ограничение размера входного файла;
- запрет shell;
- запрет произвольных путей;
- обновление библиотек;
- минимальные права S3;
- логирование без содержимого файла.

### Пример ограничений

Для каждого transcode:

```text
CPU: 1–2 cores
RAM: 1–2 GB
Time: 60–180 sec
Input size: <= 2 GB
Output size: <= 500 MB
```

Если процесс превысил лимит — убить, удалить временный объект, пометить как `PROCESS_FAILED`.

---

## 7.2. Использование FFmpeg

Если планируете использовать FFmpeg, важно:

1. Не собирать команду через shell.
2. Не передавать пользовательские строки как аргументы shell.
3. Использовать безопасный запуск процесса.
4. Ограничить ввод.
5. Использовать allowlist контейнеров.
6. Ограничить время.
7. Обновлять FFmpeg.
8. В идеале — запускать в контейнере/VM с seccomp/AppArmor/SELinux, если доступно.

### Пример безопасных идей

Не так:

```bash
ffmpeg -i "$user_file" -c:v libx264 out.mp4
```

Если `$user_file` приходит из пользовательского ввода и запускается через shell — это плохо.

Лучше:

```text
Process:
  executable: /usr/bin/ffmpeg
  args:
    - -hide_banner
    - -loglevel
    - error
    - -i
    - /tmp/jobs/{uuid}/input
    - -t
    - 300
    - -vf
    - scale='min(1920,iw)':-2
    - -c:v
    - libx264
    - -preset
    - veryfast
    - -b:v
    - 2M
    - -c:a
    - aac
    - -b:a
    - 128k
    - -map_metadata
    - -1
    - -movflags
    - +faststart
    - -y
    - /tmp/jobs/{uuid}/output
  timeout_sec: 180
  cpu_limit: 2
  memory_limit_mb: 2048
```

Точные флаги нужно подбирать под вашу нагрузку и проверять нагрузочными тестами.

---

## 7.3. Использование ImageMagick

Если используете ImageMagick:

- обязательно применить `policy.xml`;
- запретить опасные форматы;
- ограничить ресурсы;
- использовать `identify` с лимитами;
- не разрешать SVG без строгих ограничений;
- не обрабатывать файлы с правами root;
- держать ImageMagick обновленным.

Типовые ограничения:

```text
policy:
  - disallow SVG
  - disallow MSL
  - disallow EPHEMERAL
  - limit width 4096
  - limit height 4096
  - limit area 16MP
  - limit disk 100MB
  - limit memory 256MB
  - limit map 512MB
```

Конкретный синтаксис зависит от версии, нужно проверять в вашей среде.

## 8. Хранение в Yandex Object Storage

## 8.1. Приватность

По умолчанию:

```text
Bucket: private
Public access: denied
```

Доступ только через:

- backend service account;
- presigned GET/PUT;
- IAM policy.

Нельзя делать bucket public, если медиа привязаны к пользователям и комментариям, а не к публичному CDN.

---

## 8.2. Разделение прав

### Браузер

Браузер не должен иметь IAM‑ключей и не должен иметь постоянного доступа к S3.

Допустимо:

- presigned PUT для staging;
- presigned GET для просмотра, если нужно.

Запрещено:

- List bucket;
- Delete;
- PutObject в произвольные ключи;
- GetObject без разрешения;
- доступ к staging других пользователей.

### Backend API

Backend API должен иметь право:

- создавать job;
- подписывать короткие URL;
- проверять объект;
- запускать обработку.

Но лучше разделить:

```text
api-service-account:
  - Create Multipart
  - Generate presigned URL
  - HeadObject
  - PutObject staging?
  - GetObject staging?

worker-service-account:
  - GetObject staging
  - PutObject final
  - DeleteObject staging
  - DeleteObject failed final
```

Идеально — минимальные права для каждой роли.

---

## 8.3. Bucket policy

Целевая логика:

```text
deny by default
allow only:
  - backend service account
  - worker service account
  - presigned requests
```

Нужно проверить конкретный синтаксис Yandex Object Storage, потому что S3‑совместимые политики могут отличаться деталями.

### Обязательные проверки

1. Анонимный запрос без подписи получает `403`.
2. Presigned URL с истекшим временем получает `403`.
3. Presigned URL на PUT не работает для GET.
4. Presigned URL на один key не работает для другого key.
5. Browser/service account не может выполнить `ListObjects`.
6. Worker не может писать в staging, только читать, если вы так разделите права.
7. API не может удалять объекты, если удаление делает только lifecycle/cleanup service.

---

## 8.4. Шифрование

Обязательно:

```text
TLS в transit
Server-side encryption at rest
```

Варианты:

- SSE-S3;
- SSE-KMS, если нужна более сложная модель ключей и аудит.

Для корпоративного приложения я бы рекомендовал как минимум SSE-S3, а KMS — если у вас уже есть управляемые ключи и compliance‑требования.

---

## 8.5. Метаданные объектов

Для каждого объекта S3:

```text
Content-Type: image/jpeg | image/png | image/webp | video/mp4
Cache-Control: private, max-age=0
X-Content-Type-Options: nosniff
```

`X-Content-Type-Options: nosniff` особенно важен, если объекты могут быть доступны через браузер.

Если объекты идут через CDN:

- установить правильный `Content-Type`;
- включить `nosniff`;
- не позволять браузеру интерпретировать бинарный контент как HTML;
- ограничить рефереры/оригины, если используется публичный CDN.

---

## 8.6. Versioning

Для медиа лучше по умолчанию:

```text
Versioning: disabled
```

Или использовать только если есть строгие причины:

- compliance;
- восстановление;
- аудит.

### Почему

Versioning увеличивает стоимость и может накапливать старые версии после атаки.

Если включите versioning:

- добавьте lifecycle для NoncurrentVersions;
- ограничьте время жизни старых версий;
- настройте алерты.

---

## 9. Защита от DoS и “огромного счета”

Здесь нужно думать не только о “размере файла”, а обо всех линиях затрат.

## 9.1. Линии затрат и угрозы

| Линия затрат | Как может взлететь | Что делать |
|---|---|---|
| Хранение | Много объектов | quotas, retention, lifecycle, delete |
| PUT запросы | Много мелких загрузок | rate limit, max objects, batch check |
| GET запросы | Много просмотров | CDN, signed URL, cache, rate limit |
| Egress | Много выгрузки | private bucket, signed URL, limits |
| Multipart | Много частей/abort | лимиты части, TTL, auto-abort |
| Обработка | Transcode CPU/RAM | queue limits, timeouts, cgroup |
| List | Списоковые запросы | запретить List, аудит |
| Логирование | Огромные логи | sampling, retention |
| Lifecycle transitions | Массовые переходы | проверять policy, alert |

---

## 9.2. Квоты

Нужны квоты на нескольких уровнях.

### Пользователь

Пример:

```text
max_media_per_user_day: 20
max_bytes_per_user_day: 5 GB
max_total_media_per_user: 20 GB
max_concurrent_uploads_per_user: 2
max_upload_size_per_file: 2 GB
max_video_duration: 5 min
```

### Организация/проект

Если приложение многопользовательское:

```text
max_bytes_per_org_day: 100 GB
max_total_media_per_org: 1 TB
max_concurrent_processing_jobs: 20
```

### Глобально

```text
max_total_storage_feature: 5 TB
max_new_bytes_per_hour: 500 GB
max_global_concurrent_uploads: 500
max_global_processing_queue: 200
```

Эти цифры — примеры. Нужно выбирать по тарифу, продукту и бюджету.

---

## 9.3. Pre‑upload quota check

Перед выдачей presigned URL или принятием upload:

1. Проверить пользователя.
2. Проверить, что сообщение/комментарий можно создавать.
3. Проверить `declared_size`.
4. Проверить квоту пользователя.
5. Проверить дневную квоту.
6. Проверить глобальный бюджет.
7. Проверить rate limit.
8. Создать job.
9. Выдать короткий URL или принять файл.

### Важно

`declared_size` нельзя считать истиной. Это только ранний фильтр.

Финальная проверка — после появления объекта в S3:

```text
actual_size = HeadObject(key).content_length
```

Если `actual_size > limit` — удалить объект и отклонить.

---

## 9.4. Post‑upload quota check

После загрузки:

1. Вызвать `HeadObject`.
2. Проверить реальный размер.
3. Проверить, что файл не переопределил чужой key.
4. Проверить, что MIME по magic bytes совпадает.
5. Обновить БД.
6. Запустить processing.
7. После обработки снова проверить размер финального объекта.

Если обработка не прошла:

- удалить staging;
- удалить failed final;
- пометить job как `PROCESS_FAILED`;
- не привязывать к сообщению.

---

## 9.5. Rate limiting

Нужны ограничения:

### По API

```text
/uploads/request:
  - 10 req/min per user
  - 100 req/min per IP
  - 1000 req/min global
```

### По загрузкам

```text
- max concurrent uploads per user
- max concurrent uploads per IP
- max concurrent uploads global
```

### По обработке

```text
- max processing jobs per user
- max processing jobs per queue
- max CPU worker concurrency
```

### По загрузкам медиа

```text
- max download/GET per user
- max download/GET per IP
- max egress per user/day
```

Если используется CDN, rate limit лучше ставить и на CDN, и на backend.

---

## 9.6. Cleanup and lifecycle

Это критически важно.

## 9.6.1. Staging objects

Staging — недоверенные временные файлы.

Политика:

```text
staging objects TTL: 1–24 часа
```

Если объект не обработан:

```text
delete staging object
```

Если обработка не успела:

```text
delete staging object
mark job failed
```

Нельзя позволить staging‑объектам жить бесконечно.

---

## 9.6.2. Unfinished multipart

Политика:

```text
abort multipart after 24 hours
```

Или короче, например 1–4 часа.

Нужно:

- периодически проверять незавершенные multipart;
- abort;
- логировать;
- алерт при аномальном количестве.

---

## 9.6.3. Orphan objects

Orphan — объект в S3, у которого нет валидной записи в БД или запись не связана с активным сообщением.

Причины:

- ошибка обработки;
- пользователь удалил комментарий;
- транзакция БД не завершилась;
- сбой cleanup;
- атака.

Нужен scheduled job:

```text
1. Найти S3 объекты старше N часов
2. Сопоставить с БД
3. Если нет валидной привязки — удалить
4. Логировать
5. Алерт при большом числе orphan
```

---

## 9.6.4. User deletion

Если пользователь удаляет сообщение/комментарий:

Варианты:

1. Удалить медиа сразу.
2. Оставить в карантине N дней.
3. Удалить по retention.

Рекомендуемая безопасная модель:

```text
Message deleted:
  - media.status = SOFT_DELETED
  - media.delete_after = now + retention_period
Lifecycle job:
  - delete final object
  - delete thumbnails/posters
  - update metadata
```

### Деструктивная операция

Удаление объектов S3 — деструктивная операция. Поэтому нужно:

- хранить метаданные;
- иметь аудит;
- не удалять без проверки;
- иметь ручной процесс восстановления, если данные случайно удалены;
- иметь четкую retention policy.

---

## 9.7. Бюджетные алерты

Нужно настроить алерты в Yandex Cloud/вашем billing.

### Обязательные алерты

```text
Хранилище:
  - total storage size crossed threshold
  - daily growth > X TB
  - object count crossed threshold

Запросы:
  - PUT requests per hour
  - GET requests per hour
  - 403/404/5xx ratio

Multipart:
  - unfinished multipart count
  - multipart requests per hour

Processing:
  - queue depth
  - failed jobs
  - processing time p95
  - timeout count

Cost:
  - daily cost > threshold
  - weekly cost > threshold
  - anomaly detection
```

Точные метрики и возможности алертинга нужно проверить в актуальной документации Yandex Cloud.

## 10. Прикладная безопасность API

## 10.1. Аутентификация

Все upload‑эндпоинты должны быть защищены:

```text
POST /media/uploads/request
POST /media/uploads/{id}/complete
GET  /media/{id}/url
DELETE /messages/{id}
```

Без токена:

```text
401 Unauthorized
```

Без права на ресурс:

```text
403 Forbidden
```

---

## 10.2. Authorization

Пользователь может:

- загрузить медиа для своего сообщения/комментария;
- получить URL на свои медиа;
- удалить свои медиа, если разрешает бизнес‑логика.

Нельзя:

- получить URL на чужие медиа;
- удалить чужие медиа;
- загрузить медиа с чужим user_id;
- передать `user_id` в теле как доверенный параметр.

`user_id` должен браться из аутентификации, а не из запроса.

---

## 10.3. CORS

Настраивать минимально:

```text
Allowed origins:
  - your frontend domain(s)

Allowed methods:
  - POST
  - GET
  - maybe DELETE

Allowed headers:
  - Authorization
  - Content-Type

Expose headers:
  - minimum required
```

Не использовать:

```text
Access-Control-Allow-Origin: *
```

для API с auth и медиа.

---

## 10.4. CSRF

Если используется cookie‑auth:

- включить CSRF token;
- проверить `SameSite=Lax` или `Strict`;
- проверить Origin/Referer;
- не использовать GET для изменяющих операций.

Если используется bearer token:

- CSRF менее критичен, но все равно проверяйте Origin/Referer, если токен может быть в cookie.

---

## 10.5. Валидация API

Нужна строгая валидация:

```text
message text length
comment text length
file type
declared size
file name length
request id
idempotency key
```

Используйте схему запросов.

Пример поля:

```json
{
  "idempotencyKey": "uuid",
  "originalName": "photo.jpg",
  "declaredContentType": "image/jpeg",
  "declaredSizeBytes": 1234567
}
```

Но backend не должен верить этим полям как финальной правде.

---

## 10.6. Idempotency

Для upload request лучше использовать idempotency key.

Зачем:

- пользователь может нажать кнопку дважды;
- сеть может повесить запрос;
- можно избежать дублей.

Формат:

```text
Idempotency-Key: {uuid}
```

Backend:

- если key уже видел — вернуть существующий job;
- не создавать новый upload;
- не повторять processing.

---

## 11. Защита от XSS и injection

## 11.1. Медиа как XSS-вектор

Опасные случаи:

- SVG со скриптом;
- файл с `Content-Type: text/html`;
- браузер интерпретирует бинарный файл как HTML;
- CDN неверно отдает Content-Type.

### Меры

1. Не хранить HTML.
2. Не хранить SVG без строгой санитизации.
3. Отдавать медиа только как:
   - `image/jpeg`
   - `image/png`
   - `image/webp`
   - `video/mp4`
   - `video/webm`
4. Установить:
   ```text
   X-Content-Type-Options: nosniff
   ```
5. Использовать CSP на фронтенде.
6. Не вставлять содержимое файла в HTML.
7. Если есть preview, использовать `<img>` или `<video>` с src, а не raw HTML.

---

## 11.2. Command injection

При обработке:

- не использовать shell;
- не передавать имена файлов в shell-команды;
- использовать process spawning с массивом аргументов;
- генерировать внутренние пути из UUID.

---

## 11.3. SSRF

Если бекенд не принимает прямые файлы, а затем сам скачивает пользовательский URL — это уже совсем другая модель.

Но если вы делаете:

```text
user provides URL -> backend downloads from URL -> stores in S3
```

нужна защита от SSRF:

- allowlist доменов;
- запрет internal IPs;
- запрет metadata endpoints;
- запрет redirects или строгий контроль redirects;
- ограничения timeout и size.

Для вашей описанной модели лучше избегать “скачать из пользовательского URL”.

---

## 12. Приватность и retention

## 12.1. Персональные данные

Фото/видео могут содержать:

- лица сотрудников/клиентов;
- документы;
- геоданные;
- номера;
- корпоративную информацию.

Нужно определить:

1. Какие медиа разрешено загружать.
2. Кто может их видеть.
3. Сколько хранить.
4. Как удалять.
5. Как реагировать на запрос на удаление.
6. Есть ли требование локализации данных.
7. Нужно ли DLP/сканирование.

---

## 12.2. Удаление метаданных

Рекомендуется удалять:

- EXIF;
- XMP;
- GPS;
- устройство;
- автор;
- внутренние метаданные.

Для видео:

```text
-map_metadata -1
```

или эквивалент в вашем пайплайне.

---

## 12.3. Right to delete

Нужен процесс:

```text
User/admin deletes message:
  -> media marked deleted
  -> signed URLs invalidated
  -> final object scheduled for deletion
  -> thumbnails/posters scheduled for deletion
  -> audit log updated
```

Если используется CDN:

- инвалидировать кэш;
- либо использовать короткие TTL;
- либо signed URLs с коротким временем жизни.

## 16. Рекомендуемая схема состояния media object

В базе нужно хранить состояние.

```text

  PENDING_UPLOAD

  DELETED
```

### Важные состояния

Файл есть в staging, но еще не валидирован.


```text

```


```text

```

Объекты удалены.

## 17. Конкретные шаги проверки

Ниже — проверочный план. Все проверки нужно проводить в тестовом окружении/тестовом bucket, чтобы не повредить production.

## 17.1. Тесты валидации

### Тест 1: Подмена MIME

Действие:

```text
Отправить SVG, но заявить Content-Type: image/jpeg
```

Ожидаемо:

```text
Backend отклоняет объект
Или обрабатывает как SVG и отклоняет, если SVG запрещен
```

### Тест 2: Полифайл

Действие:

```text
JPEG + HTML/JS в конце файла
```

Ожидаемо:

```text
Объект отклонен или безопасно перекодирован
HTML/JS не сохраняется
```

### Тест 3: Огромное изображение

Действие:

```text
PNG 100000x100000
```

Ожидаемо:

```text
Backend отклоняет до обработки
Или worker падает по timeout и объект удаляется
```

### Тест 4: GIF bomb

Действие:

```text
GIF с большим числом кадров
```

Ожидаемо:

```text
Отклонен или перекодирован в ограниченное число кадров
```

### Тест 5: SVG со скриптом

Действие:

```text
<svg onload=alert(1)>
```

Ожидаемо:

```text
Отклонен, если SVG запрещен
```

### Тест 6: Видео дольше лимита

Действие:

```text
MP4 длительностью 30 минут
```

Ожидаемо:

```text
Отклонен
```

### Тест 7: Битый MP4

Действие:

```text
Файл с mp4-магическими байтами, но поврежденная структура
```

Ожидаемо:

```text
PROCESS_FAILED
Объекты удалены
Ошибка залогирована
```

### Тест 8: Presigned URL после истечения

Действие:

```text
Получить presigned URL
Подождать expiration
Попытать PUT
```

Ожидаемо:

```text
403
```

### Тест 9: Presigned URL на другой key

Действие:

```text
Взять подписанный URL для key A
Заменить key на key B
```

Ожидаемо:

```text
403
```

### Тест 10: Повторное использование presigned URL

Действие:

```text
Один и тот же presigned URL использовать дважды
```

Ожидаемо:

```text
Backend/поведение S3 не позволяет создать дубль
Или второй объект считается отдельным только если это допустимо
Лучше: backend инвалидирует job после первой загрузки
```

## 18. Рекомендуемая минимальная безопасная конфигурация

Если нужен минимум “чтобы не было очевидно небезопасно”, то:

1. Только аутентифицированные upload.
2. Браузер не имеет S3 keys.
3. Presigned URL:
   - 5–10 минут;
   - только PUT;
   - только конкретный key.
4. Bucket private.
5. Public access denied.
6. Encryption at rest.
7. Allowlist:
   - JPEG/PNG/WebP;
   - MP4/WebM.
8. SVG запрещен.
9. Все файлы перекодируются.
10. Исходный staging‑файл хранится максимум 24 часа.
11. Незавершенные multipart удаляются.
12. Квоты:
    - размер файла;
    - дневной объем;
    - общий объем пользователя;
    - concurrent uploads.
13. Rate limit на API.
14. Worker:
    - timeout;
    - CPU limit;
    - RAM limit.
15. Audit log.
16. Billing alerts.
17. Orphan cleanup.
18. Удаление медиа при удалении сообщений по retention.

## 19. Что нужно уточнить для финального проекта

Чтобы сделать точные лимиты и IAM‑политики, нужно знать:

1. **Публичные или приватные медиа?**
   - Только внутри приложения?
   - Или пользователи могут делиться публичными ссылками?

2. **Ожидаемые размеры:**
   - фото;
   - видео;
   - среднее;
   - максимум.

3. **Количество пользователей:**
   - DAU;
   - peak concurrent users;
   - количество медиа в день.

4. **Тариф Yandex Cloud:**
   - pay-as-you-go?
   - есть ли бюджетный cap;
   - есть ли reserved/savings;
   - какие метрики billing доступны.

5. **Где будет обработка:**
   - на enterprise-серверах;
   - в Yandex Cloud;
   - в контейнерах;
   - в K8s;
   - есть ли cgroup limits.

6. **Какие форматы обязательны:**
   - HEIC?
   - HEVC?
   - GIF?
   - WebM?
   - MP3/AAC?

7. **Нужны ли публичные ссылки:**
   - если да, нужна CDN/signed URL;
   - если нет, можно строго приватный access.

8. **Retention:**
   - сколько храниться медиа;
   - удаляются ли при удалении комментария;
   - есть ли юридические требования.

9. **Compliance:**
   - персональные данные;
   - data residency;
   - требования к шифрованию;
   - аудит.

10. **Существующая инфраструктура:**
    - API gateway;
    - WAF;
    - CDN;
    - message queue;
    - monitoring.

## 20. Краткий практический вывод

Для вашего сценария я бы рекомендовал следующую архитектуру:

```text
1. Браузер делает UX-check.
2. Backend проверяет пользователя и квоты.
3. Backend создает media job.
4. Browser загружает файл:
   - через backend, если трафик умеренный;
   - или через короткий presigned PUT в private staging bucket.
5. Backend проверяет реальный объект в S3.
6. Worker валидирует и перекодирует файл в безопасный формат.
7. Финальный объект сохраняется в private processed bucket/prefix.
8. Staging удаляется.
9. Пользователь получает доступ только через короткий signed GET или через backend.
10. Все объекты, jobs, errors, quota breaches логгируются.
11. Lifecycle удаляет staging, orphan, deleted и expired объекты.
12. Monitoring и budget alerts защищают от “огромного счета”.
```

Главное правило:

> **Никогда не доверяйте браузеру и не храните в S3 недоверенные файлы без строгой квоты, короткого TTL и пост‑проверки.**

Если хотите, следующим шагом я могу подготовить:

1. детальную threat model по STRIDE;
2. конкретную схему API endpoints;
3. таблицу лимитов под ваш ожидаемый трафик;
4. пример IAM/IAM-like политик для Yandex Object Storage;
5. чек‑лист тестов для QA;
6. архитектурную схему с diagram-описанием.
