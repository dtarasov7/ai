# Архитектурная схема с trust boundaries

Ниже — текстовая архитектурная схема. Я явно выделяю **зоны доверия**, **trust boundaries** (границы доверия), **data flows** и **security controls** на каждой границе.

Схема построена на допущениях из предыдущих сообщений. Если ваша инфраструктура отличается (например, нет CDN, нет отдельной очереди, обработка на тех же серверах, что и API) — нужно скорректировать.

---

## 1. Обозначения

```
┌─────────────────────────────────┐
│  [ЗОНА]                         │
│  УРОВЕНЬ ДО ВЕРИЯ:              │
│    U = Untrusted (недоверено)   │
│    S = Semi-trusted (подоверено)│
│    T = Trusted (доверено)       │
│    E = External (внешний)       │
│                                 │
│  ┌───┐ ┌───┐                    │
│  │A  │ │B  │  компоненты        │
│  └───┘ └───┘                    │
│                                 │
│  ──►  data flow                 │
│  ══►  trust boundary crossing   │
│  ┄┄►  optional / conditional    │
└─────────────────────────────────┘
```

## 3. Trust boundaries — детализация

### TB-1: Network Boundary (внешний мир → Edge)

| Параметр | Описание |
|---|---|
| **Что пересекает** | HTTP(S) трафик из интернета |
| **Уровень доверия "до"** | U (Untrusted) |
| **Уровень доверия "после"** | S (Semi-trusted) |
| **Угрозы** | DDoS, MITM, scanning, malicious payloads, TLS stripping |
| **Контроли** | TLS 1.2+, HSTS, WAF rules, rate limit (global), DDoS L3/L4, connection limits, request size limits |
| **Что НЕ доверяем** | IP, User-Agent, Content-Type, Origin, body content, headers |
| **Что доверяем (partial)** | Только после WAF+rate limit+TLS: что запрос пришёл с внешнего мира |

---

### TB-2: Application Boundary (Edge → Backend API)

| Параметр | Описание |
|---|---|
| **Что пересекает** | Authenticated API requests |
| **Уровень доверия "до"** | S (Semi-trusted) |
| **Уровень доверия "после"** | T (Trusted) |
| **Угрозы** | Spoofing (forged tokens), IDOR, injection, unauthorized access, quota bypass |
| **Контроли** | AuthN (JWT validation), AuthZ (RBAC), input validation, quota check, S3 key generation server-side, presigned URL scope |
| **Ключевое правило** | **Никогда не доверять user-controlled данные как доверенные.** `user_id` — только из токена. `file_type` — только из magic bytes. `file_size` — только из HeadObject. |
| **Что генерирует backend** | S3 key (UUID), presigned URL, job ID, idempotency record |

---

### TB-3: Processing Boundary (API/Queue → Workers)

| Параметр | Описание |
|---|---|
| **Что пересекает** | Media processing jobs |
| **Уровень доверия "до"** | T (Trusted) |
| **Уровень доверия "после"** | T (Trusted), но с повышенным риском (untrusted content) |
| **Угрозы** | Command injection, decoder exploits, resource exhaustion, output size bomb |
| **Контроли** | Worker получает только `job_id` + `s3_key`. Никаких user-controlled параметров. Fixed transcode profiles. CPU/RAM/time limits. No shell. Container isolation. |
| **Ключевое правило** | **Worker не принимает ни одного параметра от пользователя.** Все параметры обработки — из фиксированного профиля в коде. |

---

### TB-4: Storage Boundary (Workers/API → S3)

| Параметр | Описание |
|---|---|
| **Что пересекает** | Сетевые запросы к Yandex Object Storage |
| **Уровень доверия "до"** | T (Trusted) |
| **Уровень доверия "после"** | E (External trusted service) |
| **Угрозы** | Credential leakage, bucket policy misconfiguration, cross-tenant access, lifecycle failure |
| **Контроли** | Private bucket, least privilege IAM, prefix-scoped access, encryption at rest, lifecycle rules, no versioning (default) |
| **Ключевое правило** | **S3 — не бизнес-логика.** S3 хранит байты. Все решения (кто видит, когда удалить, какой статус) — в backend + DB. |

---

### TB-5: Browser ↔ S3 (Presigned URL path) — КРИТИЧЕСКАЯ ГРАНИЦА

| Параметр | Описание |
|---|---|
| **Что пересекает** | Прямой PUT/GET от браузера в S3 через presigned URL |
| **Уровень доверия "до"** | U (Untrusted) — браузер |
| **Уровень доверия "после"** | E (External) — S3 |
| **Угрозы** | URL reuse, key manipulation, method escalation, size bypass, List attempt |
| **Контроли** | |
| | • TTL: **3–15 минут** (не более 30 мин) |
| | • Scope: **один key, один HTTP метод** |
| | • One-time: после первого успешного PUT job → `UPLOADED`, URL невалиден |
| | • No List, no Delete, no Get (для PUT URL) |
| | • Key генерируется backend: `media/staging/{user_id}/{uuid4}` |
| | • Post-upload: backend делает HeadObject, проверяет размер и magic bytes |
| | • Если размер > limit → DeleteObject + job FAILED |
| **Ключевое правило** | **Presigned URL — не доверие. Это временный, узкий, одноразовый туннель.** |

## 4. Data flows

### 4.1. Upload flow (загрузка медиа)

```
Browser (U)
  │
  │ 1. POST /media/uploads/request
  │    { originalName, declaredType, declaredSize, idempotencyKey }
  ▼
API Gateway (S)
  │
  │ 2. AuthN + AuthZ + RateLimit + QuotaPreCheck
  ▼
Backend API (T)
  │
  │ 3. Создаёт job в DB: status=PENDING_UPLOAD
  │    Генерирует s3_key = "media/staging/{user_id}/{uuid4}"
  │
  │ 4. Генерирует presigned PUT URL (TTL=10min, method=PUT, key=s3_key)
  │
  ├──► DB: INSERT media_object (PENDING_UPLOAD, s3_key, declared_size, ...)
  │
  └──► Returns to Browser: { job_id, presigned_url, expires_at }

Browser (U)
  │
  │ 5. PUT <file> → presigned_url   [TB-5: Browser ↔ S3]
  ▼
Yandex S3 (E)
  │
  │ 6. Объект создан: media/staging/{user_id}/{uuid4}
  │
  │ (Browser может также отправить POST /media/uploads/{id}/complete)
  │
  ▼
Backend API (T)
  │
  │ 7. HeadObject(s3_key) → actual_size, content_type
  │ 8. Magic bytes check
  │ 9. Size check: actual_size <= limit?
  │ 10. Update DB: status=UPLOADED
  │
  ├──► DB: UPDATE media_object (UPLOADED, actual_size, actual_type)
  │
  └──► Queue: ENQUEUE processing_job { job_id, s3_key, profile }

Worker (T, isolated)
  │
  │ 11. GetObject(s3_key) → download to /tmp/jobs/{uuid}/input
  │ 12. Validate: ffprobe / identify (dimensions, duration, codec)
  │ 13. Transcode: FFmpeg fixed profile (H.264/AAC or WebP/JPEG)
  │ 14. Check output size
  │ 15. PutObject("media/final/{user_id}/{uuid4}")
  │ 16. PutObject("media/thumbs/{user_id}/{uuid4}")
  │ 17. Update DB: status=READY, final_size, final_sha256
  │
  ├──► S3: final/ + thumbs/ objects created
  ├──► DB: UPDATE media_object (READY, final_key, thumb_key)
  │
  │ 18. Cleanup: DeleteObject("media/staging/{user_id}/{uuid4}")
  │     (или cleanup service делает это по TTL)
  ▼
DONE: media готов к просмотру
```

### 4.2. Read flow (просмотр медиа)

```
Browser (U)
  │
  │ 1. GET /media/{id}/url
  │    (with valid session token)
  ▼
API Gateway (S)
  │
  │ 2. AuthN + AuthZ (user owns this media?)
  ▼
Backend API (T)
  │
  │ 3. Check DB: media.status == READY?
  │ 4. Check DB: media.user_id == token.user_id?
  │    (or: message is public and user has view permission)
  │ 5. Generate signed GET URL (TTL=60–300 sec, key=final_key)
  │
  └──► Returns to Browser: { signed_url, expires_at }

Browser (U)
  │
  │ 6. GET signed_url   [or CDN if used]
  ▼
Yandex S3 (E) / CDN (S)
  │
  │ 7. Returns object bytes
  ▼
Browser renders <img> or <video>
```

### 4.3. Delete flow (удаление медиа)

```
Browser (U)
  │
  │ 1. DELETE /messages/{id}  (or /media/{id})
  ▼
API Gateway (S)
  │
  │ 2. AuthN + AuthZ (user owns this?)
  ▼
Backend API (T)
  │
  │ 3. UPDATE media_object SET status=SOFT_DELETED, delete_after=now+retention
  │ 4. Invalidate any cached signed URLs
  │
  ├──► DB: media → SOFT_DELETED
  │
  └──► Queue: ENQUEUE cleanup_job { media_id, delete_after }

Cleanup Service (T) [scheduled / event-driven]
  │
  │ 5. When now >= delete_after:
  │    DELETE S3: media/final/{user_id}/{uuid4}
  │    DELETE S3: media/thumbs/{user_id}/{uuid4}
  │    UPDATE DB: media → DELETED
  │    Log: AUDIT_DELETE
  │
  ▼
DONE: media физически удалён
```

## 5. Service accounts и права доступа

| Service Account | Get | Put | Delete | List | Head | Multipart | Notes |
|---|---|---|---|---|---|---|---|
| **API Service Account** | staging/ | staging/ (optional) | ✗ | ✗ | ✓ staging/ | Create (optional) | Только для валидации post-upload |
| **Worker Service Account** | staging/ | final/, thumbs/ | ✗ | ✗ | ✗ | ✗ | Только read staging, write final |
| **Cleanup Service Account** | staging/, final/, thumbs/ | ✗ | staging/, final/, thumbs/ | ✗ | ✓ | Abort | Только удаление по TTL/retention |
| **Admin Service Account** | All | ✗ | All | ✓ (rate-limited) | ✓ | Abort | Только через admin plane + MFA |
| **Browser (presigned)** | — (PUT only) | staging/ (1 key) | ✗ | ✗ | ✗ | — | Только один key, один PUT |
| **Browser (presigned GET)** | final/, thumbs/ (1 key) | ✗ | ✗ | ✗ | ✗ | — | Только один key, TTL 60–300s |

**Принцип:** каждый service account имеет **минимально необходимые** права. API не может удалять. Worker не может листать. Browser не может удалять/листать.

## 8. Упрощённый вариант (если инфраструктура небольшая)

Если у вас **нет** отдельного K8s, очереди и выделенных worker-VM, минимальная безопасная схема:

```
Browser (U)
  │
  │ HTTPS
  ▼
API Gateway / WAF (S)
  │
  ▼
Backend API (T)
  │  • Accepts upload via HTTP (multipart/form-data)
  │  • Validates (size, type, magic bytes)
  │  • Stores to /tmp/{uuid}/input
  │  • Spawns transcode (FFmpeg) with limits:
  │     timeout, CPU, RAM (cgroup/ulimit)
  │  • Uploads final to S3
  │  • Deletes /tmp/{uuid}/
  │
  ├──► DB (T)
  │
  └──► S3 (E)
       • staging/ (optional, if using presigned)
       • final/
       • thumbs/

Monitoring:
  • Backend metrics (upload count, size, errors)
  • S3 metrics (storage, requests, egress)
  • Budget alerts
```

**Компромиссы упрощённого варианта:**
- Транскод на тех же серверах, что и API → риск resource exhaustion.
  **Митигация:** выделенный процесс с cgroup limits, очередь на уровне приложения.
- Нет отдельного cleanup service → lifecycle rules в S3 критически важны.
- Нет network segmentation → security groups + firewall rules обязательны.
