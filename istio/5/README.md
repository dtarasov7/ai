# 5. Наблюдаемость сервисов (сбор логов, трейсов, метрик)

[Практический разбор: что даёт Istio и что остаётся в сервисе](АНАЛИЗ.md).

**Можно:** Частично. **Рекомендация:** Стоит как дополнение.

## Что означает правый столбец

На скриншоте: `istiod, istio-proxy, istio kiali, prometheus&graphana, jaeger`.

Envoy генерирует сетевые метрики, access log и spans; Prometheus, хранилище логов и tracing backend принимают и хранят их. Kiali/Grafana визуализируют данные. istiod управляет настройками, но не является хранилищем телеметрии.

## Плюсы, минусы и границы ответственности

Плюс: унифицированные latency, ошибки, объём трафика. Минус: стоимость хранения, cardinality, sampling и возможные персональные данные в журналах.

Бизнес-метрики и внутренние ошибки нужны из приложения. Для связного distributed trace приложение обязано переносить trace context между входящими и исходящими вызовами. Наличие Jaeger/Kiali и приём данных нельзя считать включёнными по умолчанию.

Источник: [документация механизма](https://istio.io/latest/docs/tasks/observability/distributed-tracing/overview/).
Версию/редакцию Deckhouse и условия стенда проверяют по [общему README](../README.md).

## Испытание и критерий

Создаём HTTP-нагрузку и Telemetry с accessLogging provider envoy. Проверяем счётчик istio_requests_total и маркер запроса в журнале proxy. Затем отдельно проверяют сбор в Prometheus/лог-хранилище и связный trace в backend; автоматическая часть возвращает 2, обозначая неполную приёмку.

`01-prepare.sh` создаёт изолированные тестовые ресурсы; `02-check.sh` проверяет
заявленный сценарий; `03-cleanup.sh` удаляет namespace `pmi-istio-5` после проверки
метки владельца. Все три файла запускаются независимо через Bash, из любого каталога.
Порядок: prepare → check → сохранение результатов → cleanup. После неудачи сначала
сохраните диагностику, затем выполните cleanup. См. общие предпосылки и коды выхода.

```bash
bash 01-prepare.sh
bash 02-check.sh
bash 03-cleanup.sh
```

Для протокола сохраните версию DKP/Istio, kube-context, образы с digest, вывод команд,
HTTP-результаты и `kubectl -n pmi-istio-5 get pods,svc -o wide`.
Сценарий создан для испытания; фактическое прохождение на Deckhouse пока не подтверждено.

## Завершение приёмки наблюдаемости (после кода 2)

1. В Prometheus запросить `sum(istio_requests_total{destination_service_namespace="pmi-istio-5",reporter="destination"})`.
   Дождаться минимум двух scrape-интервалов и повторить нагрузку; значение должно расти.
   Источник: [сбор метрик](https://istio.io/latest/docs/tasks/observability/metrics/querying-metrics/).
2. В центральном лог-хранилище найти `/pmi-evidence-5` с namespace и Pod этого опыта.
   `kubectl logs` не подтверждает наличие доставки/retention в хранилище.
   Источник: [access logs](https://istio.io/latest/docs/tasks/observability/logs/access-log/).
3. Для трассировки заранее подключить поддерживаемый backend через настройки модуля
   Deckhouse и выбрать sampling для стенда. Штатный тестовый HTTP-сервер не делает
   вложенных вызовов: для проверки связности нужен реальный сервис A → B, переносящий
   `traceparent`/`tracestate` либо заголовки выбранного формата. Отправить запрос с
   известным trace-id, найти один trace со spans обоих сервисов. Отдельные spans
   или наличие Jaeger без запроса не являются прохождением этого шага.
4. Зафиксировать запросы, временное окно, скриншоты/экспорт данных и trace-id в протоколе.
   Только после этого поставить общий результат «пройдено». При отсутствии backend
   или сквозного сценария отметить «не проверено», а не «работает».

Скрипты не меняют глобальные настройки tracing, scraping и логирования. Встроенный
provider `envoy` должен быть доступен; если он переопределён, нужно адаптировать
Telemetry под фактический provider. [Telemetry API](https://istio.io/latest/docs/reference/config/telemetry/).
