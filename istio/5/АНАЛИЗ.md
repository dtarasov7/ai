# 5. Что даёт Istio для наблюдаемости сервисов

**Istio даёт единый способ видеть, как сервисы вызывают друг друга: кто кого вызывает,
сколько запросов проходит, сколько из них заканчивается ошибкой и сколько времени
занимают ответы.** Базовые измерения выполняет прокси рядом с приложением —
разработчику не нужно отдельно реализовывать их в каждом сервисе.

В нашем sidecar-режиме вызов выглядит так:

```text
Сервис «Заказы» → Envoy → Envoy → Сервис «Оплата»
```

Оба Envoy видят проходящий через них трафик и могут формировать телеметрию.
Для HTTP-показателей прокси должен распознавать HTTP; при непрозрачном для него TLS
возможности ограничены показателями соединений.

**1. Метрики: общая картина взаимодействий**

Например, можно получить такую картину — цифры условные:

| Что измеряем | Пример результата |
|---|---|
| Частота вызовов «Заказы → Оплата» | 100 запросов в секунду |
| Доля HTTP-ошибок | 8% ответов — 503 |
| Время ответа | 95% запросов завершаются быстрее 700 мс |
| Различия между версиями | У «Оплата v2» ошибок больше, чем у v1 |

Это позволяет заметить ухудшение после выкладки, найти проблемную зависимость
и настроить оповещения. Язык приложения значения не имеет: Java, Python и Go
получают общие сетевые показатели. Prometheus собирает эти метрики, Grafana
отображает их. [Стандартные метрики Istio](https://istio.io/latest/docs/reference/config/metrics/).

**2. Access logs: сведения об отдельном обращении**

При включённом журналировании Envoy может записывать метод, путь, HTTP-код,
длительность, выбранный backend и диагностические признаки отказа.

Например:

> Сервис «Заказы» обратился к `/pay`, запрос занял 5 секунд и завершился ошибкой
> соединения с backend.

Это полезно даже тогда, когда запрос не дошёл до приложения и в его собственном
журнале ничего нет. Но запись вида «не удалось списать деньги: недостаточно средств»
должен формировать код, понимающий бизнес-операцию.
[Access logs Envoy](https://istio.io/latest/docs/tasks/observability/logs/access-log/).

**3. Трейсы: путь одного запроса через несколько сервисов**

Для цепочки:

```text
Входящий запрос → Заказы → Оплата → Уведомления
```

трассировка помогает увидеть отдельные сетевые вызовы и их длительность.
Например, понять, на каком обращении возникла большая задержка.

Здесь есть существенное условие: **приложение должно передавать контекст трассировки
из входящего запроса в вызванные им исходящие запросы**. Без этого Envoy создаст
отдельные фрагменты, которые не получится надёжно связать в одну цепочку.
Внутренние операции — SQL-запрос, обработку файла, расчёт — также нужно
инструментировать отдельно.
[Условия распределённой трассировки](https://istio.io/latest/docs/tasks/observability/distributed-tracing/overview/).

Поэтому архитектурное обещание пятого пункта я бы сформулировал так:

> **Вынести на платформу стандартную наблюдаемость межсервисных вызовов.
> В приложениях оставить бизнес-метрики, содержательные журналы, внутреннюю
> диагностику и передачу контекста трассировки.**

Istio создаёт данные; хранение, поиск, графики и оповещения обеспечивают
подключённые системы наблюдаемости. Само включение Istio ещё не означает,
что весь этот путь настроен.

**Что доказывает текущий тест**

Наш текущий **тест № 5 проверяет только начало этого пути**: Envoy зарегистрировал
запросы в метриках и access log. Доставку в хранилища и связность трассировки
он автоматически не доказывает. Код выхода 2 означает необходимость закончить
ручную приёмку по [README пункта](README.md).

Для маленького стенда это позволяет сначала показать сам источник данных,
а затем отдельно подключать потребителей, контролируя расход памяти.
