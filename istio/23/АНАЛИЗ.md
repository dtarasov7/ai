# 23. Timeout: что увидит вызывающий сервис

Istio ограничивает время ожидания ответа зависимости на уровне proxy. Если
«Заказы» вызывает медленную «Оплату», правило не даёт этому конкретному HTTP-вызову
бесконечно занимать ресурсы на сетевом пути. Оно не определяет само, что делать
с заказом после ошибки, и не гарантирует остановку оплаты.

Наш пример: backend ждёт три секунды **до отправки заголовков**, route timeout
равен одной секунде, retries отключены, timeout HTTP-библиотеки клиента — десять
секунд. Первым срабатывает proxy. В этом HTTP/1.1-сценарии клиент получает HTTP 504.
Python urllib представляет такой ответ исключением HTTPError, из которого доступны
код, заголовки и тело. Другая библиотека может вернуть обычный объект ответа.

| Ситуация | Что видит вызывающий код |
|---|---|
| Proxy завершил ожидание до начала ответа backend | Обычно HTTP 504 в нашем сценарии |
| Timeout клиентской библиотеки короче, например 0,2 с | Исключение timeout без гарантированного HTTP-кода |
| Backend успел ответить при route timeout 6 с | Нормальный HTTP 200 |
| Ответ уже начат, затем поток прерван | Возможен обрыв/неполный ответ вместо нового 504 |
| gRPC или streaming | Отдельная проверка статусов и поведения конкретного SDK |

Не следует писать бизнес-логику по строке тела `upstream request timeout`:
текст и заголовки могут меняться при настройке локальных ответов, gateway и версии.
Скрипт печатает полученное тело для диагностики, но проверяет HTTP-код и время.
И сам 504 не сообщает, завершилась ли операция в БД. Похожие коды могут быть
сгенерированы другим посредником; для расследования полезны access logs и request id.

В нашем сервере отдельно считаются начало и завершение обработки. После получения
504 тест продолжает опрашивать счётчик и видит, что сервер завершил работу.
Это показывает ключевое ограничение: разрыв ожидания/соединения не равен откату
транзакции или отмене прикладного потока. Для оплаты нужны ключ идемпотентности,
запрос состояния и согласованный механизм отмены.

Route timeout — бюджет конкретного маршрута, включая разрешённые повторы.
Это не универсальный дедлайн всей цепочки A → B → C и не TCP connect timeout.
Для обычного Envoy route таймер привязан к завершению получения downstream-запроса;
долгую загрузку тела и streaming нельзя оценивать по нашему короткому GET.
Приложению всё равно нужны свои дедлайны для БД, очереди и внешних SDK, а также
обработка ситуации, когда клиент уже не ждёт результат.

Плюс — централизованный ограничитель ожидания. Минусы — опасность слишком короткого
порога, скрытая продолжающаяся работа и разные уровни таймаутов. **Стоит как
дополнительный сетевой предел**, выбираемый по SLO и измерениям задержек. Тест
проверяет 504, продолжение работы backend, успех с длинным бюджетом и отдельный
локальный timeout клиента. Это не нагрузочное измерение; перегруженный стенд
может нарушить временные допуски, что требует диагностики, а не ослабления критериев.
