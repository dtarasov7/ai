# Istio в Deckhouse: возможности и испытания

Комплект охватывает 23 возможности Istio и отделён от прежних
испытаний Deckhouse в корне проекта. «Можно» означает техническую применимость
в указанной границе; «стоит» — архитектурную рекомендацию, а не результат испытания.
Разбор подготовлен 28.10.2026. Скрипты рассчитаны на **sidecar mode**, не ambient.

В каждом каталоге 1–23 есть `АНАЛИЗ.md` с понятным объяснением пользы Istio,
прикладным примером, границами переноса из сервисного кода и связью с текущим тестом.
Прямые ссылки собраны в последнем столбце [сводной таблицы](ТАБЛИЦА.md).
В [пункте 5](5/АНАЛИЗ.md) сохранён разбор наблюдаемости из обсуждения.

Разборы объясняют sidecar-механизмы и не являются протоколами пройденных испытаний.
Примеры с названиями бизнес-сервисов и числами иллюстративны. Источники Istio/Kiali
могут описывать более новые релизы: наличие конкретных полей и интеграций сверяйте
с версиями стенда и редакцией Deckhouse. Оценки «стоит» — архитектурное суждение
в описанных условиях; они не обещают полного удаления соответствующей логики
из приложения.

В описаниях различаются исполняемые компоненты (Envoy, istiod), API-ресурсы
(VirtualService), функции (traffic splitting) и отдельные продукты (Dex, Jaeger).
Их упоминание не гарантирует наличие в конкретной поставке.
Реестр внешних сервисов — ServiceEntry, хранилище mesh CRD —
Kubernetes API/etcd, обычный DNS — CoreDNS, health checks приложения — kubelet probes.
Pilot входит в istiod. Subsets задаёт DestinationRule. Авторизация HTTP сервиса
и Kubernetes RBAC решают разные задачи. Обоснование и источники — в каждом пункте.

Полностью убрать эти вопросы из сервисов нельзя: остаются бизнес-авторизация,
контекст трассировки, readiness, совместимость версий/БД, дедлайны,
идемпотентность, обработка отказов и управление состоянием сессии.

## Лаборатория без Deckhouse

При ограничении 10 ГБ RAM используйте [инструкцию K3s + Istio на РЕД ОС 8](K3S-ISTIO-REDOS8.md).
Она описывает установку на одной ВМ с 8 ГБ RAM и отдельную проверку mesh/gateway.
В каждом каталоге 1–23 есть `01-prepare-k3s.sh`: копия подготовки с проверками
istiod, injection webhook и CRD вместо Module. Запускайте её вместо `01-prepare.sh`,
затем обычные `02-check.sh` и `03-cleanup.sh`. Namespace один и тот же для обоих
вариантов: запускайте только один вариант подготовки за прогон.
Для пункта 12 подготовлены также `02-check-k3s.sh` и `03-cleanup-k3s.sh`:
используйте все три K3s-скрипта и `LAB_IP` для NodePort 30080
(см. [пункт 12](12/README.md#вариант-k3s)). Для полной приёмки 5/19 нужны
компоненты наблюдаемости. Подробности — в инструкции.

## Запуск и ограничения стенда

Ранее в проекте указан CSE 1.73.4, но это не подтверждает версию установленного
Istio и доступность функций. Актуальная документация Deckhouse перечисляет
ограничения редакций; federation/multicluster нельзя автоматически считать
доступными в CSE. Скрипты не включают и не обновляют модули.
Сверьте поставку и [настройки модуля](https://deckhouse.io/modules/istio/configuration.html).

Нужны Bash, kubectl, административный доступ к испытательному кластеру;
для пункта 4 также Python 3.8 (команда `python`) и OpenSSL на рабочей машине, для 12 — curl.
В каждом опыте создаётся отдельный namespace `pmi-istio-N`. Prepare использует
create: существующий namespace не присваивается. Cleanup проверяет метку владельца
и удаляет namespace целиком. Не размещайте там чужие ресурсы; один пункт нельзя
запускать параллельно дважды. Check может менять только ресурсы своего опыта.

По умолчанию образ — `python:3.12-alpine`; для закрытого стенда задайте
`export TEST_IMAGE=registry.example/your-python-image:tag`.
Во всех сценариях вызывается **`python`**, включая команды запуска контейнеров;
наличие `python3` не требуется. Код рассчитан на **Python 3.8** и стандартную библиотеку.
Пример образа по умолчанию содержит более новую версию Python; ваш образ с Python 3.8
подставляйте через `TEST_IMAGE`. Для пункта 4 бинарник `python` версии 3.8 нужен также
на рабочей машине рядом с OpenSSL и kubectl. Для локальных регрессионных проверок
в каталоге `tests` дополнительно нужен PyYAML; на контейнерах испытаний он не нужен.
Не задавайте `PYTHONOPTIMIZE` и не запускайте Python с `-O`: проверки используют assert.
Образ должен быть доступен всем узлам; для приёмки закрепите его digest.
Сценарии используют HTTP/1.1, порт 8080 и домен Kubernetes `cluster.local`.
При ином cluster domain адаптируйте FQDN и trust domain (`TRUST_DOMAIN`, пункт 3/11).
Namespace получает `istio-injection=enabled`; при нескольких ревизиях задайте
`export ISTIO_REV=<метка-ревизии-Deckhouse>`. На Pod явно включена injection;
клиент plaintext и модель внешнего сервиса явно исключены.
[Правила injection и ограничения EnvoyFilter](https://deckhouse.io/modules/istio/).

Prepare проверяет Ready модуля, доступность используемых версий CRD через
`kubectl explain`, ждёт Ready всех Pod и проверяет наличие работающего istio-proxy.
Используются API networking/security v1beta1 и telemetry v1alpha1: это осознанный
выбор совместимого API; если версия не served, prepare остановится, обновлять
кластер автоматически нельзя. Поля дополнительно валидирует API при create/apply.
Глобальные DENY/Telemetry/Sidecar, admission policies, quotas и запреты registry
могут повлиять на результат: их нужно зафиксировать в протоколе.
Ресурсы VirtualService/DestinationRule/ServiceEntry имеют `exportTo: ["."]`;
в пункте 12 маршрут и subsets дополнительно видимы gateway в `d8-ingress-istio`.

Из каталога выбранного пункта:

```bash
kubectl config current-context
bash 01-prepare.sh
bash 02-check.sh
# Сохранить stdout/stderr, ресурсы и доказательства до очистки.
bash 03-cleanup.sh
```

Пункт 12 дополнительно требует `GATEWAY_CLASS` и `GATEWAY_URL` (описаны в его README).
Проверки ждут распространения правил до 30 секунд и затем выполняют серию запросов.
Код 0 — успешна только заявленная автоматическая часть; код 1 — ошибка;
пункты 5/19 возвращают 2 после автоматической части: нужно закончить ручную приёмку.
Повторный полный прогон — после cleanup. После сбоя prepare/check cleanup запускают
отдельно; namespace сохраняется для диагностики.

Испытания не являются нагрузочным benchmark или доказательством отказоустойчивости.
В этой среде доступ к Kubernetes API отсутствует; результаты статической проверки
приведены в [ПРОВЕРКА.md](ПРОВЕРКА.md). Успешный runtime не заявляется.

Сводная оценка каждого пункта: [ТАБЛИЦА.md](ТАБЛИЦА.md).

| Пункт | Испытание | Дополнительные условия |
|---|---|---|
| [20. ВМ](20/README.md) | mTLS к настоящей ВМ, отказ с чужим SAN, восстановление | Отдельная ВМ с предварительно подключённым агентом; VM_IP и VM_IDENTITY; локальный python |

| [22. Retries](22/README.md) | Успешный повтор, исчерпание, 400 без повторов, POST | Счётчик реальных обращений в backend |

Для 20–23 также есть Deckhouse и K3s prepare, общий check и cleanup.
Пункт 20 не устанавливает VM runtime и не меняет глобальный gateway: порядок
подключения агента и ограничения поддержки описаны отдельно в его README.
В 21–23 один backend, в 20 backend расположен вне Kubernetes. Новые сценарии
используют Python 3.8, подробные русские комментарии и отдельные namespace.
