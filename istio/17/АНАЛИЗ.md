# 17. Что даёт Istio для sticky sessions

**Istio может помогать направлять обращения с одним ключом на одну и ту же реплику.**
Это полезно для локальности кеша или поддержки приложения с состоянием в памяти.
Но такая привязка не обеспечивает сохранность самого состояния.

Допустим, у «Корзины» две реплики, а запрос несёт ключ сессии:

```text
Ключ user-123 → consistent hash в Envoy → обычно Pod 1
Ключ user-456 → consistent hash в Envoy → обычно Pod 2
```

При стабильном наборе endpoints один и тот же ключ позволяет воспроизводимо
выбирать backend. В используемом подходе это DestinationRule с consistentHash;
ключом могут служить заголовок, cookie или IP.
[Настройки consistent hash](https://istio.io/latest/docs/reference/config/networking/destination-rule/).

**Чем это отличается от A/B**

В A/B признак выбирает группу/версию: например, v2 вместо v1. Sticky sessions
выбирают конкретный endpoint из доступного набора. Это разные решения, и их
совместное применение нужно проектировать, а не ожидать автоматически.

| Ситуация | Что даёт привязка |
|---|---|
| Набор реплик не меняется | Один ключ обычно попадает в одну реплику |
| Удалилась реплика | Некоторые ключи получат другой backend |
| Добавлены реплики | Часть ключей перераспределится |
| Состояние было только в памяти умершего Pod | Оно не восстановится от того же ключа |

Например, после гибели Pod 1 запрос `user-123` может прийти в Pod 2.
Если корзина хранилась только в памяти Pod 1, proxy не сможет её восстановить:
он не копирует содержимое процесса приложения.

**Какая работа уходит из кода**

Можно перенести сетевую привязку и не реализовывать одинаковую логику выбора
реплики во всех клиентах. Само создание ключа, его корректная передача, срок жизни
сессии и хранение пользовательских данных остаются в приложении/системе сессий.

Если состояние должно переживать перезапуск и масштабирование, его нужно хранить
соответствующим образом, например во внешнем по отношению к Pod хранилище.
Это архитектурная рекомендация; один только mesh задачу долговечности не решает.

**Цена и условия**

Слишком активный пользователь способен перегрузить одну реплику. Привязка по IP
за NAT может объединить много пользователей под одним ключом. Разные proxy
с разным представлением endpoints также не обязаны выбрать один backend.
Поэтому в документации такая привязка называется мягкой.

Моя оценка: использовать её стоит под измеримую пользу для кеша или совместимости
legacy-приложения. Закладывать в ней гарантию непрерывности пользовательской
сессии опасно: отказоустойчивость состояния нужна отдельно.
