# 17. Sticky sessions

[Практический разбор: что даёт Istio и что остаётся в сервисе](АНАЛИЗ.md).

**Можно:** Да, мягкая привязка. **Рекомендация:** Условно; предпочесть внешнее хранение сессий.

## Как реализуется возможность

DestinationRule.loadBalancer.consistentHash распределяет запросы по заголовку/cookie/IP; один ключ обычно попадает в один endpoint при стабильном наборе реплик. Это отличается от выбора subset по группе.

## Плюсы, минусы и границы ответственности

Плюс: локальность кеша и уменьшение необходимости менять legacy-клиент. Минус: перекос нагрузки и перераспределение ключей при масштабировании/сбое.

Не гарантирует сохранность in-memory сессии и абсолютную привязку между разными proxy с разным набором endpoints. Source IP за NAT объединяет пользователей. Stateful session feature/EnvoyFilter отдельно не применяется.

Источник: [документация механизма](https://istio.io/latest/docs/reference/config/networking/destination-rule/).
Версию/редакцию Deckhouse и условия стенда проверяют по [общему README](../README.md).

## Испытание и критерий

20 независимых запросов с одним x-session-key возвращают один Pod; 100 различных ключей попадают на оба Pod. Отказ/масштабирование и сохранность сессии этим не доказываются.

`01-prepare.sh` создаёт изолированные тестовые ресурсы; `02-check.sh` проверяет
заявленный сценарий; `03-cleanup.sh` удаляет namespace `pmi-istio-17` после проверки
метки владельца. Все три файла запускаются независимо через Bash, из любого каталога.
Порядок: prepare → check → сохранение результатов → cleanup. После неудачи сначала
сохраните диагностику, затем выполните cleanup. См. общие предпосылки и коды выхода.

```bash
bash 01-prepare.sh
bash 02-check.sh
bash 03-cleanup.sh
```

Для протокола сохраните версию DKP/Istio, kube-context, образы с digest, вывод команд,
HTTP-результаты и `kubectl -n pmi-istio-17 get pods,svc -o wide`.
Сценарий создан для испытания; фактическое прохождение на Deckhouse пока не подтверждено.
