# 13. Что даёт Istio для внешних сервисов и исходящего трафика

**Istio позволяет описать внешнюю зависимость как известный mesh сервис и
применять к обращениям общие сетевые настройки.** Реестр этой зависимости задаёт
ServiceEntry; egress gateway решает задачу организации общего выхода.

Предположим, «Оплата» обращается к банковскому API:

```text
Без отдельной точки выхода:
«Оплата» → sidecar → банковский API

С общей точкой выхода:
«Оплата» → sidecar → egress gateway → банковский API
```

В первом случае запись ServiceEntry уже может быть полезна. Во втором появляются
централизованный маршрут выхода и место применения соответствующих настроек.
Сам gateway не является каталогом внешних API.
[Управление внешними сервисами](https://istio.io/latest/docs/tasks/traffic-management/egress/egress-control/).

**Практическая польза**

Команда может явно перечислить сетевые зависимости, организовать наблюдаемость
вызовов, согласовать разрешённые направления и вынести часть TLS-настроек на
proxy. Например, одинаковый порядок соединения с партнёром не придётся
поддерживать отдельными реализациями во всех клиентах.

Однако API банка, URL его бизнес-операции, формат подписи платежа и реквизиты
не становятся известны Istio автоматически. Их задаёт интеграционный код.

| Что относится к сети | Что относится к интеграции приложения |
|---|---|
| Адреса, порты, протокол | Содержание платёжного запроса |
| Путь через egress gateway | Идемпотентный идентификатор платежа |
| Сетевые TLS-настройки при выбранной схеме | Проверка бизнес-ответа банка |
| Сетевые метрики вызова | Учёт результата операции у себя |

TLS origination может перенести установление TLS от приложения к proxy,
но это отдельная архитектурная схема. Если приложение само устанавливает сквозной
HTTPS, Envoy не получает произвольный доступ к зашифрованным HTTP-заголовкам.

**Почему REGISTRY_ONLY недостаточно для запрета выхода**

Этот режим заставляет proxy отклонять неизвестные направления и помогает
обнаруживать забытые ServiceEntry. Он не предотвращает обход proxy.
Для обязательного выхода только через gateway требуются CNI/сетевые ограничения
и защита прав изменения Pod/политик. Нельзя выдавать переключение этого режима
за полноценный firewall.

Моя оценка: реестр полезен для управляемых внешних зависимостей. Egress gateway
стоит добавлять под задачу общего выхода; он требует мощности, доступности
и сопровождения, даже если сами внешние API работают исправно.
