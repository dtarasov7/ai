# 1. Маршрутизация трафика ППО внутри (east-west) и вне кластера

[Практический разбор: что даёт Istio и что остаётся в сервисе](АНАЛИЗ.md).

**Можно:** Да. **Рекомендация:** Стоит.

## Что означает правый столбец

На скриншоте: `istio-proxy (Envoy proxy: sidecar и Istio gateway)`.

Envoy выполняет маршрутизацию; istiod передаёт ему конфигурацию. VirtualService задаёт HTTP-маршруты, DestinationRule — версии и свойства upstream. Вход и выход оформляют отдельными gateway и ServiceEntry.

## Плюсы, минусы и границы ответственности

Плюс: единые правила без собственного балансировщика в каждом сервисе. Минус: дополнительный сетевой переход, расход CPU/RAM и зависимость от согласованности конфигурации.

L7-правила требуют видимого HTTP/gRPC: за сквозным TLS доступны в основном SNI и TCP. UDP и произвольная бизнес-маршрутизация сюда не относятся. Идемпотентность, дедлайны и обработка ошибки остаются в приложении.

Источник: [документация механизма](https://istio.io/latest/docs/concepts/traffic-management/).
Версию/редакцию Deckhouse и условия стенда проверяют по [общему README](../README.md).

## Испытание и критерий

Проверяем внутренний маршрут v1/v2 по HTTP-заголовку. Входящий и исходящий пути проверяются отдельно в пунктах 12 и 13; межкластерный маршрут этот опыт не доказывает.

`01-prepare.sh` создаёт изолированные тестовые ресурсы; `02-check.sh` проверяет
заявленный сценарий; `03-cleanup.sh` удаляет namespace `pmi-istio-1` после проверки
метки владельца. Все три файла запускаются независимо через Bash, из любого каталога.
Порядок: prepare → check → сохранение результатов → cleanup. После неудачи сначала
сохраните диагностику, затем выполните cleanup. См. общие предпосылки и коды выхода.

```bash
bash 01-prepare.sh
bash 02-check.sh
bash 03-cleanup.sh
```

Для протокола сохраните версию DKP/Istio, kube-context, образы с digest, вывод команд,
HTTP-результаты и `kubectl -n pmi-istio-1 get pods,svc -o wide`.
Сценарий создан для испытания; фактическое прохождение на Deckhouse пока не подтверждено.
