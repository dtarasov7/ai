# 1. Что даёт Istio для маршрутизации трафика

**Istio позволяет менять путь запроса между сервисами через настройки платформы.**
Приложение обращается к привычному имени сервиса, а прокси выбирает подходящую
версию и реплику. Не нужно в каждом клиенте писать собственные правила вида
«этому пользователю отправить запрос в новую версию».

Представим сервис «Заказы», который вызывает «Оплату». У «Оплаты» одновременно
работают v1 и v2:

```text
«Заказы» → Envoy → «Оплата v1» — обычные запросы
                → «Оплата v2» — запросы с x-cohort: B
```

Правило задаётся VirtualService, а соответствие v1/v2 меткам Pod — DestinationRule.
Выполняет его Envoy; istiod доставляет конфигурацию прокси.
[Механизмы маршрутизации](https://istio.io/latest/docs/concepts/traffic-management/).

Практическая польза здесь — возможность переключать путь вызова без новой сборки
и перезапуска каждого клиента «Оплаты». Это особенно заметно, когда клиентов много
и они написаны на разных языках. У всех остаётся единая политика маршрута,
а изменение можно проверить по реальным ответам backend.

**Как понимать «внутри и вне кластера»**

| Направление | Пример | Что настраивает платформа |
|---|---|---|
| Между сервисами | «Заказы → Оплата» | Внутренние маршруты и subsets |
| Вход в кластер | Браузер → сервис | Ingress gateway и правила host/path |
| Выход из mesh | Сервис → внешний API | ServiceEntry и при необходимости egress gateway |

Внешний API не становится доступным только от появления маршрута: нужны сеть,
адрес, доступные порты и корректные сертификаты. Вход подробно разобран в
[пункте 12](../12/АНАЛИЗ.md), исходящий трафик — в [пункте 13](../13/АНАЛИЗ.md).

**Что можно вынести из приложения**

На платформу можно перенести сетевой выбор версии, распределение запросов
по готовым репликам и правила по HTTP-признакам. Сервису остаются выбор нужной
бизнес-операции, формирование запроса, дедлайн, обработка отказа и идемпотентность.
Например, proxy может доставить запрос «Оплате v2», но не определит, разрешено ли
повторно списать деньги после неоднозначного таймаута.

HTTP-условия работают, когда Envoy видит HTTP. Если приложение само шифрует
соединение до удалённого приложения, proxy не сможет читать его URL и заголовки
без соответствующей организации TLS. Для TCP возможностей выбора меньше.
Дополнительные proxy также требуют памяти, CPU и сопровождения правил.
