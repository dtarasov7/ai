# 3. Что даёт Istio для межсервисной аутентификации и авторизации

**Istio позволяет проверять, какой сервис пришёл с запросом, и применять к нему
общие правила доступа.** Для этого он использует криптографически подтверждённую
identity workload, а не доверие к произвольному заголовку с названием сервиса.

Например, «Оплату» должны вызывать «Заказы», но не «Рекомендации»:

```text
«Заказы»       → mTLS → Envoy «Оплаты» → запрос разрешён
«Рекомендации» → mTLS → Envoy «Оплаты» → запрос запрещён
```

Identity привязана к Kubernetes ServiceAccount. Proxy предъявляют сертификаты,
а `PeerAuthentication` в режиме STRICT требует mTLS. `AuthorizationPolicy`
решает, разрешено ли удостоверенному вызывающему сервису обращение.
[Пример правил межсервисного доступа](https://istio.io/latest/docs/tasks/security/authorization/authz-http/).

**Это два разных вопроса**

| Механизм | Что устанавливает |
|---|---|
| Аутентификация через mTLS | Кто находится на другом конце защищённого соединения? |
| Авторизация через policy | Можно ли этой identity выполнить такой вызов? |

Одного mTLS недостаточно, чтобы разрешить доступ только «Заказам»: другие
доверенные участники mesh тоже могут иметь действительные сертификаты.
Нужна политика разрешённых обращений.

**Какая работа уходит из сервисного кода**

Можно вынести проверку клиентского сертификата на сетевой границе,
выдачу/обновление mesh-сертификатов средствами платформы и общие ограничения
по identity, методу и пути. Не требуется реализовывать собственный одинаковый
механизм доверия в каждом HTTP-сервере.

Но отдельный ServiceAccount нужно назначать осмысленно. Если несколько разных
приложений работают под одной учётной записью, правило по этой identity не сможет
различить их как разные сервисы. Права изменения ServiceAccount и политик —
также часть платформенной защиты.

**Что обязательно остаётся в приложении**

Утверждение «это сервис Заказы» не означает «он вправе оплатить любой заказ».
Сумму, состояние заказа, принадлежность клиенту и запрет повторного списания
проверяет бизнес-логика. Общий сервисный доступ не заменяет пользовательскую
авторизацию из [пункта 4](../4/АНАЛИЗ.md).

Dex относится к входу пользователей. Kubernetes RBAC регулирует операции с API
Kubernetes, например изменение Deployment, и не заменяет AuthorizationPolicy
на запрос к `/pay`. Эти механизмы регулируют доступ на разных уровнях.

**Что доказывает текущий тест**
