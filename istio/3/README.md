# 3. Аутентификация и авторизация. Разграничение доступа (система)

[Практический разбор: что даёт Istio и что остаётся в сервисе](АНАЛИЗ.md).

**Можно:** Да, для межсервисного доступа. **Рекомендация:** Стоит.

## Что означает правый столбец

На скриншоте: `dex-authenticator, dex-idp-proxy, mTLS, RBAC, AuthorizationPolicies`.

Для workload-to-workload нужны mTLS, Kubernetes ServiceAccount, PeerAuthentication STRICT и AuthorizationPolicy. Сертификаты удостоверяют сервисную identity; правило разрешает конкретный principal. Dex относится к пользовательскому входу. Kubernetes RBAC регулирует API Kubernetes, а не HTTP сервиса.

## Плюсы, минусы и границы ответственности

Плюс: выдача и ротация сертификатов, единая проверка вызывающего сервиса. Минус: управление trust domain, политиками и миграцией на STRICT.

mTLS без AuthorizationPolicy не ограничивает круг доверенных клиентов. Доступ к объектам предметной области, tenant и содержимое запросов сервис проверяет сам. Обход proxy и права изменения политик должны быть закрыты платформой.

Источник: [документация механизма](https://istio.io/latest/docs/tasks/security/authorization/authz-http/).
Версию/редакцию Deckhouse и условия стенда проверяют по [общему README](../README.md).

## Испытание и критерий

Клиент allowed получает 200; клиент denied с другим ServiceAccount получает 403; клиент без sidecar не устанавливает обычное HTTP-соединение с STRICT backend. Положительная проверка исключает ошибочное принятие общего отказа за защиту.

`01-prepare.sh` создаёт изолированные тестовые ресурсы; `02-check.sh` проверяет
заявленный сценарий; `03-cleanup.sh` удаляет namespace `pmi-istio-3` после проверки
метки владельца. Все три файла запускаются независимо через Bash, из любого каталога.
Порядок: prepare → check → сохранение результатов → cleanup. После неудачи сначала
сохраните диагностику, затем выполните cleanup. См. общие предпосылки и коды выхода.

```bash
bash 01-prepare.sh
bash 02-check.sh
bash 03-cleanup.sh
```

Для протокола сохраните версию DKP/Istio, kube-context, образы с digest, вывод команд,
HTTP-результаты и `kubectl -n pmi-istio-3 get pods,svc -o wide`.
Сценарий создан для испытания; фактическое прохождение на Deckhouse пока не подтверждено.
