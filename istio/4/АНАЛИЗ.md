# 4. Что даёт Istio для пользовательской аутентификации и авторизации

**Istio может проверять предъявленный пользовательский JWT и отсеивать запросы
по его проверенным признакам.** Он помогает унифицировать сетевую проверку токена,
но полный процесс входа пользователя включает другие компоненты.

Пример взаимодействия:

```text
Пользователь → IdP: вход и получение токена
Пользователь с JWT → Envoy → сервис «Документы»
                       ↓
          проверка подписи, issuer, audience, срока
          и условия допуска по проверенной роли
```

`IdP` — поставщик удостоверений, например существующая корпоративная система
входа. `JWT` — подписанный набор утверждений о пользователе. Istio проверяет его
через RequestAuthentication; AuthorizationPolicy требует токен и нужные claims.
Без второй части запрос без токена может быть разрешён.
[Поведение RequestAuthentication](https://istio.io/latest/docs/reference/config/security/request_authentication/).

Предположим, `/reports` разрешён только роли `reader`. После проверки подписи
proxy может отклонить токен с ролью `guest` до обращения к приложению.
Переданный пользователем обычный заголовок `role: reader` такой проверкой не является.

**Где проходят границы ответственности**

| Работа | Кто её выполняет |
|---|---|
| Вход, MFA, выдача и обновление токена | IdP, OIDC proxy и соответствующий пользовательский поток |
| Проверка принятого JWT и общих условий допуска | Istio при настроенных политиках |
| Право читать конкретный документ | Приложение или отдельная система бизнес-авторизации |
| Реакция интерфейса на истёкшую сессию | Клиентское приложение и система входа |

Например, роль `reader` не даёт права видеть документы всех организаций.
Сервису нужно проверить tenant, принадлежность документа и актуальные ограничения.
Старый корректно подписанный JWT также не становится автоматически недействительным
в момент изменения роли в корпоративной базе: схему срока жизни и отзыва проектируют отдельно.

**Что можно вынести из кода**

На платформу можно перенести одинаковую проверку подписи и общие ограничения
на HTTP-границе. Приложению всё равно нужен надёжный способ получить проверенную
identity для бизнес-проверок; выбранные настройки передачи токена/claims нужно
согласовать. Просто удалить библиотеку авторизации из всех сервисов было бы неверно.

Цена такого решения — сопровождение IdP, ключей, доступности JWKS и политик.
Наличие Dex или настройки входа в Kiali не включает автоматически SSO каждого приложения.
