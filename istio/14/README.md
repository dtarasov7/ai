# 14. Circuit breaker

[Практический разбор: что даёт Istio и что остаётся в сервисе](АНАЛИЗ.md).

**Можно:** Да, сетевой. **Рекомендация:** Стоит с настройкой под нагрузку.

## Как реализуется возможность

DestinationRule.connectionPool ограничивает соединения/очереди/запросы, outlierDetection временно исключает проблемные upstream. Решение принимает каждый Envoy локально.

## Плюсы, минусы и границы ответственности

Плюс: ограничение давления на зависимость и распространения отказов. Минус: ошибочные пороги дают дополнительные 503, а retries могут усилить нагрузку.

Это не единый распределённый circuit breaker на весь сервис и не бизнес-fallback. Приложение обязано обработать отказ и определить идемпотентность. Outlier detection пассивный и зависит от трафика; не равен активному health check.

Источник: [документация механизма](https://istio.io/latest/docs/tasks/traffic-management/circuit-breaking/).
Версию/редакцию Deckhouse и условия стенда проверяют по [общему README](../README.md).

## Испытание и критерий

Один запрос проходит; конкурентные медленные запросы переполняют лимит. Требуем одновременно 200, 503 и рост upstream_rq_pending_overflow в статистике клиента. Это проверка connectionPool, не отдельное испытание outlierDetection.

`01-prepare.sh` создаёт изолированные тестовые ресурсы; `02-check.sh` проверяет
заявленный сценарий; `03-cleanup.sh` удаляет namespace `pmi-istio-14` после проверки
метки владельца. Все три файла запускаются независимо через Bash, из любого каталога.
Порядок: prepare → check → сохранение результатов → cleanup. После неудачи сначала
сохраните диагностику, затем выполните cleanup. См. общие предпосылки и коды выхода.

```bash
bash 01-prepare.sh
bash 02-check.sh
bash 03-cleanup.sh
```

Для протокола сохраните версию DKP/Istio, kube-context, образы с digest, вывод команд,
HTTP-результаты и `kubectl -n pmi-istio-14 get pods,svc -o wide`.
Сценарий создан для испытания; фактическое прохождение на Deckhouse пока не подтверждено.
