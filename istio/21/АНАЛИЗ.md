# 21. Fault injection: искусственные ошибки и задержки

Istio позволяет намеренно ухудшить HTTP-вызовы выбранной зависимости, чтобы
проверить поведение вызывающего сервиса. Например, «Оплата» здорова, но для тестового
запроса «Заказов» proxy возвращает 503 или задерживает передачу на две секунды.
Менять код «Оплаты» для такой имитации не требуется.

```text
Заказы → Envoy с fault rule → Оплата
             ├─ abort: клиент получает 503, Оплата не вызвана
             └─ delay: запрос передаётся Оплате позже
```

В VirtualService выбирают запрос по пути/заголовкам и задают `fault.abort` либо
`fault.delay`, вероятность и величину воздействия. В нашем тесте вероятность 100%,
чтобы результат каждого запроса был предсказуем. Процент 10% на десяти запросах
не гарантирует ровно один отказ.

| Что даёт механизм | Что нужно от разработки |
|---|---|
| Повторяемая имитация сетевой ошибки зависимости | Проверка fallback и понятного ответа пользователю |
| Задержка вызова без замедления самого backend | Ограничение очередей, потоков и времени ожидания |
| Выбор тестовой группы запросов | Доверенное назначение тестового заголовка |
| Единая настройка для разных языков | Проверка транзакций и бизнес-инвариантов |

Особенно полезно проверить: не зависает ли вызывающий сервис, освобождает ли ресурсы,
не создаёт ли повторный платёж, возвращает ли пользователю ожидаемую ошибку.
Зелёный тест proxy ещё не доказывает ни один из этих бизнес-результатов. Для этого
учебный клиент надо заменить своим сервисом и определить критерии его поведения.

Fault injection не моделирует заполненный диск, блокировку БД, потерю отдельных
TCP-пакетов или падение процесса. Для HTTP внутри непрозрачного TLS правила L7 не
работают без доступа proxy к HTTP. Выбранный заголовок — средство маршрутизации,
а не авторизации: нельзя оставлять возможность любому внешнему пользователю включать
аварию. На рабочем контуре область воздействия должна быть явно ограничена.

Существенная особенность Istio: на маршруте с fault injection нельзя рассчитывать
на обычное совместное действие route retries/timeout. Поэтому в пунктах 22–23
задержки и 503 создаёт **сам учебный backend**, а не fault rule на клиентском proxy.
Это предотвращает проверку не того механизма.

Наш тест подтверждает: обычный запрос доходит один раз; abort возвращает 503 и
вообще не доходит; delay возвращает 200 спустя примерно две секунды и доходит один
раз; незатронутый запрос снова проходит. Счётчик на сервере — независимое
доказательство отсутствия вызова при abort. **Стоит для испытаний устойчивости**;
в штатной конфигурации это не средство повышения доступности.
