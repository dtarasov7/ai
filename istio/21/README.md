# 21. Fault injection: искусственные ошибки и задержки

[Подробный анализ](АНАЛИЗ.md) · [Общие условия](../README.md) · [Таблица](../ТАБЛИЦА.md)

## Что проверяем

Обычный запрос: 200/1 обращение; abort: 503/0; delay: 200/1 и задержка ≥1,8 с; обычный запрос снова проходит.

Создаются namespace `pmi-istio-21`, один backend с sidecar, клиент с sidecar,
ConfigMap с учебным HTTP-сервером, Service, DestinationRule и VirtualService.
Приложение хранит счётчики в памяти по уникальному id; readiness и чтение `/stats`
не меняют их. Перезапуск backend во время check делает результат недостоверным.
Клиент не делает собственных повторов. Весь трафик — учебный HTTP/1.1.

## Запуск

Нужны работающий sidecar Istio, kubectl и Bash. Образ `TEST_IMAGE` должен содержать
`python` ≥3.8 и стандартную библиотеку. По умолчанию — `python:3.12-alpine`.
Запускайте из этого каталога, по одному опыту; не используйте `PYTHONOPTIMIZE`.

```bash
# Для Deckhouse:
bash 01-prepare.sh
# Для K3s ВМЕСТО предыдущей команды:
# bash 01-prepare-k3s.sh
bash 02-check.sh
# Сохраните вывод и диагностические ресурсы перед очисткой.
bash 03-cleanup.sh
```

Prepare не меняет глобальную конфигурацию и отказывается присваивать чужой namespace.
Check ждёт маркер маршрута до 30 попыток, затем проверяет HTTP-коды, время и число
обращений. Код 0 означает PASS только перечисленных случаев; любой assert/ошибка
даёт ненулевой выход. Cleanup проверяет владельца и удаляет только namespace опыта.
После ошибки сохраните `kubectl -n pmi-istio-21 get pods` и логи контейнера app
Deployment/demo-v1; повторный полный прогон выполняйте после cleanup.

## Ограничения

Это тест механизма Istio, а не бизнес-поведения вашего сервиса. Чтобы проверить
fallback/транзакции приложения, нужен отдельный сценарий с самим приложением.
Не проверены gRPC, streaming, HTTPS внутри приложения и влияние нагрузки.
Глобальные политики и нехватка ресурсов могут изменить результат. Скрипты используют
совместимые API v1beta1; served-версии и поля проверяет API стенда.
Реальный прогон требует доступного Kubernetes; локальная статическая проверка
не является подтверждением работы proxy. См. [анализ](АНАЛИЗ.md) для точной семантики.
