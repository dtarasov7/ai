# 7. Что даёт Istio для хранения конфигурации

**Istiod не следует использовать как универсальное хранилище настроек приложений.**
Он читает сетевую конфигурацию и доставляет её proxy. Следует различать
хранение правил mesh и параметров прикладных сервисов.

Для маршрута взаимодействие выглядит так:

```text
VirtualService в Kubernetes API → istiod → рабочая конфигурация Envoy
```

Долговечный ресурс хранится системой Kubernetes, а преобразование и доставка —
работа istiod. [Роль istiod](https://istio.io/latest/docs/ops/deployment/architecture/).
В обычном Kubernetes backend хранения — etcd; в одноузловом K3s из нашей инструкции
по умолчанию используется SQLite. Поэтому даже слово «etcd» нельзя считать
обязательным свойством каждого испытательного стенда.
[Варианты хранилища K3s](https://docs.k3s.io/datastore).

**Пример, показывающий границу**

| Настройка | Подходит ли механизм Istio? |
|---|---|
| Направлять 10% трафика в v2 | Да, как mesh-правило в VirtualService |
| Использовать конкретный алгоритм балансировки | Да, через DestinationRule |
| Размер бизнес-скидки | Нет, это конфигурация приложения |
| Пароль подключения к базе | Нет, это задача управления секретами |

Для двух последних строк нужны соответствующие средства Kubernetes или отдельная
система конфигурации/секретов. Приложение должно прочитать настройки, проверить
значения и определить, можно ли применить их без перезапуска.

**Какая польза всё-таки есть**

Декларативные сетевые правила можно хранить в Git, обсуждать как изменения
конфигурации и применять штатными средствами доставки. Сервисам не нужно читать
пользовательские YAML Istio и самостоятельно реализовывать их сетевую семантику.
Однако Git не появляется автоматически от установки mesh: репозиторий и процесс
применения организует команда платформы.

Нужно сопровождать права записи в API, резервирование datastore и порядок
восстановления. Рабочая конфигурация, уже полученная Envoy, не является резервной
копией всей системы. Доступность приложения со старой конфигурацией не гарантирует
выдачу сертификатов и правил новым proxy при недоступном control plane.

**Что можно обещать архитекторам**

Можно централизованно управлять сетевыми настройками сервисов. Обещать перенос
всех прикладных настроек в istiod технически неправильно. Более простое решение
для настроек конкретного сервиса — оставить их в предназначенном для этого
источнике и не вводить дополнительный путь через mesh.

**Что доказывает текущий тест**
