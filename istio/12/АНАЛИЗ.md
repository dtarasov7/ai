# 12. Что даёт Istio для публикации сервиса наружу

**Istio ingress gateway даёт общую точку входа, на которой можно выбрать сервис
по имени сайта и пути, применить сетевые политики и при необходимости завершить TLS.**
Сервисы за ним могут оставаться внутренними и не публиковать каждый собственный
внешний порт.

Пример для сайта:

```text
Браузер → адрес входа → Istio ingress gateway
                         ├─ /orders → «Заказы»
                         └─ /pay    → «Оплата»
```

В режиме, используемом в наших сценариях, gateway — запущенный Envoy.
Ресурс Gateway описывает listener, а VirtualService — маршрут к backend.
В Deckhouse Pod/Service контроллера создаются соответствующими средствами платформы.
[Примеры публикации в Deckhouse](https://deckhouse.io/modules/istio/examples.html).

**Что это освобождает от самостоятельной реализации**

Приложению не обязательно самому управлять внешними доменами, общей точкой
TLS termination и выбором версии за публичным URL, если эти функции действительно
приняты gateway. Например, сертификат публичного сайта может обслуживаться на
входе, а внутри mesh используется отдельное mTLS-взаимодействие.

Один только gateway не решает все вопросы публикации:

| Часть пути | Что нужно обеспечить |
|---|---|
| Пользователь нашёл сайт | DNS или явный адрес и Host |
| Сеть доставила соединение | Доступный IP, LB/NodePort и firewall |
| Gateway принял запрос | Listener, сертификат для HTTPS и подходящий host |
| Запрос дошёл до приложения | VirtualService, доступный backend и политики |

Поэтому наличие объекта Gateway ещё не означает, что сервис доступен с рабочей
машины. Его нужно проверить через реальный вход, а не только через port-forward
непосредственно к приложению.

**Что остаётся у сервиса и команды платформы**

Сервис обрабатывает HTTP-запрос и бизнес-авторизацию, формирует корректные
перенаправления и ссылки с учётом схемы публикации. Согласовать доверенные
заголовки внешнего proxy также необходимо. TLS termination не исправляет
уязвимость обработчика или ошибочные права пользователя.

Платформа сопровождает сам gateway, сертификаты, внешнюю сеть и маршруты.
Это дополнительный компонент, потребляющий ресурсы. Моя оценка: он полезен
для единого управления входом в mesh; менять уже работающий ingress только ради
слова Istio следует при наличии конкретных требований.

**Как устроен наш K3s-вариант и что проверяет тест**

В K3s уже установлен `istio-system/istio-ingressgateway`. Service NodePort
публикует порт 80 на 30080. Тестовый Gateway выбирает его Pod через
`istio: ingressgateway`; маршрут и subsets видимы namespace gateway.
Адрес проверки — `http://${LAB_IP}:30080`, нужный Host передаётся явно.

Тест № 12 требует `/allowed` → HTTP 200 и v1, `/blocked` → 404.
Он проверяет HTTP-публикацию. Выполнение check на самой ВМ не подтверждает
внешнюю достижимость с рабочего места. HTTPS, цепочка сертификатов, WAF и защита
от перегрузки этим опытом не проверяются.
Запуск обоих вариантов — в [README пункта](README.md); [общие условия](../README.md).
