# Проверка комплекта Istio

Дата: 28.10.2026. Комплект: 19 каталогов, 19 описаний и 78 исполняемых
сценариев (57 исходных, 19 копий prepare и копии check/cleanup пункта 12 для K3s); общие инструкции и сводная таблица.

## Что проверено локально в исходных 57 сценариях

- `bash -n` отдельно для каждого из 57 файлов: ошибок нет.
- `shellcheck -S warning istio/*/*.sh`: ошибок и предупреждений нет.
- YAML из heredoc разобран PyYAML; Python из heredoc, `python -c` и ConfigMap
  с HTTP-сервером синтаксически проверен. Проверены ссылки на локальные документы,
  UTF-8 и отсутствие CRLF.
- Все 19 prepare выполнены с подменённым kubectl: разобраны 175 реально
  сформированных объектов (включая Namespace и JSON-ресурсы JWT).
  Проверены совпадение selector/labels, ограничение exportTo и экспорт subsets
  пункта 12 в namespace gateway. Это проверка генерации, не применения Kubernetes API.
- Одноразовые JWT реально подписаны OpenSSL; подписи четырёх токенов проверены
  RSA-ключом из JWKS, повреждённая подпись отвергнута. Неверные claims должен
  отклонить Envoy на стенде — локальная проверка подписи этого не доказывает.
- Логика HTTP-стенда проверена в пяти случаях: обычный запрос, готовность,
  неготовность, явный 503 и задержка. Проверены код и Content-Length;
  HTTP-сокеты и mesh в этой проверке не использовались.
- 76 проверок cleanup с подменённым kubectl: для каждого пункта свои ресурсы
  удаляются, чужая/отсутствующая метка запрещает удаление, отсутствующий namespace
  считается уже очищенным. Реальные объекты кластера не создавались и не удалялись.

Временные средства генерации/подмены kubectl и тестовые ключи удалены после проверки.
Сценарии самостоятельные: общей исполняемой библиотеки и генератора для запуска не нужно.

## Что не подтверждено

`kubectl config current-context` вернул `kind-ktop-test`. Команда
`kubectl --request-timeout=5s get --raw=/version` завершилась ошибкой:

```text
Unable to connect to the server: dial tcp 127.0.0.1:35865: socket: operation not permitted
```

Это ограничение доступа в текущем окружении; состояние целевого Deckhouse неизвестно.
Не выполнялись server-side schema/admission validation, injection, xDS propagation,
сетевые проверки, измерение долей трафика, работа с ingress и приёмка backend/UI.
Статические проверки и mock не подтверждают совместимость с конкретной поставкой
CSE 1.73.4 или работоспособность на живом кластере.

Для фактического прогона нужен kubeconfig доступного испытательного Deckhouse.
Пример команды после указания реального файла kubeconfig:

```bash
KUBECONFIG=/путь/к/deckhouse-kubeconfig bash istio/1/01-prepare.sh
```

Затем с тем же kubeconfig выполнить check и cleanup. Фактическую версию Istio,
редакцию/лицензию DKP и доступность нужных функций следует записать в протокол.
Пункты 5/19 требуют ручной фиксации backend/UI после автоматической части;
их код 2 означает незавершённую полную приёмку. Для пунктов с частичной реализацией
проверяется только явно заявленная область применимости возможности.

## Копии prepare для K3s

Созданы `1–19/01-prepare-k3s.sh`: вместо Module проверяются rollout и readyReplicas
istiod, готовые endpoints, injection webhook (Service, namespace, /inject, caBundle)
и Established используемых CRD. Сохранены проверки API и вся дальнейшая подготовка.

- Все 19 новых скриптов прошли `bash -n` и
  `shellcheck -S warning istio/*/01-prepare-k3s.sh`.
- Проверены UTF-8/LF и исполняемые права.
- JSONPath извлечения webhook проверен локальным kubectl на тестовых данных
  через `config view`, без обращения к API.
- `python -m unittest discover -s tests -p 'test_istio_k3s_preconditions.py' -v`:
  все 6 тестовых методов прошли. Подмена kubectl проверяет все 19 копий на допуск
  к первой операции создания и остановку при недоступном istiod, нуле готовых реплик,
  отсутствии webhook, CRD или нужной версии API. Отдельно проверены пустой CA,
  неверный namespace/путь/Service webhook, отсутствие и задержка готовых endpoints,
  выбор revision и нестандартного namespace Istio.
- Сравнение 18 копий с исходниками подтверждает неизменность всех команд, начиная
  с `kubectl explain`, включая манифесты и проверку фактической injection.
  Для пункта 12 дополнительно адаптирован ingress; серверный стенд сохранён.

Новые сценарии на реальном K3s не запускались. Для полной приёмки 5/19
нужны компоненты наблюдаемости из инструкции K3s.

## Ingress пункта 12 на K3s

В `12/01-prepare-k3s.sh` использованы существующий gateway в `istio-system`,
selector `istio: ingressgateway`, экспорт VirtualService/DestinationRule
в `istio-system`. Проверка Deployment/Ready Pod и Service NodePort 80 -> 30080
выполняется до создания ресурсов опыта. Созданы `02-check-k3s.sh` и
`03-cleanup-k3s.sh`: проверка адреса `http://${LAB_IP}:30080` и очистка namespace
с проверкой владельца. Исходные Deckhouse-скрипты сохранены.

Проверки:

- `bash -n` и `shellcheck -S warning istio/12/*-k3s.sh` проходят.
- `PYTHONDONTWRITEBYTECODE=1 python -m unittest discover -s tests -p 'test_istio_k3s*.py' -v`:
  все 11 тестовых методов прошли.
- Новые mock-проверки охватывают создание Gateway/VirtualService/DestinationRule,
  selector/exportTo/subset, остановку до мутаций при отсутствии gateway или неверном
  типе/порте Service, корректный Host/NodePort, повтор при отказе соединения,
  отклонение неверной версии backend и HTTP-кодов, очистку только своего namespace.
- Проверены UTF-8/LF и ссылки на локальные документы.

Применение на реальном кластере и внешний сетевой доступ не проверены:
доступного K3s-стенда в этом окружении нет.

## Python 3.8 и комментарии для проверяющих

Изменения относятся только к комплекту Istio 1–19 и его локальным проверкам.
Все 78 Bash-сценариев используют `python` вместо `python3`, включая команды
контейнеров, локальную подготовку JWT и K3s-копии. В Bash, YAML и Python добавлены
пояснения на русском, смысловые блоки разделены пустыми строками; объявления
JWT-ресурсов и таблицы ожидаемых кодов раскрыты для чтения.

Проверки выполнены настоящим **Python 3.8.20**, доступным как `/usr/bin/python`:

- Все 78 файлов прошли `bash -n` и `shellcheck -S warning istio/*/*.sh`.
- Из heredoc, аргументов `-c`, ConfigMap и команд Pod извлечены **137 Python-программ**.
  Все разобраны и скомпилированы с грамматикой Python 3.8.
- Сравнение AST с исходниками до правок подтвердило неизменность логики всех
  137 программ. После замены имени интерпретатора также совпали данные всех
  **351 YAML-манифеста**; комментарии исходного кода backend при сравнении исключены.
- `PYTHONDONTWRITEBYTECODE=1 python -m unittest discover -s tests -p 'test_istio*.py' -v`:
  **15 тестовых методов прошли**. Помимо прежних предусловий/ingress, проверены
  обработка HTTP 200 и 403, распространение сетевой ошибки, пять случаев работы
  backend/readiness, создание JWT с OpenSSL, четыре корректные подписи и одна
  повреждённая, удаление временного закрытого ключа.
- Проверены UTF-8/LF, локальные ссылки и Bash/Python/YAML в контрольных опытах
  инструкции K3s. Пакет ОС `python3` в команде dnf — название пакета, не вызов
  интерпретатора в сценарии.

Образ по умолчанию оставлен учебным примером. Рабочий образ с бинарником `python`
версии 3.8 задаётся через `TEST_IMAGE`; его доступность на узлах нужно проверить
на реальном стенде. Полный сетевой прогон на Deckhouse/K3s не выполнялся.
