# 16. A/B

[Практический разбор: что даёт Istio и что остаётся в сервисе](АНАЛИЗ.md).

**Можно:** Да для маршрута; частично для эксперимента. **Рекомендация:** Стоит при доверенном назначении группы.

## Как реализуется возможность

Для устойчивого A/B VirtualService выбирает версию по cookie/заголовку с группой пользователя. Случайное разделение весами удобно для canary, но не гарантирует постоянную группу участника.

## Плюсы, минусы и границы ответственности

Плюс: серверные версии без бизнес-ветвления сетевого маршрута. Минус: нужно отдельное назначение группы, аналитика и контроль качества эксперимента.

Istio не рассчитывает статистическую значимость и не хранит состав экспериментальных групп. Клиентский x-cohort легко подделать; для защищённых сценариев группу назначает доверенный backend/edge. Не использовать A/B-заголовок как авторизацию.

Источник: [документация механизма](https://istio.io/latest/docs/tasks/traffic-management/request-routing/).
Версию/редакцию Deckhouse и условия стенда проверяют по [общему README](../README.md).

## Испытание и критерий

Без x-cohort и с A — v1; с B — v2 на повторных запросах. Это детерминированный выбор версии, не измерение эффективности эксперимента.

`01-prepare.sh` создаёт изолированные тестовые ресурсы; `02-check.sh` проверяет
заявленный сценарий; `03-cleanup.sh` удаляет namespace `pmi-istio-16` после проверки
метки владельца. Все три файла запускаются независимо через Bash, из любого каталога.
Порядок: prepare → check → сохранение результатов → cleanup. После неудачи сначала
сохраните диагностику, затем выполните cleanup. См. общие предпосылки и коды выхода.

```bash
bash 01-prepare.sh
bash 02-check.sh
bash 03-cleanup.sh
```

Для протокола сохраните версию DKP/Istio, kube-context, образы с digest, вывод команд,
HTTP-результаты и `kubectl -n pmi-istio-16 get pods,svc -o wide`.
Сценарий создан для испытания; фактическое прохождение на Deckhouse пока не подтверждено.
