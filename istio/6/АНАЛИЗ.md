# 6. Что даёт Istio для обнаружения сервисов

**Istio помогает proxy узнавать, какие экземпляры нужного сервиса доступны сейчас.**
Клиент обращается к стабильному имени, а адреса конкретных Pod обновляются
в сетевой конфигурации без ручного редактирования клиента.

Представим, что у «Оплаты» работала одна реплика, затем добавили ещё одну:

```text
До масштабирования: «Заказы» → «Оплата» → Pod 1
После:              «Заказы» → «Оплата» → Pod 1 или Pod 2
```

istiod получает сведения из Kubernetes и доставляет их Envoy. Proxy может выбирать
готовый endpoint напрямую; для дополнительных сервисов вне обычного Kubernetes
реестра применяют ServiceEntry.
[Как Istio использует сервисы и endpoints](https://istio.io/latest/docs/ops/configuration/traffic-management/traffic-routing/).

**Что здесь уже делает Kubernetes**

В обычном Kubernetes Service уже даёт стабильную точку обращения и использует
актуальные endpoints. Поэтому утверждение «без Istio каждому приложению придётся
вручную хранить IP Pod» неверно. Большая часть такой задачи решается платформой
и без mesh.

Добавленная ценность Istio появляется, когда обнаруженный набор адресов нужно
использовать вместе с его политиками: subsets версий, сетевой авторизацией,
наблюдаемостью, дополнительными записями сервисов. Это мой архитектурный вывод:
ради одного стабильного имени Service вводить отдельный mesh обычно избыточно.

**Три шага, которые важно различать**

| Задача | Пример |
|---|---|
| Разрешить имя | Получить IP для `payment.shop.svc.cluster.local` |
| Обнаружить экземпляры | Узнать адреса готовых Pod «Оплаты» |
| Выбрать маршрут | Направить запрос в subset v2 |

Первый вопрос разобран в [пункте 10](../10/АНАЛИЗ.md), последний — в
[пункте 1](../1/АНАЛИЗ.md). Наличие сервиса в реестре не означает, что доступ
к нему разрешён любой identity.

**Что остаётся в приложении**

Сервису не нужен собственный список Pod, если он корректно использует платформенный
Service. Однако он должен знать логическое имя своей зависимости, корректно
обрабатывать её отсутствие и не рассчитывать на бессрочную жизнь одного TCP-соединения.
Обновление endpoints не переносит автоматически уже установленные соединения.

Платформенная команда сопровождает Service, labels, readiness и область видимости
конфигурации. При задержке обновления адресов часть запросов может попасть
в меняющийся набор реплик; это нужно учитывать при проверках выкладки.

**Что доказывает текущий тест**

Тест № 6 начинает с v1, добавляет v2 и получает реальные ответы обеих версий.
После удаления v2 ответы должны остаться только от v1. Это показывает изменение
доступных backend, но само по себе не отделяет все механизмы Istio от базового
discovery Kubernetes и не проверяет multicluster.
