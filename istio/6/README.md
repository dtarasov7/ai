# 6. Обнаружение сервисов

[Практический разбор: что даёт Istio и что остаётся в сервисе](АНАЛИЗ.md).

**Можно:** Да. **Рекомендация:** Стоит; Kubernetes часто достаточен.

## Как реализуется возможность

istiod наблюдает Service и EndpointSlice Kubernetes и сообщает Envoy адреса доступных workload. ServiceEntry добавляет сторонние адреса. Для приложения обычно достаточно стабильного имени Kubernetes Service.

## Плюсы, минусы и границы ответственности

Плюс: изменение реплик не требует переконфигурации клиентов. Минус: ресурсы control plane и proxy, область видимости конфигурации и задержки обновления.

Discovery не означает DNS-разрешение имени и не является контролем доступа. Для обычного Kubernetes Service выделенный mesh ради одного discovery обычно избыточен. Межкластерное обнаружение требует отдельной настройки.

Источник: [документация механизма](https://istio.io/latest/docs/ops/configuration/traffic-management/traffic-routing/).
Версию/редакцию Deckhouse и условия стенда проверяют по [общему README](../README.md).

## Испытание и критерий

Начинаем с v1; включаем ранее выключенную v2, ждём Ready и получаем обе версии, затем выключаем v2 и проверяем только v1. Это наблюдаемое обновление маршрутов, а не просто наличие Service.

`01-prepare.sh` создаёт изолированные тестовые ресурсы; `02-check.sh` проверяет
заявленный сценарий; `03-cleanup.sh` удаляет namespace `pmi-istio-6` после проверки
метки владельца. Все три файла запускаются независимо через Bash, из любого каталога.
Порядок: prepare → check → сохранение результатов → cleanup. После неудачи сначала
сохраните диагностику, затем выполните cleanup. См. общие предпосылки и коды выхода.

```bash
bash 01-prepare.sh
bash 02-check.sh
bash 03-cleanup.sh
```

Для протокола сохраните версию DKP/Istio, kube-context, образы с digest, вывод команд,
HTTP-результаты и `kubectl -n pmi-istio-6 get pods,svc -o wide`.
Сценарий создан для испытания; фактическое прохождение на Deckhouse пока не подтверждено.
