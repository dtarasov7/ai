# 11. Изоляция сетей

[Практический разбор: что даёт Istio и что остаётся в сервисе](АНАЛИЗ.md).

**Можно:** Частично. **Рекомендация:** Стоит совместно с CNI.

## Как реализуется возможность

PeerAuthentication и AuthorizationPolicy ограничивают обращения к workload по identity и L7-признакам. Kubernetes NetworkPolicy/Cilium ограничивают сетевую достижимость. VirtualService и Sidecar exportTo управляют маршрутизацией/видимостью, а не создают границу безопасности.

## Плюсы, минусы и границы ответственности

Плюс: правила по сервисной identity, методу и пути. Минус: две согласуемые плоскости политик и сложная диагностика отказов.

Istio не заменяет изоляцию Pod/узлов, контроль UDP, hostNetwork, egress firewall и защиту от обхода proxy. Для заявления о полной изоляции нужны тесты CNI и доступа к IP напрямую.

Источник: [документация механизма](https://istio.io/latest/docs/ops/best-practices/security/).
Версию/редакцию Deckhouse и условия стенда проверяют по [общему README](../README.md).

## Испытание и критерий

Разрешённый mesh-клиент: GET → 200, POST → 403; другой ServiceAccount → 403; plaintext → отказ при STRICT. Доказывается L7/identity-ограничение, не полная сетевая изоляция; в основном комплекте см. пункт 64.

`01-prepare.sh` создаёт изолированные тестовые ресурсы; `02-check.sh` проверяет
заявленный сценарий; `03-cleanup.sh` удаляет namespace `pmi-istio-11` после проверки
метки владельца. Все три файла запускаются независимо через Bash, из любого каталога.
Порядок: prepare → check → сохранение результатов → cleanup. После неудачи сначала
сохраните диагностику, затем выполните cleanup. См. общие предпосылки и коды выхода.

```bash
bash 01-prepare.sh
bash 02-check.sh
bash 03-cleanup.sh
```

Для протокола сохраните версию DKP/Istio, kube-context, образы с digest, вывод команд,
HTTP-результаты и `kubectl -n pmi-istio-11 get pods,svc -o wide`.
Сценарий создан для испытания; фактическое прохождение на Deckhouse пока не подтверждено.
