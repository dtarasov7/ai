# 22. Retries: точные условия повторных запросов

Istio может повторить неуспешный HTTP-вызов внутри Envoy. Вызывающее приложение
обычно получает только окончательный ответ, а промежуточные ошибки скрыты.
Например, два ответа 503 и затем 200 превращаются для приложения в один успешный
вызов с увеличенным временем ожидания. Это полезно при кратковременных сбоях,
но не гарантирует безопасного повторения бизнес-операции.

В опыте задано явно: `attempts: 2`, `retryOn: "503"`, `perTryTimeout: 2s`,
общий `timeout: 8s`. Это **до трёх обращений всего**, а не две попытки всего.
Повторы выполняются последовательно с задержками backoff; число может уменьшиться
при исчерпании общего бюджета, ограничении ресурсов proxy или разрыве клиента.
Настройки повторов по умолчанию могут зависеть от версии и mesh config.

| Условие в нашем опыте | Backend получает | Клиент получает |
|---|---|---|
| 503, 503, затем 200 | 3 обращения | Последний 200 и тело с attempt=3 |
| Постоянный 503 | 3 обращения | Последний 503 |
| 400 | 1 обращение | 400 без повтора |
| 503, маршрут attempts=0 | 1 обращение | Первый 503 |
| POST: 503, 503, 200 | 3 обращения | 200; метод сам не запретил повторы |

Указанное число 503 относится к **полученному ответу upstream**. Синтезированный
proxy 503 из-за разрыва соединения не становится автоматически условием `"503"`:
для сетевых событий задаются соответствующие условия вроде `reset` или
`connect-failure`. Более широкое `5xx` имеет другую семантику; подменять им список
конкретных статусов без анализа нельзя. Общий route timeout ограничивает весь вызов
вместе с повторами и backoff. Его истечение — конец бюджета, а не повод начать
новый полный цикл. Per-try timeout ограничивает отдельную попытку; наш узкий тест
проверяет ответы 503 и не доказывает поведение всех сетевых ошибок.

Нельзя обещать повтор после уже переданного клиенту ответа или для произвольного
бесконечного потока. Важны буферизация тела, протокол, лимиты и состояние соединения.
Для gRPC отдельно проверяют статус, trailers и поведение SDK; HTTP-тест этого не
покрывает. Заголовки управления Envoy тоже могут менять поведение, поэтому их
нужно учитывать и фильтровать на границе доверия.

Что остаётся в коде: ключ идемпотентности, защита от двойной записи, обработка
окончательной ошибки и общий дедлайн бизнес-операции. Даже 503 может прийти после
записи в БД. Если SDK делает три попытки, а proxy три, backend может получить
девять обращений. Нужно согласовать владельца retry policy.

Плюсы — единая политика без библиотек каждого языка и устранение коротких отказов.
Минусы — скрытые промежуточные ошибки, дополнительная нагрузка и задержка, риск
повторных действий. **Стоит выборочно для безопасных операций**, после согласования
с разработчиком. Наш backend считает запросы по уникальному id, поэтому тест
проверяет фактические повторы, а не только «в конце получили 200».
