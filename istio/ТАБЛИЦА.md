# Сводная оценка возможностей Istio

Номера 1–19 совпадают со строками скриншота; 20–23 добавлены по обсуждению. «Частично» означает, что перенос
всей функции из приложения в Istio невозможен. Столбец «Анализ» поясняет, какую работу можно
вынести из приложений и какие дополнительные возможности получит команда.
Подробности и источники доступны через README соответствующего пункта.
Рекомендации не означают, что испытания уже пройдены.

| № | Пункт | Можно средствами Istio | Стоит ли делать | Анализ |
| --- | --- | --- | --- | --- |
| [1](1/README.md) | Маршрутизация трафика ППО внутри (east-west) и вне кластера | Да | Стоит | Не нужно в каждом приложении писать правила выбора версии вызываемого сервиса. Можно централизованно направлять разные запросы в разные версии и менять эти правила без перевыпуска приложений. |
| [2](2/README.md) | Конфигурирование обнаружения сервисов и управления трафиком (pilot) | Да | Стоит | Не нужно разрабатывать собственную систему доставки сетевых настроек всем сервисам. Изменения правил взаимодействия и адресов работающих экземпляров распространяются централизованно. |
| [3](3/README.md) | Аутентификация и авторизация. Разграничение доступа (система) | Да, для межсервисного доступа | Стоит | Не нужно в каждом сервисе отдельно реализовывать защищённое соединение и проверку того, какому сервису разрешено его вызывать. Получаем единые правила межсервисного доступа; права на конкретный заказ или документ по-прежнему проверяет приложение. |
| [4](4/README.md) | Аутентификация и авторизация. Разграничение доступа (пользователь) | Частично | Стоит для JWT и грубых правил | Можно вынести из приложений проверку подлинности предъявленного удостоверения пользователя и общие ограничения по роли. Вход в систему и проверка права пользователя на конкретные данные требуют отдельных средств. |
| [5](5/README.md) | Наблюдаемость сервисов (сбор логов, трейсов, метрик) | Частично | Стоит как дополнение | Получаем общую картину: кто кого вызывает, сколько вызовов завершается ошибкой и где возникают задержки. Не нужно отдельно писать одинаковый сбор этих показателей в каждом сервисе; сведения о бизнес-событиях и внутренних действиях добавляет приложение. |
| [6](6/README.md) | Обнаружение сервисов | Да | Стоит; Kubernetes часто достаточен | Не нужно хранить в приложениях списки адресов всех экземпляров зависимого сервиса и самостоятельно обновлять их при запуске или остановке экземпляров. Базовую возможность уже даёт Kubernetes; Istio дополняет её общими правилами взаимодействия. |
| [7](7/README.md) | Хранение конфигурации ОКС (istiod) | Нет как универсальное хранилище; да для mesh-конфигурации | Не стоит для конфигурации приложения | Получаем единое место управления правилами взаимодействия сервисов. Хранение бизнес-настроек приложения, например тарифов и параметров расчёта, этим пунктом не решается. |
| [8](8/README.md) | Группировка сервисов | Частично | Стоит для версий; не для каталога систем | Можно разделять экземпляры сервиса на группы, например по версиям, и отдельно направлять к ним запросы. Приложениям не нужно самостоятельно хранить состав этих групп и выбирать адреса их участников. |
| [9](9/README.md) | Управление стратегиями развёртывания | Частично | Стоит в связке с CI/CD | Можно менять порядок перевода запросов на новую версию без изменения вызывающих приложений. Запуск самих версий и решение о продолжении или откате обновления остаются частью процесса выпуска. |
| [10](10/README.md) | Разрешение имён | Частично | Kubernetes DNS — основа; Istio по необходимости | Приложение может обращаться к зависимости по постоянному имени, не отслеживая смену её адреса. В Kubernetes это уже доступно без Istio; дополнительная польза Istio возникает при подключении внешних сервисов и специальных настройках разрешения имён. |
| [11](11/README.md) | Изоляция сетей | Частично | Стоит совместно с CNI | Не нужно дублировать в каждом сервисе общие запреты на вызовы от других сервисов. Получаем централизованные ограничения взаимодействия; полную сетевую изоляцию обеспечивают вместе с другими средствами платформы. |
| [12](12/README.md) | Публикация сервисов (входящий трафик) | Да | Стоит при использовании mesh | Не нужно в каждом приложении реализовывать общую внешнюю точку входа и распределение входящих запросов между сервисами. Можно единообразно публиковать сервисы и менять направления запросов без изменения их кода. |
| [13](13/README.md) | Реестр внешних сервисов (исходящий трафик) | Да | Стоит; gateway нужен не всегда | Получаем общий учёт внешних систем, к которым обращаются сервисы, и единые правила таких обращений. Можно организовать общую точку выхода; вызовы внешних систем и обработка их бизнес-ответов остаются в приложении. |
| [14](14/README.md) | Circuit breaker | Да, сетевой | Стоит с настройкой под нагрузку | Не нужно в каждом клиенте отдельно писать сетевые ограничения числа одновременных обращений и очереди запросов к зависимости. Получаем защиту от части перегрузок и возможность временно обходить сбоящие экземпляры; действия бизнеса при отказе определяет приложение. |
| [15](15/README.md) | Canary, blue-green | Да, распределение трафика | Стоит совместно с CI/CD | Можно сначала направить на новую версию небольшую долю запросов, затем увеличить её или быстро вернуть запросы на прежнюю версию. В вызывающих приложениях не нужно писать эту логику; возврат трафика не отменяет уже сделанные изменения данных. |
| [16](16/README.md) | A/B | Да для маршрута; частично для эксперимента | Стоит при доверенном назначении группы | Можно направлять разные группы пользователей в разные версии сервиса для сравнения поведения. Не нужно писать выбор версии в каждом вызывающем приложении; назначение пользователей в группы и оценку результатов эксперимента нужно организовать отдельно. |
| [17](17/README.md) | Sticky sessions | Да, мягкая привязка | Условно; предпочесть внешнее хранение сессий | Не нужно самостоятельно писать распределение запросов, которое старается возвращать одного пользователя к тому же экземпляру сервиса. Сохранность его сессии при отказе или замене экземпляра требует отдельного решения. |
| [18](18/README.md) | Health checks | Частично | Стоит использовать Kubernetes probes | Можно автоматически учитывать наблюдаемые ошибки экземпляров при распределении запросов. Проверки готовности и перезапуск уже предоставляет Kubernetes; приложение должно сообщать, когда оно действительно готово обслуживать запросы. |
| [19](19/README.md) | Отображение топологии и информационных потоков | Да для наблюдаемого трафика | Стоит | Получаем наглядную схему фактических связей между сервисами с показателями ошибок и задержек, что упрощает поиск проблем. Не нужно строить такую карту в приложениях; она показывает наблюдаемые вызовы, а не всю бизнес-архитектуру. |
| [20](20/README.md) | Сервисы на обычных ВМ | Да в upstream; поддержка ОС/поставкой требует проверки | Стоит для legacy-сервисов | Можно включить сервисы на обычных ВМ в общие правила защищённого взаимодействия и наблюдения вместе с сервисами Kubernetes. Переносить их в контейнеры ради этого не обязательно; применимость к выбранной ОС и поставке нужно подтвердить. |
| [21](21/README.md) | Fault injection | Да, HTTP delay/abort | Стоит для тестирования | Можно намеренно задерживать вызовы зависимости или возвращать ошибки, чтобы проверить устойчивость своего сервиса. Не нужно добавлять в вызываемое приложение специальный код имитации этих сбоев. |
| [22](22/README.md) | Retries | Да, по условиям политики | Стоит выборочно для безопасных операций | Можно вынести из приложения повторные обращения при выбранных временных сбоях: вызывающий сервис обычно получает итоговый ответ. Приложение всё равно должно защищать бизнес-операции от повторного выполнения, например двойного списания денег. |
| [23](23/README.md) | Timeout | Да, ограничение ожидания proxy | Стоит вместе с прикладными дедлайнами | Можно централизованно ограничить ожидание ответа зависимости, чтобы отдельный вызов не затягивался бесконечно. Вызывающий сервис получает ошибку и должен обработать её; ограничение ожидания не гарантирует остановку работы или отмену операции у получателя. |
