# 2. Конфигурирование обнаружения сервисов и управления трафиком (pilot)

[Практический разбор: что даёт Istio и что остаётся в сервисе](АНАЛИЗ.md).

**Можно:** Да. **Рекомендация:** Стоит.

## Как реализуется возможность

Pilot — функция control plane istiod, а не отдельный обязательный сервис. Kubernetes API и CRD служат источниками правил; istiod преобразует их в xDS и доставляет прокси. Federation и multicluster — дополнительные способы объединения кластеров.

## Плюсы, минусы и границы ответственности

Плюс: декларативная централизованная настройка. Минус: операционная сложность, задержка распространения и необходимость контролировать конфликты правил.

Изменение CRD не означает мгновенного применения всеми Envoy. Federation/multicluster не нужны для обычного discovery и зависят от редакции, сетевой связности и модели доверия.

Источник: [документация механизма](https://istio.io/latest/docs/ops/deployment/architecture/).
Версию/редакцию Deckhouse и условия стенда проверяют по [общему README](../README.md).

## Испытание и критерий

Переключаем VirtualService с v1 на v2 и обратно, проверяем ответы и неизменность UID серверных Pod. Это опыт одного кластера, не проверка federation.

`01-prepare.sh` создаёт изолированные тестовые ресурсы; `02-check.sh` проверяет
заявленный сценарий; `03-cleanup.sh` удаляет namespace `pmi-istio-2` после проверки
метки владельца. Все три файла запускаются независимо через Bash, из любого каталога.
Порядок: prepare → check → сохранение результатов → cleanup. После неудачи сначала
сохраните диагностику, затем выполните cleanup. См. общие предпосылки и коды выхода.

```bash
bash 01-prepare.sh
bash 02-check.sh
bash 03-cleanup.sh
```

Для протокола сохраните версию DKP/Istio, kube-context, образы с digest, вывод команд,
HTTP-результаты и `kubectl -n pmi-istio-2 get pods,svc -o wide`.
Сценарий создан для испытания; фактическое прохождение на Deckhouse пока не подтверждено.
