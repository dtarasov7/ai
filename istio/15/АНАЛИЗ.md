# 15. Что даёт Istio для canary и blue-green

**Istio позволяет дозировать трафик новой версии и переключать его между двумя
уже работающими версиями приложения.** Это инструмент сетевого управления выпуском;
его полезность особенно заметна, когда новую версию нужно сначала проверить на
небольшой части настоящих обращений.

**Canary: постепенное расширение доли**

```text
Начало:       v1 получает 100%, v2 — 0%
Пробный этап: v1 получает 90%,  v2 — 10%
Продвижение:  v1 получает 50%,  v2 — 50%
Завершение:   v1 получает 0%,   v2 — 100%
```

Проценты здесь иллюстративные. DestinationRule описывает subsets, VirtualService
задаёт веса. При ухудшении показателей оператор или система rollout возвращает
долю новой версии к нулю.
[Переключение весов Istio](https://istio.io/latest/docs/tasks/traffic-management/traffic-shifting/).

**Blue-green: подготовить и переключить**

Параллельно работают старый и новый варианты. Новый проходит необходимые проверки,
после чего маршрут направляет к нему пользовательские обращения. Старый вариант
некоторое время сохраняют для возможного сетевого отката.

| Схема | Основной смысл |
|---|---|
| Canary | Постепенно увеличивать участие новой версии |
| Blue-green | Переключиться между подготовленными вариантами |
| A/B из пункта 16 | Сохранять выбранные группы участников для сравнения поведения |

Точный вес — не обещание, что каждый десятый пользователь попадёт в v2.
Для HTTP это выбор на уровне маршрутизируемых запросов. Один пользователь может
попасть в разные версии; длинный поток, повторы и особенности соединений требуют
отдельного учёта. Устойчивую группу задают по признаку запроса.

**Какая работа уходит из кода**

Клиентам не требуется собственный переключатель URL между адресами v1 и v2.
Платформа выполняет сетевой выбор. Но создание версий, проверку готовности,
анализ метрик и решение о переходе выполняют другие части процесса релиза.
Сам Istio не определит по продажам, что новый релиз неудачен.

У разработчиков остаются совместимость API, сессий, данных и фоновых задач.
Если v2 записала необратимые изменения в БД, возврат HTTP-маршрута на v1
не отменит эти изменения. Нельзя выводить гарантию безопасного rollback только
из возможности быстро поменять вес.

**Что даёт и чего стоит такой подход**

Плюс — ограничить первоначальную экспозицию нового кода и отделить сетевое
переключение от выкладки. Минусы — дополнительные мощности для параллельных
версий и необходимость определить хорошие критерии продвижения.
Моя оценка: это полезная возможность mesh, но принимать её нужно вместе с
процессом выпуска из [пункта 9](../9/АНАЛИЗ.md), а не вместо него.

**Что доказывает текущий тест**

Тест № 15 отправляет 1000 запросов при весах 90/10, допускает 5–15% ответов v2,
затем проверяет полное переключение на v2 и откат на v1.
Это статистическая проверка маршрута на небольшой выборке. Автоматическое принятие
решения, SLO, сохранность сессий и миграции данных она не доказывает.
