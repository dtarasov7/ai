# 15. Canary, blue-green

[Практический разбор: что даёт Istio и что остаётся в сервисе](АНАЛИЗ.md).

**Можно:** Да, распределение трафика. **Рекомендация:** Стоит совместно с CI/CD.

## Как реализуется возможность

Две версии создают отдельно, DestinationRule задаёт subsets. VirtualService направляет 90/10 для canary и 100/0 либо 0/100 для blue-green. Автоматизацию продвижения и rollback выполняет rollout-controller/CI/CD.

## Плюсы, минусы и границы ответственности

Плюс: постепенное включение и быстрый сетевой откат. Минус: параллельные мощности и совместимость состояния/БД.

Вес — вероятность маршрута, не точная доля пользователей или маленькой выборки. Sticky sessions, долгие TCP/gRPC-потоки и повторные запросы меняют наблюдаемую картину. Смена маршрута не переносит активную сессию.

Источник: [документация механизма](https://istio.io/latest/docs/tasks/traffic-management/traffic-shifting/).
Версию/редакцию Deckhouse и условия стенда проверяют по [общему README](../README.md).

## Испытание и критерий

1000 отдельных HTTP-запросов при 90/10: v2 должна попасть в широкий интервал 5–15%; затем 100% v2 и откат на 100% v1. Это статистический smoke test, а не доказательство SLO.

`01-prepare.sh` создаёт изолированные тестовые ресурсы; `02-check.sh` проверяет
заявленный сценарий; `03-cleanup.sh` удаляет namespace `pmi-istio-15` после проверки
метки владельца. Все три файла запускаются независимо через Bash, из любого каталога.
Порядок: prepare → check → сохранение результатов → cleanup. После неудачи сначала
сохраните диагностику, затем выполните cleanup. См. общие предпосылки и коды выхода.

```bash
bash 01-prepare.sh
bash 02-check.sh
bash 03-cleanup.sh
```

Для протокола сохраните версию DKP/Istio, kube-context, образы с digest, вывод команд,
HTTP-результаты и `kubectl -n pmi-istio-15 get pods,svc -o wide`.
Сценарий создан для испытания; фактическое прохождение на Deckhouse пока не подтверждено.
