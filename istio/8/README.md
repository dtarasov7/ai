# 8. Группировка сервисов

[Практический разбор: что даёт Istio и что остаётся в сервисе](АНАЛИЗ.md).

**Можно:** Частично. **Рекомендация:** Стоит для версий; не для каталога систем.

## Как реализуется возможность

Service объединяет Pod по labels, DestinationRule определяет subsets версий, а VirtualService маршрутизирует между ними. Namespace и labels удобны для организационной группировки. VirtualService — правило маршрутизации, не универсальная группа сервисов.

## Плюсы, минусы и границы ответственности

Плюс: единое имя для нескольких версий и управление трафиком. Минус: риск несовпадения selector, labels и subset.

Группа независимых сервисов, владение командой, граница безопасности и бизнес-каталог сами по себе не создаются. Subset не порождает Deployment и не добавляет реплики.

Источник: [документация механизма](https://istio.io/latest/docs/reference/config/networking/destination-rule/).
Версию/редакцию Deckhouse и условия стенда проверяют по [общему README](../README.md).

## Испытание и критерий

Под Service demo работают subsets v1/v2. Без заголовка ответ v1, с x-cohort: B — v2. Проверяем HTTP-ответы обеих групп.

`01-prepare.sh` создаёт изолированные тестовые ресурсы; `02-check.sh` проверяет
заявленный сценарий; `03-cleanup.sh` удаляет namespace `pmi-istio-8` после проверки
метки владельца. Все три файла запускаются независимо через Bash, из любого каталога.
Порядок: prepare → check → сохранение результатов → cleanup. После неудачи сначала
сохраните диагностику, затем выполните cleanup. См. общие предпосылки и коды выхода.

```bash
bash 01-prepare.sh
bash 02-check.sh
bash 03-cleanup.sh
```

Для протокола сохраните версию DKP/Istio, kube-context, образы с digest, вывод команд,
HTTP-результаты и `kubectl -n pmi-istio-8 get pods,svc -o wide`.
Сценарий создан для испытания; фактическое прохождение на Deckhouse пока не подтверждено.
