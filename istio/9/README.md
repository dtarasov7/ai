# 9. Управление стратегиями развёртывания

[Практический разбор: что даёт Istio и что остаётся в сервисе](АНАЛИЗ.md).

**Можно:** Частично. **Рекомендация:** Стоит в связке с CI/CD.

## Как реализуется возможность

Istio меняет направление и долю трафика между уже запущенными версиями. Deployment/rollout-controller создаёт реплики, CI/CD меняет веса, анализирует метрики и принимает решение об откате.

## Плюсы, минусы и границы ответственности

Плюс: переключение сети отдельно от выкладки кода. Минус: нужно согласовать rollout, readiness, метрики и сетевые правила.

Istio сам не выполняет сборку, миграции БД, автоматическую оценку SLO и rollback по бизнес-ошибкам. Две версии должны быть совместимы по API/данным; долгие соединения не переключаются мгновенно.

Источник: [документация механизма](https://istio.io/latest/docs/tasks/traffic-management/traffic-shifting/).
Версию/редакцию Deckhouse и условия стенда проверяют по [общему README](../README.md).

## Испытание и критерий

v1 → v2 → v1 с проверкой ответов и неизменности Pod. Доказывается управление маршрутом/ручной откат, не полноценный rollout-controller.

`01-prepare.sh` создаёт изолированные тестовые ресурсы; `02-check.sh` проверяет
заявленный сценарий; `03-cleanup.sh` удаляет namespace `pmi-istio-9` после проверки
метки владельца. Все три файла запускаются независимо через Bash, из любого каталога.
Порядок: prepare → check → сохранение результатов → cleanup. После неудачи сначала
сохраните диагностику, затем выполните cleanup. См. общие предпосылки и коды выхода.

```bash
bash 01-prepare.sh
bash 02-check.sh
bash 03-cleanup.sh
```

Для протокола сохраните версию DKP/Istio, kube-context, образы с digest, вывод команд,
HTTP-результаты и `kubectl -n pmi-istio-9 get pods,svc -o wide`.
Сценарий создан для испытания; фактическое прохождение на Deckhouse пока не подтверждено.
