# 9. Что даёт Istio для управления стратегиями развёртывания

**Istio позволяет отдельно управлять двумя событиями: версия уже запущена,
но пользовательский трафик к ней ещё не направлен.** Это даёт возможность подготовить
новый backend, а затем менять его участие в обслуживании через сетевые правила.

Пример выпуска «Оплаты v2»:

```text
1. CI/CD создаёт v2; v1 продолжает обслуживать пользователей.
2. Kubernetes подтверждает readiness v2.
3. Меняем маршрут Istio: часть запросов получает v2.
4. По результатам проверки увеличиваем долю либо возвращаем трафик в v1.
```

VirtualService задаёт направления и веса маршрутов.
[Конфигурация маршрутов](https://istio.io/latest/docs/reference/config/networking/virtual-service/).
Deployment управляет Pod и их обновлением — это отдельный механизм Kubernetes.
[Задачи Deployment](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/).

**Кто выполняет работу в полноценном процессе**

| Действие | Исполнитель |
|---|---|
| Собрать образ и запустить новую версию | CI/CD и Kubernetes |
| Подтвердить способность принимать запросы | Приложение и readiness probe |
| Выбрать долю трафика в версии | Правила Istio |
| Оценить ошибки и время ответа | Система наблюдаемости и процедура анализа |
| Принять решение о продвижении/откате | Оператор либо настроенный rollout-controller |

Сетевое переключение можно показать без переустановки клиентских приложений.
Это полезнее, чем условие в каждом клиенте «если включён новый релиз, вызывай другой URL».
Но план выпуска, последовательность шагов и критерии приемлемости всё равно нужны.

**Что остаётся обязанностью разработки**

Обе версии должны понимать совместимые API и данные. Например, если v2 изменила
формат записи в БД так, что v1 его не читает, сетевой откат на v1 не исправит данные.
Миграции, совместимость очередей, фоновые задачи и идемпотентность остаются
частью прикладного проекта.

Смена маршрута также не означает мгновенного переноса уже открытого долгого потока.
Нужно определить, как завершаются старые соединения и сколько времени сохраняется
старая версия. Сам Istio не выполняет бизнес-анализ качества выпуска.

**Когда усложнение оправдано**

Моя оценка: mesh полезен, если требуется управлять экспозицией уже работающих версий
и он входит в общую сетевую архитектуру. Для простой замены нескольких stateless Pod
штатного rolling update Kubernetes может быть достаточно. Введение mesh добавляет
правила, ресурсы и отдельные причины отказов, которые придётся сопровождать.
