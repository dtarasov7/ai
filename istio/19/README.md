# 19. Отображение топологии и информационных потоков

[Практический разбор: что даёт Istio и что остаётся в сервисе](АНАЛИЗ.md).

**Можно:** Да для наблюдаемого трафика. **Рекомендация:** Стоит.

## Как реализуется возможность

Kiali строит граф по метрикам Istio из Prometheus и ресурсам Kubernetes/Istio. Узлы — workloads/services, рёбра — наблюдаемые обращения с ошибками/задержками.

## Плюсы, минусы и границы ответственности

Плюс: диагностика зависимостей и ошибочных маршрутов. Минус: зависимость от scraping, интервала графа и покрытия mesh.

Это не полный каталог архитектуры: без трафика ребро может отсутствовать. Не раскрывает семантику данных, цепочки внутри брокера, обходящие proxy соединения и все будущие зависимости. Права доступа Kiali настраиваются отдельно.

Источник: [документация механизма](https://kiali.io/docs/faq/graph/).
Версию/редакцию Deckhouse и условия стенда проверяют по [общему README](../README.md).

## Испытание и критерий

Генерируем трафик allowed → demo, проверяем исходные метрики Envoy; затем в Kiali выбирают namespace и окно 5–15 минут, подтверждают рёбра и значения. Скрипт возвращает 2 до ручной фиксации UI, чтобы наличие метрик не выдать за готовый граф.

`01-prepare.sh` создаёт изолированные тестовые ресурсы; `02-check.sh` проверяет
заявленный сценарий; `03-cleanup.sh` удаляет namespace `pmi-istio-19` после проверки
метки владельца. Все три файла запускаются независимо через Bash, из любого каталога.
Порядок: prepare → check → сохранение результатов → cleanup. После неудачи сначала
сохраните диагностику, затем выполните cleanup. См. общие предпосылки и коды выхода.

```bash
bash 01-prepare.sh
bash 02-check.sh
bash 03-cleanup.sh
```

Для протокола сохраните версию DKP/Istio, kube-context, образы с digest, вывод команд,
HTTP-результаты и `kubectl -n pmi-istio-19 get pods,svc -o wide`.
Сценарий создан для испытания; фактическое прохождение на Deckhouse пока не подтверждено.

## Завершение приёмки графа (после кода 2)

1. Проверить в Prometheus наличие `istio_requests_total{source_workload_namespace="pmi-istio-19"}`.
   Дождаться минимум двух scrape-интервалов. При необходимости повторить check,
   чтобы трафик находился в выбранном временном окне.
2. Открыть Kiali, выбрать namespace `pmi-istio-19`, Graph, период 5–15 минут
   и представление Versioned app/Workload. Подтвердить клиент `allowed`, сервис
   `demo` и обе версии backend, направление рёбер и ненулевую частоту запросов.
3. Сопоставить имена Pod/labels с графом; сохранить снимок и временной интервал.
   При отсутствии графа проверить scraping, выбранный namespace, фильтры и RBAC.
   Не принимать только наличие веб-интерфейса за результат.

Kiali и Prometheus должны быть уже настроены; скрипты их не устанавливают.
После фиксации UI испытание принимается вручную; код 2 сам по себе не означает
ошибки mesh и не является полной успешной приёмкой.
