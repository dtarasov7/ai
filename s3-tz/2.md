## 10. Требования к сохранности и целостности данных

### 10.1. Защита данных

10.1.1. Решение должно использовать репликацию, erasure coding либо комбинацию данных методов.

10.1.2. Схема защиты должна обеспечивать сохранность данных при проектном количестве одновременных отказов.

10.1.3. Поставщик должен предоставить описание выбранной схемы, включая:

* количество фрагментов данных;

* допустимое количество отказов;
* коэффициент накладных расходов;
* требования к количеству узлов и доменам отказа.

### 10.2. Контроль целостности

10.2.1. Для каждого объекта должна рассчитываться и храниться контрольная сумма либо эквивалентный идентификатор целостности.

10.2.2. Проверка целостности должна выполняться:

* при записи;
* при чтении;
* при передаче между узлами;
* при репликации;
* в ходе фоновой проверки.

10.2.3. При выявлении повреждённого фрагмента система должна автоматически восстановить его из исправных копий или контрольных фрагментов.

10.2.4. События повреждения и восстановления должны регистрироваться в журнале аудита и системе мониторинга.

### 10.3. Защита от скрытого повреждения

10.3.1. Решение должно обеспечивать защиту от bit rot и иных скрытых повреждений данных.

10.3.2. Должна выполняться периодическая фоновая проверка целостности данных.

10.3.3. Периодичность и интенсивность проверки должны настраиваться.

10.3.4. Фоновая проверка не должна приводить к существенному нарушению клиентской нагрузки.

### 10.4. Защита от логического удаления

10.4.1. Для критичных данных должны поддерживаться:

* версионирование;
* Object Lock;
* retention;
* legal hold;
* задержка физического удаления;
* отдельные права на удаление объектов и версий.

10.4.2. Административные полномочия должны быть разделены таким образом, чтобы одна учётная запись не могла одновременно отключить защиту и удалить защищённые данные, если это предусмотрено политиками заказчика.

10.4.3. Массовые операции удаления должны регистрироваться и при необходимости формировать предупреждение.

### 10.5. Долговечность данных

10.5.1. Поставщик должен указать расчётный показатель долговечности данных.

10.5.2. Методика расчёта должна учитывать:

* надёжность дисков;
* количество копий или контрольных фрагментов;
* время восстановления;
* вероятность одновременных отказов;
* размер кластера;
* распределение по доменам отказа.

10.5.3. Декларируемые показатели должны сопровождаться описанием допущений и ограничений.

* сведения об ошибках;
* версию программного обеспечения.

13.6.3. Перед передачей диагностического пакета поставщику должна быть доступна возможность исключения или маскирования конфиденциальной информации.

## 14. Требования к мониторингу, журналированию и аудиту

### 14.1. Мониторинг состояния

14.1.1. Решение должно обеспечивать мониторинг:

* доступности сервисов;
* состояния узлов;
* состояния дисков;
* состояния сетевых интерфейсов;
* температуры оборудования;
* состояния блоков питания;
* свободной и занятой ёмкости;
* состояния метаданных;
* состояния репликации;
* состояния фоновых операций;
* состояния сертификатов;
* состояния лицензий.

14.1.2. Для каждого контролируемого параметра должны быть доступны текущее значение, исторические данные и пороговые значения.

### 14.2. Мониторинг производительности

14.2.1. Должны собираться показатели:

* количество S3-операций;
* распределение операций по типам;
* пропускная способность чтения и записи;
* задержки операций;
* количество ошибок;
* количество активных соединений;
* загрузка процессоров;
* использование памяти;
* загрузка сети;
* загрузка дисков;
* размер очередей;
* интенсивность фонового восстановления.

14.2.2. Метрики должны быть доступны в разрезе:

* кластера;
* узла;
* диска;
* бакета;
* арендатора;
* типа операции;
* временного интервала.

14.2.3. Должна поддерживаться передача метрик в систему мониторинга заказчика через [Prometheus/OpenMetrics, SNMP или иной согласованный интерфейс].

### 14.3. Оповещения

14.3.1. Решение должно формировать оповещения как минимум о следующих событиях:

* недоступность узла;
* отказ диска;
* потеря требуемого уровня избыточности;
* превышение порогов ёмкости;
* ошибка репликации;
* нарушение целостности;
* истечение сертификата;
* ошибка резервного копирования конфигурации;
* неуспешное обновление;
* превышение порогов задержки;
* аномальный рост количества ошибок.

14.3.2. Для каждого оповещения должны указываться:

* уровень критичности;
* время возникновения;
* затронутый компонент;
* описание причины;
* рекомендуемые действия;
* статус подтверждения;
* время устранения.

14.3.3. Должна поддерживаться передача оповещений по электронной почте и во внешние системы мониторинга.

### 14.4. Журналирование

14.4.1. Решение должно вести:

* системные журналы;
* журналы S3 API;
* административные журналы;
* журналы безопасности;
* журналы репликации;
* журналы фоновых операций;
* журналы обновления.

14.4.2. Формат журналов должен быть документирован.

14.4.3. Должна поддерживаться централизованная передача журналов по протоколу syslog либо через иной согласованный механизм.

14.4.4. Должна быть предусмотрена настройка уровня детализации журналирования.

14.4.5. Изменение уровня журналирования не должно требовать полной остановки сервиса.

14.4.6. Срок хранения локальных журналов должен настраиваться.

### 14.5. Синхронизация времени

14.5.1. Все компоненты должны синхронизировать системное время с NTP-серверами заказчика.

14.5.2. Система должна формировать предупреждение при превышении допустимого расхождения времени.

14.5.3. Все события и журналы должны содержать отметку времени с указанием часового пояса либо в формате UTC.

## 15. Интеграционные требования

### 15.1. Интеграция с прикладными системами

15.1.1. Решение должно обеспечивать подключение прикладных систем заказчика по S3 API.

15.1.2. Перечень целевых систем, подлежащих обязательной проверке, должен быть приведён в приложении к ТЗ.

15.1.3. Для каждой системы должны быть проверены:

* аутентификация;
* загрузка объектов;
* скачивание объектов;
* удаление объектов;
* multipart upload;
* работа с метаданными;
* обработка ошибок;
* версионирование;
* политики жизненного цикла;
* presigned URL;
* производительность.

15.1.4. Выявленные особенности совместимости должны быть документированы.

### 15.2. Интеграция с системами резервного копирования

15.2.1. Решение должно поддерживать использование в качестве S3-репозитория для систем резервного копирования заказчика.

15.2.2. Должны быть проверены:

* создание репозитория;
* запись резервной копии;
* чтение и восстановление;
* синтетические операции;
* удаление по политике хранения;
* неизменяемость резервных копий;
* параллельная работа нескольких заданий;
* восстановление после потери соединения.

15.2.3. Поставщик должен указать наличие официальной сертификации или подтверждённой совместимости с используемыми системами резервного копирования.

### 15.3. Интеграция с платформами контейнеризации

15.3.1. При использовании Kubernetes решение должно поддерживать доступ приложений к S3 API из контейнерной среды.

15.3.2. Должны поддерживаться:

* безопасное хранение ключей доступа;
* использование временных учётных данных;
* автоматизированное создание бакетов — при необходимости;
* сетевое взаимодействие через сервисы и балансировщики;
* сбор метрик в системе мониторинга Kubernetes.

15.3.3. Поддержка CSI-драйвера или файлового доступа к объектному хранилищу рассматривается как отдельная функция и не должна подменять требования к S3 API.

### 15.4. Интеграция с системами идентификации

15.4.1. Решение должно интегрироваться с корпоративной службой каталогов или поставщиком идентификации заказчика.

15.4.2. Должна поддерживаться привязка групп каталога к ролям объектного хранилища.

15.4.3. Блокировка пользователя в корпоративной системе идентификации должна приводить к прекращению его административного доступа в сроки, определённые механизмом синхронизации.

### 15.5. Интеграция с KMS и HSM

15.5.1. При использовании внешнего управления ключами решение должно интегрироваться с KMS или HSM заказчика.

15.5.2. Должны быть проверены:

* создание ключа;
* использование ключа для шифрования;
* ротация ключа;
* временная недоступность KMS;
* восстановление соединения;
* аудит обращения к ключам;
* разграничение административных полномочий.

15.5.3. Поставщик должен описать поведение системы при недоступности внешнего сервиса управления ключами.

### 15.6. Интеграция с системами мониторинга и SIEM

15.6.1. Метрики должны передаваться в систему мониторинга заказчика.

15.6.2. Журналы безопасности и аудита должны передаваться в SIEM.

15.6.3. Передаваемые события должны содержать достаточные данные для идентификации:

* пользователя;
* операции;
* объекта;
* источника подключения;
* результата выполнения;
* времени события.

15.6.4. Поставщик должен предоставить описание форматов метрик, журналов и событий.

### 15.7. Интеграция с балансировщиками нагрузки и DNS

15.7.1. Решение должно поддерживать работу с внешними балансировщиками нагрузки, используемыми заказчиком.

15.7.2. Должны поддерживаться проверки состояния узлов.

15.7.3. Должна быть обеспечена возможность использования единого DNS-имени для S3 API.

15.7.4. При отказе отдельного узла клиентские приложения не должны требовать изменения настроек подключения.

15.7.5. Решение должно поддерживать корректную работу TLS-сертификатов при использовании единого DNS-имени и virtual-hosted-style addressing.

### 15.8. Интеграция с системами автоматизации

15.8.1. Решение должно предоставлять документированный API для автоматизации административных операций.

15.8.2. Через API должны быть доступны как минимум:

* создание бакетов;
* создание пользователей;
* выпуск ключей;
* настройка политик;
* настройка квот;
* получение статистики;
* получение состояния кластера;
* управление узлами;
* получение событий и предупреждений.

15.8.3. Поставщик должен предоставить документацию и примеры вызова API.

### 15.9. Требования к проверке интеграций

15.9.1. Все обязательные интеграции должны быть проверены на пилотном стенде.

15.9.2. Для каждой интеграции должен быть оформлен протокол, содержащий:

* конфигурацию компонентов;
* используемые версии;
* сценарии тестирования;
* ожидаемый результат;
* фактический результат;
* выявленные ограничения;
* рекомендации по промышленной эксплуатации.

15.9.3. Интеграция считается успешно пройденной при отсутствии критических и блокирующих дефектов и выполнении всех обязательных сценариев.

Следующим логичным этапом будет заполнение измеримых параметров: ёмкости, количества объектов, SLA, RPO/RTO, пропускной способности, IOPS и перечня обязательных интеграций.
