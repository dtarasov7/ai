## 1. Что описывает документ

Рассматриваются внутренние сертификаты Deckhouse Kubernetes Platform (DKP), версии 1.73.4 CSE PRO. Описание составлено по публичным исходникам этой версии. Установленный кластер не обследовался: наличие компонента в исходниках не означает, что он включён в конкретном кластере. Закрытые изменения сертифицированных контейнерных образов отдельно не проверялись.

Исключены сертификаты внешних точек входа в кластер (ingress) и модуль ingress-nginx. Внутренние защищённые соединения Dex, служб проверки ресурсов, мониторинга, хранилища образов и виртуальной частной сети (VPN) рассмотрены. Они имеют собственные сертификаты независимо от того, как организован внешний доступ.

Удостоверяющий центр (УЦ; английское обозначение CA) подписывает сертификаты и тем самым подтверждает их происхождение. **Конечный сертификат** выдаётся серверу, клиенту или компоненту; он не даёт права выпускать другие сертификаты. TLS — протокол защиты соединения с использованием сертификатов; HTTPS — протокол обмена данными HTTP, работающий через TLS.

**В DKP нет одного УЦ и одного процесса, которые выпускают все сертификаты.** Разные группы обслуживают установщик kubeadm, модуль control-plane-manager, встроенные средства Kubernetes, служебные программы модулей и сами запускаемые процессы. Cert-manager — отдельный компонент автоматизации сертификатов — управляет только сертификатами, которые ему действительно заказаны.

Не каждый компонент получает личный клиентский сертификат для обращения к программному интерфейсу Kubernetes (API). Многие программы используют служебную учётную запись Kubernetes (ServiceAccount) и её токен JWT — подписанные данные, подтверждающие эту учётную запись. Файлы `sa.key` и `sa.pub` содержат ключи подписи и проверки таких токенов. **Это ключи для токенов, а не сертификаты X.509**, поэтому корпоративный УЦ не выпускает их как обычные сертификаты TLS. X.509 — формат сертификата, используемый в рассматриваемых соединениях.

## 2. Сертификаты управляющих компонентов Kubernetes

### 2.1. Три независимых УЦ и место хранения

При первоначальной установке программа настройки узлов bashible вызывает kubeadm — средство установки Kubernetes. Kubeadm создаёт исходные сертификаты и ключи.

Они сохраняются **в объекте Kubernetes типа Secret с именем `d8-pki`, в пространстве имён `kube-system`**. Secret — объект Kubernetes для хранения данных, в данном случае сертификатов и ключей. Запись `kube-system/d8-pki` обозначает пространство имён и имя этого объекта; это не путь к файлу на диске.

Далее модуль control-plane-manager, управляющий основными компонентами Kubernetes, устанавливает необходимые копии **в файлы на управляющих узлах**, преимущественно в каталог `/etc/kubernetes/pki`. Управляющий узел — сервер кластера, на котором работают Kubernetes API и другие управляющие процессы.

В объекте Secret хранятся материалы трёх разных УЦ. У каждого своя задача и собственная пара сертификат/ключ:

| Удостоверяющий центр | Какие сертификаты подписывает | Для каких соединений |
| --- | --- | --- |
| УЦ Kubernetes | Сертификат сервера API; сертификат клиента API для обращения к kubelet; клиентские сертификаты управляющих программ и узлов | Программы и узлы → API Kubernetes; сервер API → kubelet |
| УЦ etcd — базы состояния кластера | Сертификаты серверов etcd, участников обмена между ними и клиентов etcd | API Kubernetes → etcd; серверы etcd → друг к другу; проверки работоспособности etcd |
| УЦ доверенных прокси (front-proxy) | Сертификат прокси, которому API разрешает передавать сведения об имени пользователя | Прокси → API и расширения API |

Таким образом, здесь используются **разные УЦ для разных задач**, а не один общий издатель. По исходным настройкам kubeadm срок сертификата УЦ составляет около 10 лет, конечного сертификата — около года. Автоматическая замена конечных сертификатов не означает автоматическую смену всех УЦ: исследованный код копирует базовые УЦ из объекта Secret `d8-pki`.

### 2.2. Какие файлы проверяет control-plane-manager

Модуль проверяет семь пар файлов сертификат/ключ. Пути в таблице приведены относительно каталога `/etc/kubernetes/pki` на управляющем узле:

| Файл сертификата | Назначение |
| --- | --- |
| `apiserver.crt` | Серверный сертификат API Kubernetes |
| `apiserver-kubelet-client.crt` | Клиентский сертификат, с которым сервер API обращается к kubelet |
| `apiserver-etcd-client.crt` | Клиентский сертификат сервера API для доступа к etcd |
| `front-proxy-client.crt` | Сертификат доверенного прокси |
| `etcd/server.crt` | Сертификат сервера etcd |
| `etcd/peer.crt` | Сертификат участника обмена между серверами etcd |
| `etcd/healthcheck-client.crt` | Сертификат клиента, проверяющего работоспособность etcd |

Отдельно проверяются файлы подключения к API, называемые kubeconfig: `admin.conf`, `controller-manager.conf` и `scheduler.conf` в каталоге `/etc/kubernetes`. Такой файл содержит адрес API, данные для проверки его сертификата и учётные данные клиента, включая клиентский сертификат.

У локальных HTTPS-портов kube-controller-manager `10257` и kube-scheduler `10259` есть ещё и **собственные серверные сертификаты**. Они не совпадают с клиентскими сертификатами из файлов подключения. В типовой исходной реализации Kubernetes без заданных файлов серверные сертификаты создаются в памяти при запуске процесса. Шаблоны DKP используют эти локальные порты для мониторинга и проверки работоспособности. Поведение конкретного контейнерного образа зависит от выбранной версии Kubernetes.

### 2.3. Когда происходит обновление

Если нужный файл отсутствует, control-plane-manager вызывает kubeadm для его создания. При изменении расчётной конфигурации модуль также проверяет имя владельца сертификата, разрешённые имена и адреса, алгоритм ключа, наличие ключа и срок действия. Перевыпуск выполняется, в частности, если осталось менее 30 суток. Для файлов подключения проверяются также адрес API и правильность содержимого.

Новая пара записывается на узел, после чего штатный процесс применяет конфигурацию и при необходимости перезапускает соответствующий компонент.

Проверки выполняются при запуске управляющей программы и применении конфигурации. Дополнительно предусмотрено периодическое обновление управляющей программы: значение `rollout_epoch` пересчитывается каждый час и меняет эпоху примерно раз в 10 суток. **Это повод для очередного применения конфигурации, а не требование выпускать новый сертификат каждые 10 суток.** В коде есть проверка контрольной суммы конфигурации, при совпадении которой часть проверок существующих файлов может пропускаться.

## 3. Сертификаты узлов и контроллеров управления узлами

Kubelet — программа на каждом узле Kubernetes, которая запускает и обслуживает поды. Под — объект Kubernetes, объединяющий один или несколько контейнеров приложения. Kubelet нужны клиентский сертификат для обращения к API и серверный сертификат для приёма защищённых соединений.

При первоначальном подключении узла kubelet отправляет запрос на подписание сертификата (Certificate Signing Request, CSR). В Kubernetes такой запрос представлен отдельным объектом `CertificateSigningRequest`. В штатной конфигурации включены автоматическое обновление клиентского сертификата и, после первоначальной установки управляющего узла, получение серверного сертификата через тот же механизм.

Сначала уполномоченный компонент разрешает запрос, затем подписывающий компонент Kubernetes выпускает сертификат. Модуль node-manager участвует в проверке и разрешении запросов kubelet; подпись выполняет встроенная служба Kubernetes. Эти действия не следует смешивать. Ориентир срока — 8760 часов, то есть год. Kubelet сам выбирает момент обновления до истечения срока; точный интервал зависит от версии Kubernetes и случайного сдвига.

Cluster API (CAPI) — набор контроллеров управления узлами кластера; CAPS — его поставщик для статических узлов (Cluster API Provider Static). Для их клиентского подключения к API есть отдельная служебная программа `generate_capi_kubeconfig.go`. Она запрашивает сертификат на 180 суток. При включённой функции программа вызывается перед применением конфигурации модуля и ежедневно в `01:00`. В этом пути нет проверки «старый сертификат ещё действует — новый не нужен». **Срок 180 суток не означает одну выдачу раз в 180 суток.**

Источники: [настройки kubelet](https://github.com/deckhouse/deckhouse/blob/v1.73.4/candi/bashible/common-steps/all/064_configure_kubelet.sh.tpl), [разрешение запросов узлов](https://github.com/deckhouse/deckhouse/blob/v1.73.4/modules/040-node-manager/hooks/kubelet_csr_approver.go), [сертификат подключения CAPI](https://github.com/deckhouse/deckhouse/blob/v1.73.4/modules/040-node-manager/hooks/generate_capi_kubeconfig.go).

## 4. Общая программа выпуска сертификатов внутренних служб

Во многих модулях используется одна общая программная функция `RegisterInternalTLSHook`. Это hook — служебная программа, которую Deckhouse запускает при определённых событиях. В данном случае она обслуживает сертификат службы и сохраняет результат в объекте Secret.

При отсутствии объекта Secret программа создаёт локальный УЦ с сертификатом, подписанным собственным ключом (самоподписанным), затем подписывает им сертификат службы. Самоподписанным является сертификат УЦ; сертификат службы подписан этим УЦ.

**Исходный срок сертификатов УЦ и службы — 87600 часов, около 10 лет.** Если объект Secret существует, из его полей `ca.crt`, `tls.crt` и `tls.key` читаются сертификат УЦ, сертификат службы и ключ службы. Эти обозначения — имена полей объекта Secret, а не обязательно файлы на узле. Компонент, использующий Secret, может получить их как смонтированные файлы.

Новая локальная цепочка создаётся, если осталось менее 182,5 суток до истечения сертификата УЦ или службы, изменился требуемый набор имён либо в Secret отсутствует сертификат УЦ. Разрешённые имена и адреса указываются в расширении сертификата Subject Alternative Name (SAN).

Проверка вызывается перед применением конфигурации модуля (`OnBeforeHelm`) и при соответствующих событиях объекта Secret. Отдельного ежедневного задания у общей функции нет. Ошибка разбора сертификата записывается в журнал, но сама по себе не гарантирует автоматическую замену: код избегает бесконечного повторения генерации.

Результат используется для формирования объекта Secret и настроек доверия клиентов. Например, в настройках вызываемой API-сервером службы заполняется поле `caBundle` — набор сертификатов УЦ, которым API должен доверять. Такие вызываемые службы часто называются webhook: они проверяют или преобразуют объекты Kubernetes при их создании и изменении. Объект APIService описывает подключение расширения API; CRD — описание дополнительного типа объекта Kubernetes.

Обновление завершено только тогда, когда **новую пару и новые настройки доверия применили работающие процессы**. Изменение объекта Secret само по себе этого не доказывает. Одни компоненты перечитывают файлы, другим нужен перезапуск.

Этот УЦ проверяет клиентов и не является серверным сертификатом каждого proxy |

## 6. Как учитываются остальные компоненты DKP

Prometheus, Alertmanager, Grafana, службы экспорта метрик, Loki, log-shipper, kube-proxy, descheduler, chrony, контроллеры облачных провайдеров и другие модули могут принимать HTTPS через kube-rbac-proxy. Тогда рассматривается сертификат этого прокси, а не отдельный УЦ каждого продукта. Файл `module-coverage.csv` показывает, в каких публичных шаблонах обнаружен такой путь.

В некоторых путях мониторинга явно задано `insecureSkipVerify: true` — отключение проверки сертификата сервера. Если заменить серверный сертификат на корпоративный, но оставить эту настройку, клиент не начнёт проверять корпоративный УЦ и имя сервера. Изменить файл сертификата и включить доказуемую проверку подлинности сервера — две самостоятельные работы.

У модулей без обнаруженного генератора может использоваться незашифрованный HTTP, служебная учётная запись для API, обращение к внешнему HTTPS-серверу либо логика сторонней программы. По одному имени модуля нельзя назначить ему собственный сертификат. Анализ исходников не доказывает отсутствие сертификатов в закрытом или внешнем модуле; фактический перечень требует данных установленного кластера.

Источник примера: [настройка проверки TLS при сборе метрик Prometheus](https://github.com/deckhouse/deckhouse/blob/v1.73.4/modules/300-prometheus/templates/prometheus/servicemonitor.yaml).

## 7. Ответы на основные замечания ИБ

| Замечание | Что показал анализ |
| --- | --- |
| Неконтролируемый выпуск | Есть несколько локальных процессов, имеющих право подписи. Часть запросов проходит через объекты `CertificateSigningRequest`, часть подписывается без создания таких объектов. Единого реестра всех выдач в корпоративном УЦ нет |
| Нецелевое использование | УЦ Kubernetes, etcd и доверенных прокси выполняют разные роли. Для клиентского входа в API имя владельца и группы из сертификата влияют на права. Доверие ко всему корпоративному корню может расширить круг принимаемых клиентов |
| Непонятен механизм отзыва | В штатной аутентификации Kubernetes по клиентскому сертификату нет отзыва отдельного сертификата по списку отзыва или сетевой проверке статуса. OpenVPN явно проверяет список отозванных сертификатов; это свойство нельзя переносить на API и остальные службы |
| Слишком длительный срок | Общая функция InternalTLS создаёт сертификаты примерно на 10 лет. В некоторых специальных программах нет найденного таймера заблаговременной замены |
| Сбой обновления | Заменить нужно не только объект Secret или файл, но и настройки доверия и данные работающих процессов. Потеря Secret может привести к созданию другого локального УЦ |

Источники: [проверка клиентских сертификатов Kubernetes](https://kubernetes.io/docs/reference/access-authn-authz/authentication/#x509-client-certs), [проверка списка отзыва в OpenVPN](https://github.com/deckhouse/deckhouse/blob/v1.73.4/modules/500-openvpn/templates/openvpn/configmap.yaml).

Требование корпоративных сертификатов необходимо применить к каждой роли и каждому процессу выпуска. Смена одного общего издателя влияет только на явно использующие его сертификаты. Варианты перехода приведены во втором документе.
