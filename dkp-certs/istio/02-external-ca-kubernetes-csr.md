## 1. Как устроен вариант

Корпоративный удостоверяющий центр (УЦ; в настройках также обозначается CA) подписывает каждый сертификат приложения Istio. Ключ подписывающего УЦ остаётся вне Kubernetes, при необходимости в аппаратном модуле защиты ключей HSM. Идентичность приложения — его служебное имя, указываемое в сертификате. Служба istiod проверяет заявителя и передаёт запрос внешнему подписанту через программный интерфейс Kubernetes — API.

В поде Kubernetes — объекте, объединяющем контейнеры приложения, — рядом с приложением установлен дополнительный контейнер Istio. Такой режим называется sidecar. Агент получает сертификаты, а сетевой прокси Envoy использует их для защиты соединений. TLS — протокол защиты соединения; mTLS означает взаимную проверку сертификатов клиентом и сервером.

Архитектура соответствует схеме `02-external-ca-kubernetes-csr.vsdx`. Она подходит при запрете хранения подписывающего ключа в кластере или требовании корпоративной регистрации каждой выдачи. Поддержку необходимых изменений в Deckhouse 1.73.4 CSE PRO нужно подтвердить с вендором; установленный кластер не обследовался.

## 2. Компоненты и объекты Kubernetes

| Компонент или объект | Назначение |
| --- | --- |
| Агент Istio и прокси Envoy в поде | Создают ключ и запрос, получают и применяют сертификат |
| Istiod — управляющая служба Istio | Проверяет заявителя и запрашиваемую идентичность, создаёт запрос Kubernetes |
| Объект `CertificateSigningRequest` | Хранит запрос на подписание сертификата — CSR, Certificate Signing Request; выбранного подписанта, решение о разрешении выдачи и результат |
| Процесс разрешения выдачи | Проверяет выполнение согласованных условий; может выполняться istiod или отдельной программой |
| Внешний подписывающий контроллер, он же коннектор УЦ | Отслеживает запросы, обращается в корпоративный УЦ и записывает результат в Kubernetes |
| Корпоративный УЦ | Проверяет полномочия подключения и правила выдачи, подписывает и регистрирует сертификат |

`CertificateSigningRequest` — объект API Kubernetes, а не файл на диске и не просто текст CSR. В его поле `spec.signerName` указывается логическое имя подписанта. Это не сетевой адрес УЦ. Коннектор содержит настройки обращения к настоящему программному интерфейсу корпоративного УЦ. Готовый сертификат записывается в поле `status.certificate` этого объекта. [Описание API запросов Kubernetes](https://kubernetes.io/docs/reference/access-authn-authz/certificate-signing-requests/).

На схеме коннектор расположен внутри кластера; допустим и внешний контроллер с доступом к API и нужными правами. Встроенного API запросов недостаточно для произвольного корпоративного УЦ: нужна совместимая программа обработки. Компоненты istio-csr и cert-manager для этого конкретного пути не обязательны. [Внешняя подпись Istio через Kubernetes](https://istio.io/latest/docs/tasks/security/cert-management/custom-ca-k8s/).

## 3. Как проходит выдача

До первого запроса настраиваются внешний режим подписи, подписант, права и сеть коннектора. Проверяющие стороны заранее получают доверенный корневой сертификат. Цепочка, возвращённая вместе с новым сертификатом, не заменяет первоначальную настройку доверия.

1. Агент создаёт собственный ключ и текст запроса CSR. Закрытый ключ приложения остаётся в поде.
2. Istiod проверяет заявителя. Приложение действует от имени объекта Kubernetes `ServiceAccount` — служебной учётной записи; запрашиваемая идентичность должна соответствовать её полномочиям.
3. Istiod создаёт объект `CertificateSigningRequest`. Уполномоченный процесс разрешает выдачу в соответствии с политикой. В технической документации этот шаг называется approval.
4. Коннектор получает содержимое разрешённого запроса и передаёт его корпоративному УЦ.
5. УЦ проверяет правила, подписывает сертификат и возвращает цепочку. Коннектор проверяет результат и записывает его в объект запроса.
6. Istiod получает результат и возвращает агенту. Агент передаёт сертификат Envoy через SDS — внутренний механизм доставки секретов Secret Discovery Service.

Стрелка от API к коннектору на схеме означает получение события и данных запроса. Постоянное соединение для наблюдения за событиями открывает сам контроллер. Зелёные стрелки показывают возврат сертификата, а не передачу закрытого ключа.

Корпоративный УЦ должен поддерживать идентификаторы служб SPIFFE: стандарт, по которому Istio указывает идентичность приложения. Идентификатор вида `spiffe://<домен>/ns/<пространство-имён>/sa/<учётная-запись>` помещается в дополнительные имена сертификата — расширение Subject Alternative Name (SAN). Нужны подходящие назначения взаимной проверки TLS и автоматическая выдача без ручного согласования каждого пода. Обычные правила сертификата внешнего веб-сервера могут не подойти.

## 4. Когда поступают запросы

Первый сертификат требуется каждому новому поду с дополнительным контейнером Istio. Далее агент автоматически обновляет его. Перезапуск агента с потерей пары ключ/сертификат также может вызвать новую выдачу. Перезапуск только контейнера приложения при работающем прокси сам по себе новой выдачи не требует.

Для расчётов приняты стандартные значения: сертификат действует 24 часа, запрос обновления отправляется примерно через 12 часов. Фактические сроки могут отличаться из-за настроек агента и правил УЦ. При обычном обращении приложения к другому сервису используется уже полученный сертификат.

Увеличение срока уменьшает нагрузку выдачи, но продлевает возможное использование украденного ключа приложения. Этот выбор согласовывается с ИБ. [Срок действия в Istio](https://istio.io/latest/about/faq/security/), [параметры агента](https://github.com/istio/istio/blob/master/pilot/cmd/pilot-agent/options/options.go).

## 5. Риск: неконтролируемый выпуск

**Сценарий.** Из-за ошибки проверки либо взлома istiod/коннектора в УЦ поступает запрос чужой идентичности. Наличие одного центрального сервера подписи не доказывает проверку полномочий.

На стороне УЦ нужны отдельные правила для Istio: разрешённый домен доверия, типы имён и назначения, конечный сертификат без права подписи (`CA:FALSE`) и максимальный срок. Учётная запись коннектора не должна выбирать посторонние правила или выпускать сертификат УЦ. Проверяется и прямое обращение к УЦ в обход коннектора.

Istiod и коннектор должны проверять заявителя, принадлежность SPIFFE-имени служебной учётной записи, доверенного создателя объекта запроса и условия разрешения выдачи. Автоматическая отметка `Approved` — «выдача разрешена» — не является проверкой, если ставится любому запросу.

УЦ обычно не знает напрямую о каждом поде: он доверяет программе проверки заявителя. В англоязычной документации такую роль называют Registration Authority (RA), то есть регистрационный центр. Если скомпрометированная программа вправе заявлять любое разрешённое имя, риск подделки этого имени сохраняется даже при строгих правилах УЦ. Для усиления нужна независимая проверка полномочий, а не предположение, что её уже выполняет УЦ.

Корпоративный реестр должен связывать запрос, издателя, серийный номер, имена и срок. Привязку к поду и ServiceAccount обеспечивает интеграция. Объекты запросов Kubernetes могут удаляться и не заменяют постоянный реестр. Проверить нужно также прямые и повторные выдачи.

В варианте с промежуточным УЦ корпоративная система заранее ограничивает переданные полномочия. Здесь добавляется возможность применять корпоративные правила и учитывать результат при **каждой подписи**, если обходной путь отсутствует.

## 6. Риск: нецелевое использование

**Сценарий.** Выданный для Istio сертификат принимается внешним сервисом или используется для другого кластера.

Для независимой сети сервисов Istio утверждается уникальный домен доверия — поле `trustDomain`. В правила выдачи включаются этот домен, формат SPIFFE-имени, необходимые назначения и предел срока. Запрос чужого домена, недопустимого доменного имени, IP-адреса или имени владельца должен отклоняться самим УЦ либо независимой проверенной политикой.

Принимающий сервис должен разрешать конкретные служебные учётные записи и операции. Для этого в Istio задаются объекты `AuthorizationPolicy` — политики доступа к сервисам. [Авторизация Istio](https://istio.io/latest/docs/reference/config/security/authorization-policy/).

Внешние корпоративные системы, доверяющие тому же корню, должны отдельно отклонять сертификат Istio для своих способов входа. Назначения `clientAuth` и `serverAuth` означают проверку клиента и сервера, но используются многими продуктами и не обозначают «только Istio». Уникальное имя само по себе не заставляет внешнюю систему отвергнуть сертификат.

Правила УЦ ограничивают выдачу для посторонней цели. Проверки принимающей стороны ограничивают применение уже выданного сертификата. Если внешняя система продолжает принимать его из-за широкого доверия, риск остаётся.

## 7. Риск: отзыв в УЦ не применяется прокси

**Сценарий.** Сертификат помечен отозванным в корпоративном УЦ, но Envoy не получает или не проверяет эту информацию.

Для работающего отзыва нужно подтвердить полный путь: серийный номер попадает в сведения об отзыве, они доставляются всем принимающим прокси, применяются и вызывают отказ TLS с ещё действующим по сроку сертификатом. Проверяются период доставки и поведение при недоступном источнике.

CRL — список отозванных сертификатов; OCSP — протокол запроса статуса сертификата. Их наличие в УЦ не доказывает использование в Istio. Например, распространение файла `ca-crl.pem` для подключаемых УЦ добавлено в исходный Istio 1.27. Это не подтверждает функцию в установленном CSE PRO или выбранном пути запросов Kubernetes. До испытания отзыв по серийному номеру считается **необеспеченным**. [Изменения Istio 1.27](https://istio.io/latest/news/releases/1.27.x/announcing-1.27/change-notes/).

### 7.1. Украден сертификат и ключ приложения

Прекращаются новые выдачи скомпрометированному субъекту; принимающие сервисы блокируют его идентичность. Такая блокировка затрагивает все поды одной ServiceAccount и является ограничением доступа, а не отзывом одного серийного номера. При подтверждённой поддержке применяется и отзыв в УЦ.

Удаление объекта `CertificateSigningRequest` и перезапуск пода не аннулируют украденную копию. Без проверки отзыва остаются блокировка доступа и ожидание окончания срока при прекращении новых выдач. Уже установленные соединения требуют отдельного прекращения. Время блокировки измеряется до отказа всех затронутых принимающих сторон.

### 7.2. Взломана программа проверки или коннектор

Нужно остановить выдачи через скомпрометированный путь, найти выданные сертификаты в корпоративном реестре и прекратить их принятие. Отмена учётных данных коннектора не отменяет уже выданные сертификаты. Остановка выдачи затронет и легитимные приложения; регламент должен учитывать это последствие.

### 7.3. Взломан подписывающий УЦ

Старая цепочка должна перестать приниматься всеми проверяющими сторонами: через проверенный запрет издателя, отзыв либо смену доверенного корня. Замена только промежуточного сертификата при прежнем корне этого не гарантирует. Масштаб определяется всеми системами, доверяющими этому УЦ.

Внешний УЦ упрощает регистрацию выдач и оформление отзыва, но сам по себе не обеспечивает применение отзыва в Istio. Если требуется прекратить использование быстрее, чем может истечь сертификат, нужен доказанный механизм отзыва или блокировки.

## 8. Нагрузка и недоступность внешнего УЦ

### 8.1. Средняя и пиковая нагрузка

Для стабильного числа `N` работающих агентов и обновления раз в 12 часов оценка обращений за подписью:

```text
В сутки ≈ 2 × N + S + повторные попытки
```

`S` — дополнительные первые выдачи при создании и замене подов. При частой замене подов точнее считать время жизни каждого агента. Повторная попытка не обязательно заканчивается новой выдачей.

| Сценарий | Оценка без повторов |
| --- | --- |
| 10 000 постоянно работающих агентов | Около 20 000 выдач в сутки на обновление |
| Средняя нагрузка только от этих обновлений | Около 0,23 выдачи в секунду |
| Запуск 10 000 новых подов за 60 секунд | Около 167 первоначальных выдач в секунду |

Проблему определяет пик: массовое обновление приложений, восстановление после аварии, увеличение числа экземпляров или одновременный перезапуск агентов. Разнесённые первые выдачи не гарантируют разнесения последующих повторов.

Число выпусков не равно числу сетевых вызовов. УЦ может требовать отправку и опрос результата; Kubernetes создаёт и обновляет объекты запросов и рассылает события. Поэтому отдельно оцениваются УЦ, коннектор, сервер API и база etcd, хранящая состояние Kubernetes.

При условной мощности УЦ 20 подписей в секунду 10 000 запросов требуют не менее 500 секунд даже без фоновых операций. Если время ожидания клиентов меньше задержки очереди, повторы усиливают перегрузку. Ограничения задаются также аппаратным модулем ключей, лицензией, квотами и записью аудита.

### 8.2. Что происходит при отказах

| Отказ | Результат |
| --- | --- |
| Недоступны УЦ, его программный интерфейс или сеть | Первая выдача и обновление не завершаются |
| Отказал коннектор или истекли его учётные данные | Запросы остаются без результата или завершаются ошибкой |
| Нет разрешения выдачи или нужных прав Kubernetes | Запрос не проходит проверку либо обработку |
| Перегружены API или etcd | Растёт время записи запросов и получения результата |
| Исчерпана мощность или квота УЦ | Очередь, превышение времени ожидания и повторы |
| Выдана неподходящая цепочка | Сертификат не применяется или не принимается участниками соединений |

Новый под без сертификата не может полноценно участвовать во взаимно защищённом обмене. Его готовность к работе зависит от настроек приложения и прокси; не обязательно останавливаются все процессы пода.

Работающие прокси используют текущие сертификаты до истечения срока. Затем новые соединения начинают отказывать. Установленные соединения могут продолжить работу до разрыва, но это не гарантия доступности. Время на восстановление определяется минимальным оставшимся сроком, а не гарантированными 24 часами.

### 8.3. Как снизить риск

1. Согласовать максимальный поток запросов и допустимую задержку с владельцем корпоративного УЦ, включая восстановление после аварии.
2. Испытать всю цепочку под нагрузкой. Измерять время до получения пригодного сертификата, а не только операцию подписи.
3. Резервировать УЦ, сеть и коннектор. Несколько экземпляров коннектора не должны без необходимости подписывать один запрос повторно.
4. Ограничить число одновременных запросов, очередь и повторы. Между повторами увеличивать задержку и добавлять случайный сдвиг. При поддержке УЦ повтор одного запроса не должен бесконтрольно создавать новые выдачи.
5. Выполнять массовые обновления и восстановление подов постепенно, сохраняя мощность для продления уже работающих приложений.
6. Контролировать скорость, ошибки, задержки, возраст очереди, ожидающие запросы и минимальный остаток срока. Сигнал должен оставлять время для восстановления.

## 9. Что предъявить ИБ для принятия решения

| Замечание | Подтверждение | Остаточный риск |
| --- | --- | --- |
| Неконтролируемый выпуск | УЦ отклоняет чужие имена, запрос сертификата УЦ и лишний срок даже при прямом вызове; каждая выдача есть в реестре | Доверенная программа проверки может подделать разрешённые имена, если независимой проверки нет |
| Нецелевое использование | Посторонние правила выдачи недоступны; внешние системы отклоняют сертификат Istio для своих задач | Широкое доверие принимающей системы не исправляется одним выбором места подписи |
| Отзыв | Ещё действующий отозванный сертификат отклоняется всеми прокси в измеренный срок; текущие соединения прекращаются | Запись только в УЦ не обеспечивает отзыв |
| Массовые запросы и отказ УЦ | Измерены поток, очередь, задержка и восстановление; обновление работает при согласованной деградации | Внешняя цепочка остаётся зависимостью запуска и обновления сертификатов |
| Дополнительное ПО CSE PRO | Вендор подтверждает поддержку режима и выбранного коннектора | Возможность исходного Istio сама по себе не подтверждает поддержку сертифицированной поставкой |

Вариант даёт центральный учёт каждой подписи и позволяет оставить ключ УЦ вне кластера. Он требует достаточной производительности и доступности. Целевое использование и фактическое применение отзыва доказываются отдельно.
