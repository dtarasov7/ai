# Техническое задание на разработку архитектурных схем трёхузлового кластера VictoriaMetrics

## 1. Общее описание архитектуры

Необходимо разработать 5 отдельных архитектурных схем, описывающих взаимодействие компонентов трёхузлового кластера VictoriaMetrics, маршрутизацию запросов, балансировку нагрузки и механизмы обеспечения высокой доступности (HA).

Используемая версия VictoriaMetrics — 1.130.0.

Кластер состоит из трёх узлов. На каждом узле размещается по одному экземпляру следующих компонентов:

- `vmauth` — аутентификация, авторизация и HTTP-маршрутизация.
- `vminsert` — приём и распределение записываемых метрик.
- `vmselect` — выполнение запросов чтения метрик.
- `vmstorage` — хранение метрик.
- `vmalert` — вычисление alerting и recording rules.
- `Alertmanager` — обработка, группировка и доставка уведомлений.

Все три экземпляра Alertmanager объединены в отдельный HA-кластер с использованием gossip-протокола.

### 1.1. Размещение компонентов

| Компонент             | Узел 1    | Узел 2    | Узел 3    |
| --------------------- | --------- | --------- | --------- |
| IP-адрес              | 10.0.0.11 | 10.0.0.12 | 10.0.0.13 |
| vmauth                | 8427      | 8427      | 8427      |
| vminsert              | 8480      | 8480      | 8480      |
| vmselect              | 8481      | 8481      | 8481      |
| vmstorage (HTTP)      | 8482      | 8482      | 8482      |
| vmalert               | 8880      | 8880      | 8880      |
| Alertmanager (HTTP)   | 9093      | 9093      | 9093      |
| Alertmanager (gossip) | 9094      | 9094      | 9094      |

Дополнительно используется виртуальный адрес:

`VIP: 10.0.0.100`

Его доступность обеспечивается Keepalived (VRRP), а балансировка входящих соединений — IPVS/LVS в режиме Direct Routing (DR).

### 1.2. Принцип балансировки входящего трафика

Keepalived обеспечивает наличие VIP на одном из узлов, выполняющем роль активного IPVS-директора.

При поступлении нового соединения:

1. Клиент обращается к VIP `10.0.0.100`.
2. Активный IPVS-директор выбирает один из трёх экземпляров `vmauth`.
3. Соединение передаётся выбранному узлу в режиме Direct Routing без изменения IP-адреса назначения.
4. `vmauth` проверяет учётные данные и маршрутизирует HTTP-запрос на соответствующий backend.
5. Ответ возвращается клиенту непосредственно через выбранный узел, минуя IPVS-директор.

Необходимо предусмотреть правильную конфигурацию VIP на loopback-интерфейсах real servers, подавление нежелательных ARP-ответов и проверки доступности `vmauth`.

На уровне IPVS балансируются TCP-соединения, на уровне `vmauth` — HTTP-запросы. Это два независимых уровня балансировки.

### 1.3. Единый визуальный стиль

Все схемы должны иметь одинаковое расположение узлов:

- Узел 1 — слева.
- Узел 2 — в центре.
- Узел 3 — справа.

На каждом узле показывается ровно один экземпляр каждого участвующего в конкретной схеме компонента.

Рекомендуется использовать единую цветовую кодировку:

| Цвет соединения | Значение                                    |
| --------------- | ------------------------------------------- |
| Синий           | Входящий HTTP-трафик через VIP              |
| Зелёный         | Чтение метрик                               |
| Красный         | Запись метрик                               |
| Фиолетовый      | Административный доступ и управление        |
| Оранжевый       | Уведомления и взаимодействие с Alertmanager |

На всех схемах необходимо явно различать:

- Балансируемые HTTP-запросы.
- Точечную маршрутизацию к определённому компоненту.
- Прямые межмодульные TCP-соединения.
- Служебные соединения HA.
- Сценарии отказов и резервные пути.

## 2. Схема №1 — Внутрикластерный обмен данными

### Назначение

Показать взаимодействие `vminsert`, `vmselect` и `vmstorage` внутри кластера VictoriaMetrics без внешних клиентов и без участия HTTP-балансировки.

### Компоненты

На каждом из трёх узлов:

- Один `vminsert`.
- Один `vmselect`.
- Один `vmstorage`.

На данной схеме не показывать `vmauth`, `vmalert`, Alertmanager, Grafana, Prometheus и VIP.

### Связи

Запись метрик:

Каждый `vminsert` соединяется со всеми тремя `vmstorage` через TCP 8400.

```
vminsert-1 ──┬──> vmstorage-1
             ├──> vmstorage-2
             └──> vmstorage-3

vminsert-2 ──┬──> vmstorage-1
             ├──> vmstorage-2
             └──> vmstorage-3

vminsert-3 ──┬──> vmstorage-1
             ├──> vmstorage-2
             └──> vmstorage-3
```

Связи показывают возможность записи на каждый экземпляр `vmstorage`. Это не означает обязательного дублирования каждой записи во все три хранилища: фактическое размещение определяется шардированием и `-replicationFactor`.

Чтение метрик:

Каждый `vmselect` соединяется со всеми тремя `vmstorage` через TCP 8401.

```
Каждый из 3 vmselect
          |
          | TCP 8401
          v
Все 3 экземпляра vmstorage
```

Для обоих типов соединений используется внутренний протокол VictoriaMetrics. `vmauth` не участвует в данном обмене.

### Отображаемые сценарии HA

| Отказ           | Ожидаемое поведение                                      |
| --------------- | -------------------------------------------------------- |
| `vmstorage-1`   | Новые записи перераспределяются на доступные `vmstorage` |
| `vmstorage-1`   | `vmselect` читает данные с доступных хранилищ            |
| Один `vminsert` | Другие `vminsert` сохраняют возможность приёма метрик    |
| Один `vmselect` | Другие `vmselect` продолжают выполнять запросы           |

Для отказа `vmstorage` необходимо показать различие между работой с репликацией и без неё.

При `-replicationFactor=1` часть исторических метрик может оказаться временно недоступна.

При `-replicationFactor=2` и корректной настройке чтения оставшиеся узлы могут сохранить доступность реплицированных данных после отказа одного `vmstorage`.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://docs.victoriametrics.com\&sz=32)

docs.victoriametrics.com



Ключевой смысл схемы: все экземпляры `vminsert` и `vmselect` работают со всем кластером `vmstorage`, а не только с хранилищем своего узла.

## 3. Схема №2 — Чтение метрик внешней Grafana

### Назначение

Показать полный путь запросов чтения метрик из Grafana в кластер VictoriaMetrics, включая балансировку на двух уровнях.

### Компоненты

- Внешняя Grafana.
- VIP `10.0.0.100`.
- Keepalived (VRRP).
- IPVS/LVS Direct Routing.
- Три экземпляра `vmauth`.
- Три экземпляра `vmselect`.
- Три экземпляра `vmstorage`.

### Последовательность обработки запроса

Grafana

HTTP / PromQL

VIP 10.0.0.100

Keepalived + IPVS/LVS-DR

vmauth-1

vmauth-2

vmauth-3

Каждый vmauth балансирует HTTP-запросы на все три vmselect

vmselect-1

vmselect-2

vmselect-3

Каждый vmselect обращается ко всем трём vmstorage

vmstorage-1

vmstorage-2

vmstorage-3

Каждый экземпляр `vmauth` должен иметь в своей конфигурации три backend-адреса:

```
10.0.0.11:8481
10.0.0.12:8481
10.0.0.13:8481
```

Для выбранного `vmselect` все три `vmstorage` являются источниками данных.

### Сценарии HA

- Отказ одного `vmauth`: IPVS направляет новые соединения на оставшиеся экземпляры.
- Отказ одного `vmselect`: `vmauth` продолжает использовать доступные backend.
- Отказ одного `vmstorage`: `vmselect` продолжает чтение с учётом доступности и репликации данных.
- Отказ узла с активным VIP: Keepalived переносит VIP на другой узел.

На рисунке важно продемонстрировать, что `vmauth-1` может отправить запрос в `vmselect-2` или `vmselect-3`.

Ключевой смысл схемы: двухуровневая балансировка устраняет привязку клиентского запроса к конкретному узлу обработки.

## 4. Схема №3 — Запись метрик внешним Prometheus

### Назначение

Показать поступление метрик по протоколу Prometheus Remote Write и их распределение внутри кластера VictoriaMetrics.

### Компоненты

- Внешний Prometheus или vmagent.
- VIP `10.0.0.100`.
- Keepalived и IPVS/LVS-DR.
- Три экземпляра `vmauth`.
- Три экземпляра `vminsert`.
- Три экземпляра `vmstorage`.

### Последовательность обработки

```
Prometheus
    |
    | HTTP Remote Write
    v
VIP 10.0.0.100
    |
    | IPVS/LVS Direct Routing
    v
Один из трёх vmauth
    |
    | HTTP-балансировка
    v
Один из трёх vminsert
    |
    | TCP 8400
    v
Кластер из трёх vmstorage
```

Каждый `vmauth` должен иметь три backend-адреса:

```
10.0.0.11:8480
10.0.0.12:8480
10.0.0.13:8480
```

Каждый `vminsert` поддерживает соединения со всеми тремя `vmstorage`.

На рисунке обязательно показать:

- Ровно три экземпляра `vminsert` на весь кластер.
- Возможность выбора любого `vminsert` каждым `vmauth`.
- Связи каждого `vminsert` со всеми тремя `vmstorage`.
- Прямой возврат ответа от выбранного узла к Prometheus в режиме DR.

### Сценарии HA

| Отказ                  | Поведение                                |
| ---------------------- | ---------------------------------------- |
| Один `vmauth`          | IPVS исключает недоступный real server   |
| Один `vminsert`        | `vmauth` использует доступные экземпляры |
| Один `vmstorage`       | `vminsert` перераспределяет новые записи |
| Активный IPVS-директор | Keepalived переключает VIP               |

Prometheus должен иметь возможность повторной отправки временно не принятых данных средствами Remote Write.

Ключевой смысл схемы: приём метрик распределён между всеми `vminsert`, которые независимо работают с кластером хранения.

## 5. Схема №4 — Административный доступ к конкретным компонентам

### Назначение

Показать доступ администраторов к GUI, status, metrics и диагностическим HTTP-интерфейсам каждого модуля на любом из трёх узлов.

### Компоненты

- Внешние администраторы.
- VIP `10.0.0.100`.
- Keepalived и IPVS.
- Три `vmauth`.
- На каждом узле:
  - `vminsert`
  - `vmselect`
  - `vmstorage`
  - `vmalert`
  - `Alertmanager`

### Принцип маршрутизации

На первом уровне IPVS выбирает один из трёх `vmauth`.

На втором уровне выбранный `vmauth` направляет запрос строго на конкретный компонент указанного узла.

Балансировка между однотипными backend в этом сценарии не используется.

Например:

| Внешний путь           | Целевой компонент |
| ---------------------- | ----------------- |
| `/node1/vmselect/`     | `10.0.0.11:8481`  |
| `/node2/vminsert/`     | `10.0.0.12:8480`  |
| `/node3/vmstorage/`    | `10.0.0.13:8482`  |
| `/node1/vmalert/`      | `10.0.0.11:8880`  |
| `/node2/alertmanager/` | `10.0.0.12:9093`  |

Все три `vmauth` должны иметь одинаковую конфигурацию адресной маршрутизации, позволяющую направлять запрос к любому указанному компоненту.

При использовании URL-префиксов необходимо корректно настроить их обработку и генерацию ссылок в UI компонентов.

### Сценарии HA

Отказ vmauth: администратор продолжает обращаться к конкретному компоненту через другой экземпляр `vmauth`.

Отказ целевого модуля: администратор получает ошибку недоступности именно запрошенного компонента. Автоматическая замена его другим не производится.

Отказ всего узла: доступ к компонентам этого узла прекращается, но административные интерфейсы оставшихся узлов доступны.

Отказ активного IPVS-директора: Keepalived переключает VIP на резервный узел.

Ключевой смысл схемы: балансировка входящих соединений не изменяет адресность административных запросов.

## 6. Схема №5 — vmalert и кластер Alertmanager

### Назначение

Показать отказоустойчивую работу подсистемы алертинга, включающей вычисление правил, чтение метрик, запись recording rules, передачу алертов и HA-кластер Alertmanager.

### 6.1. Компоненты

На каждом узле:

- `vmalert`
- `vmauth`
- `vmselect`
- `vminsert`
- `Alertmanager`

Дополнительно:

- VIP `10.0.0.100`.
- Keepalived.
- IPVS/LVS Direct Routing.

Все три Alertmanager соединены друг с другом через gossip-протокол и образуют единый кластер HA.

### 6.2. Получение данных для вычисления правил

Каждый `vmalert` использует VIP `10.0.0.100` в качестве точки доступа к метрикам.

Путь запроса:

```
vmalert-1 ─┐
vmalert-2 ─┼──> VIP ──> IPVS ──> vmauth ──> vmselect
vmalert-3 ─┘                           балансировка
```

При этом:

- IPVS распределяет соединения между тремя `vmauth`.
- Каждый `vmauth` балансирует HTTP-запросы между всеми тремя `vmselect`.
- Каждый `vmselect` работает со всеми тремя `vmstorage`.

Для получения метрик используется параметр `-datasource.url`, для восстановления состояния алертов — `-remoteRead.url`.

При отказе одного `vmselect` запросы направляются на доступные экземпляры.

### 6.3. Запись результатов recording rules

Результаты recording rules сохраняются в VictoriaMetrics через `vminsert`.

Путь записи:

```
vmalert
   |
   | -remoteWrite.url
   v
VIP 10.0.0.100
   |
   v
IPVS → один из vmauth
             |
             v
        один из vminsert
             |
             v
         vmstorage
```

Каждый `vmauth` должен иметь все три `vminsert` в списке backend.

При отказе одного `vminsert` запись перенаправляется на оставшиеся экземпляры.

Параметр `-remoteWrite.url` является опциональным для работы самого `vmalert`, но необходим, если результаты recording rules и состояние алертов должны сохраняться в VictoriaMetrics.

### 6.4. Передача алертов в Alertmanager

В отличие от обращения к VictoriaMetrics, для передачи алертов не используется VIP и не требуется балансировка через `vmauth`.

Каждый `vmalert` должен отправлять алерты напрямую во все три экземпляра Alertmanager.

```
vmalert-1 ──┬──> Alertmanager-1
            ├──> Alertmanager-2
            └──> Alertmanager-3

vmalert-2 ──┬──> Alertmanager-1
            ├──> Alertmanager-2
            └──> Alertmanager-3

vmalert-3 ──┬──> Alertmanager-1
            ├──> Alertmanager-2
            └──> Alertmanager-3
```

Таким образом, необходимо отобразить 9 логических направлений HTTP-доставки алертов — от каждого из трёх `vmalert` ко всем трём Alertmanager на порт 9093.

На каждом `vmalert` задаются следующие параметры:

```
-notifier.url=http://10.0.0.11:9093 \
-notifier.url=http://10.0.0.12:9093 \
-notifier.url=http://10.0.0.13:9093
```

Штатный `vmalert` поддерживает несколько адресов Alertmanager и отправляет одинаковые алерты всем настроенным получателям.&#x20;

### 6.5. Взаимодействие Alertmanager между собой

Все три Alertmanager работают одновременно и формируют HA-кластер.

Каждый Alertmanager обменивается служебным состоянием с двумя другими экземплярами через gossip-протокол.

```
              Alertmanager-1
               /         \
              /           \
             /             \
   Alertmanager-2 ───── Alertmanager-3

          TCP/UDP 9094
```

На схеме показать три двунаправленные связи:

- Alertmanager-1 ↔ Alertmanager-2.
- Alertmanager-1 ↔ Alertmanager-3.
- Alertmanager-2 ↔ Alertmanager-3.

Взаимодействие происходит напрямую, без `vmauth`, VIP и IPVS.

Кластер Alertmanager использует gossip для обмена состоянием подавлений (silences) и журналом отправленных уведомлений (notification log).

Каждый экземпляр получает алерты независимо, но благодаря общему состоянию минимизирует дублирование итоговых уведомлений. При сетевых разделениях возможны дубли: архитектура Alertmanager предпочитает повторную доставку потере критического уведомления.&#x20;

### 6.6. HA-стратегия vmalert

Для трёх экземпляров `vmalert` следует предусмотреть одинаковые наборы alerting rules, чтобы отказ одного экземпляра не останавливал вычисление правил.

При такой конфигурации:

- Все три `vmalert` независимо вычисляют правила.
- Каждый отправляет сработавшие алерты всем трём Alertmanager.
- Alertmanager выполняет дедупликацию совпадающих алертов при согласованных labels.
- При отказе одного `vmalert` два оставшихся продолжают вычисление правил.

Для recording rules необходимо учитывать, что одинаковые правила на нескольких `vmalert` могут приводить к дублирующейся записи результатов. Альтернативой является распределение recording rules между экземплярами с отдельным механизмом переключения при отказе.

Документация VictoriaMetrics описывает использование нескольких идентично настроенных `vmalert` как стандартный подход к HA.&#x20;

### 6.7. Сценарии отказов

| Отказ                   | Ожидаемое поведение                                               |
| ----------------------- | ----------------------------------------------------------------- |
| `vmalert-1`             | Оставшиеся два экземпляра продолжают вычислять идентичные правила |
| `vmauth-1`              | IPVS направляет новые соединения на доступные `vmauth`            |
| `vmselect-1`            | `vmauth` использует остальные `vmselect`                          |
| `vminsert-1`            | `vmauth` использует остальные `vminsert`                          |
| `Alertmanager-1`        | Остальные два продолжают принимать алерты                         |
| Два Alertmanager        | Оставшийся экземпляр может продолжать уведомления                 |
| Потеря gossip-связности | Возможны повторные уведомления                                    |
| Отказ владельца VIP     | Keepalived переключает VIP на резервный узел                      |

При недоступности Alertmanager вычисление правил в `vmalert` продолжается, но возникают ошибки доставки уведомлений.

При недоступности `vmselect` вычисление правил затрудняется или останавливается до восстановления доступа к данным.

При недоступности `vminsert` вычисление alerting rules может продолжаться, но сохранение результатов recording rules и состояния алертов нарушается.

### 6.8. Особенность подключения vmalert к VIP

Для всех трёх `vmalert` рекомендуется использовать общий VIP вместо локальных адресов `vmauth`, чтобы отказ одного экземпляра `vmauth` не создавал зависимость от конкретного узла.

При этом требуется проверить, что обращения от самих узлов — участников IPVS/LVS-DR — к VIP правильно обрабатываются сетевой конфигурацией. В частности, необходимо исключить проблемы маршрутизации и ARP, возникающие при использовании real server в качестве клиента собственного VIP.

На схеме нужно показать этот путь как логическую HA-связь, а в технической документации отдельно зафиксировать требования к её сетевой реализации.

Ключевой смысл схемы: `vmalert` использует VIP и `vmauth` для отказоустойчивого доступа к VictoriaMetrics, но напрямую отправляет алерты всем трём Alertmanager. Alertmanager обеспечивают собственную кластерную отказоустойчивость без внешнего балансировщика в тракте получения алертов.

## 7. Сводная матрица отказоустойчивости

| Отказ компонента             | Кто обеспечивает HA                           | Схемы      |
| ---------------------------- | --------------------------------------------- | ---------- |
| Активный VIP / IPVS-директор | Keepalived / VRRP                             | 2, 3, 4, 5 |
| Один `vmauth`                | IPVS / LVS                                    | 2, 3, 4, 5 |
| Один `vmselect`              | Балансировка vmauth                           | 2, 5       |
| Один `vminsert`              | Балансировка vmauth                           | 3, 5       |
| Один `vmstorage`             | Встроенная логика VictoriaMetrics, репликация | 1, 2, 3    |
| Один `vmalert`               | Несколько экземпляров vmalert                 | 5          |
| Один Alertmanager            | Alertmanager HA / gossip                      | 5          |
| Полный отказ одного узла     | Совокупность всех HA-механизмов               | 1–5        |

Указанные механизмы обеспечивают продолжение работы при соблюдении условий сетевой доступности, правильной конфигурации health checks, достаточного резерва ресурсов и согласованных настроек репликации.

Переключение не гарантирует сохранения уже установленных TCP-соединений и успешного завершения каждого HTTP-запроса, выполнявшегося в момент отказа.

## 8. Перечень итоговых схем

| № | Имя файла                     | Содержание                                                                                          |
| - | ----------------------------- | --------------------------------------------------------------------------------------------------- |
| 1 | `01-cluster-internal-traffic` | Внутренние соединения vminsert, vmselect и vmstorage                                                |

Каждая схема должна быть самостоятельной, иметь заголовок, понятную легенду, адреса и порты компонентов, направления запросов, описание балансировки и основные сценарии HA.

Желательные форматы: SVG для масштабирования и редактирования и PNG для включения в эксплуатационную и проектную документацию.

Итоговый комплект должен показывать пять разных аспектов одной и той же архитектуры, не меняя топологию узлов и не дублируя компоненты на схемах.
