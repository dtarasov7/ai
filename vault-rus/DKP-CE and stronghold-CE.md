Да, такую архитектуру можно реализовать: три сервера, на каждом одновременно работают control plane, worker-компоненты, Ingress и экземпляр Stronghold CE. При этом можно получить отказоустойчивый Kubernetes-кластер и отказоустойчивый Stronghold с Raft Replication Factor = 3.

Это вполне разумная конфигурация для выделенного кластера управления секретами, особенно если он будет обслуживать Ansible, CI/CD и несколько внешних Kubernetes-кластеров через Deckhouse SSI.

Но я бы не рассчитывал ресурсы только по минимальным требованиям Kubernetes: здесь одновременно работают два кворумных хранилища — Kubernetes etcd и Stronghold Raft.

## 2. Сколько ресурсов необходимо на каждый сервер

Для такого сценария я бы рассматривал следующие конфигурации:

| Ресурс на сервер            | Минимум для пилота | Рекомендую для production |
| --------------------------- | ------------------ | ------------------------- |
| CPU                         | 12 vCPU            | 16–24 vCPU                |
| RAM                         | 24–32 ГБ           | 64 ГБ                     |
| Диски                       | 150 ГБ SSD         | 250–500 ГБ NVMe/SSD       |
| Дисковая производительность | 3 000 IOPS         | 5 000+ IOPS               |
| Сеть                        | 1 Гбит/с           | 10 Гбит/с желательно      |
| Количество серверов         | 3                  | 3                         |

Это моя суммарная оценка для совместного размещения Deckhouse, etcd, ingress, системных компонентов и Stronghold, а не официальная минимальная спецификация вендора.

Почему такие цифры:

- Для production master-узла Deckhouse приводит ориентир 8 CPU и 16 ГБ RAM.&#x20;

  [image](https://www.google.com/s2/favicons?domain=https://deckhouse.ru\&sz=32)

  Deckhouse Kubernetes Platform

- Для небольшого кластера Stronghold документация указывает 4–8 ядер и 8–16 ГБ RAM, а также быстрый диск от 3 000 IOPS. Эти характеристики следует учитывать при sizing экземпляров Stronghold.&#x20;

  [image](https://www.google.com/s2/favicons?domain=https://deckhouse.ru\&sz=32)

  Deckhouse Stronghold

- Остальной запас нужен для Ingress, Deckhouse modules, мониторинга, всплесков нагрузки и сохранения работы после потери одного сервера.

Мой выбор для закупки: 3 × (16–24 vCPU, 64 ГБ RAM, 250–500 ГБ NVMe). Если серверы физические, CPU нужно оценивать по реальным ядрам и ожидаемой нагрузке, а не напрямую приравнивать ядра к vCPU.

## 3. Как распределить ресурсы по компонентам

Ориентировочный ресурсный бюджет на один сервер для начального production-развёртывания:

| Компонент                      | CPU        | RAM      |
| ------------------------------ | ---------- | -------- |
| Control plane, etcd, Deckhouse | 4–6 vCPU   | 8–12 ГБ  |
| Stronghold CE (одна реплика)   | 4–6 vCPU   | 8–12 ГБ  |
| Ingress NGINX                  | 1–2 vCPU   | 1–2 ГБ   |
| Мониторинг и системные сервисы | 2–3 vCPU   | 4–8 ГБ   |
| Итого рабочая оценка           | 11–17 vCPU | 21–34 ГБ |

Это бюджет мощности, а не готовые Kubernetes `requests` и `limits`. Поэтому конфигурация 16 vCPU / 32 ГБ достаточно плотная, а 24 vCPU / 64 ГБ даёт более комфортный резерв, в том числе для обслуживания кластера после отказа узла.

## 4. Важные особенности реализации

Размещение: все три узла должны быть master-узлами DKP, с разрешённым запуском дополнительной нагрузки на control plane. Для Ingress потребуются соответствующие `nodeSelector`, `tolerations` и настройки распределения реплик.

Хранилище: по умолчанию модуль Stronghold использует локальное хранилище master-узлов. Для этой схемы я бы не вводил распределённое блочное хранилище только ради Stronghold: Raft уже реплицирует данные между узлами. Диски должны быть быстрыми и надёжными.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://deckhouse.ru\&sz=32)

Deckhouse Stronghold



Входящий трафик: не полагаться на один IP отдельного сервера. Нужна отказоустойчивая точка входа — например, внешний HA-балансировщик либо поддерживаемая DKP-схема VIP/failover.

Резервное копирование: Raft RF=3 не заменяет backup. Нужны резервные копии за пределами этих трёх серверов и проверенная процедура восстановления.

Восстановление и безопасность: в режиме автоматического управления Stronghold модуль сохраняет unseal-key и root-token в Kubernetes Secret `d8-stronghold/stronghold-keys`. Поэтому безопасность Kubernetes control plane и etcd напрямую влияет на безопасность хранилища секретов. Доступ к этому Secret необходимо строго ограничить.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://deckhouse.ru\&sz=32)

Deckhouse



Изоляция: при такой схеме отказ одного узла затрагивает одновременно компоненты DKP, один экземпляр etcd, Stronghold и Ingress. Нужно проверить сценарии потери узла, его возврата и последовательных обновлений.

## 5. Настройка Stronghold CE

Для включения модуля используется следующий базовый манифест:

```

apiVersion: deckhouse.io/v1alpha1
kind: ModuleConfig
metadata:
  name: stronghold
spec:
  version: 1
  enabled: true
  settings:
    management:
      mode: Automatic

```

Это начальная конфигурация; дополнительные настройки зависят от выбранной версии DKP и модуля. В частности, документация модуля указывает требование Deckhouse версии 1.72 и выше и допускает использование Stronghold CE без ключа EE.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://deckhouse.ru\&sz=32)

Deckhouse



При этом термины DKP OSS/Open и DKP CE стоит сверить с конкретным релизом: в новых документах названия редакций изменились, поэтому совместимость модуля и редакции надо проверять по выбранному каналу обновлений.

Размещение: 3 master + worker + ingress, 3 Stronghold Raft replicas, отдельная HA-точка входа.

С запасом под небольшую и среднюю нагрузку и отказ одного сервера. Для окончательного sizing нужны RPS аутентификации/чтения, количество клиентов, набор включённых модулей и требования к мониторингу.

Для выделенного хранилища, у которого основной профиль — KV v2, периодические чтения сертификатов Ansible и загрузка секретов Kubernetes-приложениями, такой конфигурации, вероятно, будет достаточно с существенным запасом. Для больших потоков запросов и частых аутентификаций sizing нужно подтверждать нагрузочными испытаниями.

Ещё один момент: если все остальные Kubernetes-кластеры будут получать секреты из этого Stronghold через SSI, то выделенный трёхузловой кластер становится критической зависимостью для их запуска и обновления. Поэтому я бы особенно тщательно проверил доступность внешнего endpoint и сценарий отказа одного сервера.
