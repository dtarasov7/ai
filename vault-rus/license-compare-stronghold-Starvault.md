# Подробное сравнение лицензирования Deckhouse Stronghold EE и StarVault

Я проверил официальные правила лицензирования обоих продуктов. В них есть существенные различия, особенно для твоей архитектуры с тремя изолированными контурами PROD, LT и TEST.

Главный вывод:

- Stronghold EE лицензируется по двум метрикам: количеству инсталляций и количеству клиентов.
- StarVault лицензируется по количеству клиентов, рассчитываемых как сумма `Entities + Non-Entities`.
- Для обоих продуктов важны идентичности, которые обращаются к секретам, а не количество самих секретов или KV mounts.
- У StarVault есть особое правило: Kubernetes-кластер может считаться одним клиентом при использовании единого ServiceAccount. Это необходимо отдельно проверить для Deckhouse SSI.

| Параметр                    | Stronghold EE                                        | StarVault                                              |

| Основная метрика            | Инсталляции + Clients                                | Clients                                                |

## 2. Что такое Entity

Entity — это логическая идентичность в Vault, которая представляет конкретного пользователя, приложение или технического клиента.

Entity — не секрет, не токен и не Pod.

Например, в Vault есть пользователь `ivan.petrov`, который может аутентифицироваться через LDAP и OIDC.

LDAP

ivan.petrov

OIDC

ivan.petrov

Entity: ivan.petrov

Одна логическая идентичность

Policies

users-personal · infra-read

Две учётные записи, привязанные к одной Entity через Identity Aliases, могут представлять одного клиента.

Но если LDAP и OIDC создают разные Entities, один физический сотрудник может учитываться как два логических клиента. Для HashiCorp Vault это определяется Identity mapping и правилами client count.&#x20;

HashiCorp Developer

+1

.



### Примеры Entities в твоей инфраструктуре

| Источник доступа        | Что может быть Entity                                   |
| ----------------------- | ------------------------------------------------------- |
| Пользователь через OIDC | Один сотрудник                                          |
| Ansible через AppRole   | Одна техническая роль Ansible                           |
| GitLab CI через JWT     | Идентичность проекта или job согласно JWT claims        |
| Kubernetes Auth         | Идентичность, связанная с ServiceAccount и auth mount   |
| Сервис на VM            | Сервисная identity или AppRole                          |
| Deckhouse SSI           | Идентичность, под которой интеграция обращается к Vault |

Важно: наличие объекта Entity в системе и его участие в коммерческом расчёте — не всегда одно и то же. В HashiCorp Vault клиентские метрики учитывают активность за период, а StarVault в опубликованных правилах описывает зарегистрированные сущности. Поэтому период и алгоритм подсчёта следует уточнять отдельно.

## 3. Что такое Non-Entity

Non-Entity — это клиент, который обращается к Vault с токеном, не связанным с явной Entity.

В опубликованных правилах StarVault перечислены временные токены, анонимные запросы, фоновые процессы и разовые подключения.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://api.orionsoft.ru\&sz=32)

api.orionsoft.ru

.



Однако формулировка «временный токен» может вводить в заблуждение.

Не каждый временный Vault Token является Non-Entity.

Сценарий A — Entity

```
Kubernetes ServiceAccount
         ↓
   Kubernetes Auth
         ↓
   Vault Entity
         ↓
Vault Token (TTL 1h)
         ↓
  Чтение секрета
```

Хотя токен временный, он связан с идентичностью. В стандартной модели Vault такой доступ относится к Entity.

Сценарий B — Non-Entity

```
Администратор или сервис
         ↓
   Создаёт Token
         ↓
  Token без Entity
         ↓
   Другой процесс
         ↓
  Чтение секрета
```

Токен не связан с конкретной Entity. При использовании такого токена возникает Non-Entity client.

### Сколько Non-Entities возникает при создании токенов?

Тут есть очень важная тонкость.

Нельзя автоматически утверждать:

`1 Token = 1 Non-Entity client`

В современных версиях HashiCorp Vault неидентифицированные токены могут группироваться по сочетанию Namespace, Identity Alias и Policies. Поэтому 1 000 токенов не обязательно превращаются в 1 000 Non-Entity clients.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://developer.hashicorp.com\&sz=32)

HashiCorp Developer

.



Для StarVault Orion soft даёт рекомендацию: при отсутствии измерений предварительно закладывать Non-Entities в размере 5% от Entities. Но это именно оценочный коэффициент, а не универсальная формула фактического подсчёта.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://api.orionsoft.ru\&sz=32)

api.orionsoft.ru

.



Например:

| Метрика                   | Количество |
| ------------------------- | ---------- |
| Entities                  | 200        |
| Non-Entities, оценочно 5% | 10         |
| Всего Clients             | 210        |

Вендор также рекомендует предусматривать запас до 20% на рост.

## 4. Самое интересное: как лицензируется Kubernetes через Deckhouse SSI

Это, вероятно, наиболее важная часть для выбора между продуктами.

### Stronghold EE

Официальная формулировка Stronghold:

Клиент — приложение, сервис или пользователь с уникальными учётными данными. Реплики одного сервиса и экземпляры, использующие одинаковый набор секретов, рассматриваются как одно приложение.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://deckhouse.ru\&sz=32)

Deckhouse

.



Например:

```
Deckhouse PROD
│
├── payments-api
│   ├── Pod 1
│   ├── Pod 2
│   └── Pod 3
│
├── billing-api
│   ├── Pod 1
│   └── Pod 2
│
└── reporting-api
    ├── Pod 1
    └── Pod 2
```

Если каждому приложению соответствует отдельная аутентификационная идентичность, ориентир — 3 клиента Stronghold, а не 7 Pod.

### StarVault

В официальном документе Orion soft есть особое условие:

Один Kubernetes-кластер учитывается как один клиент при обращении через единый ServiceAccount.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://api.orionsoft.ru\&sz=32)

api.orionsoft.ru

.



Это правило потенциально очень выгодно, но его нельзя без проверки переносить на любую схему SSI.

Есть два возможных варианта архитектуры:

Вариант A — отдельная аутентификация приложений

```
Kubernetes Cluster
├── SA payments-api → Vault
├── SA billing-api  → Vault
└── SA reporting    → Vault
```

У каждого приложения собственная identity и ограниченные ACL.

Это предпочтительно для разграничения прав и аудита.

В модели клиентских identities ориентир — 3 клиента; точное правило StarVault для такой схемы нужно подтвердить.

Вариант B — единая identity интеграции

```
Kubernetes Cluster
       ↓
  Общий ServiceAccount
       ↓
    StarVault
```

Согласно опубликованным условиям StarVault, один Kubernetes-кластер может считаться одним клиентом при таком способе подключения.

Но общая identity может расширить область доступа и ослабить индивидуальную трассировку приложений. Сам по себе Deckhouse SSI не гарантирует выполнение этого условия.

Что нужно проверить у Orion soft: если в Deckhouse SSI используются 100 разных ServiceAccounts и Kubernetes Auth Roles, будет ли это 100 Entities или один Kubernetes client?

Опубликованные правила StarVault одновременно упоминают сервисы и приложения как самостоятельные клиенты и особое правило для Kubernetes-кластера. Поэтому без письменного разъяснения вендора считать 100 приложений одним клиентом нельзя.

Также важно проверить, какие именно Kubernetes credentials использует выбранный режим SSI и поддерживает ли он централизованную identity без нарушения требуемой модели доступа.

## 5. Наложим лицензирование на твои пять KV mounts

Напомню архитектуру — по отдельной инсталляции в каждом контуре:

```
PROD / LT / TEST
│
├── certs/    → Ansible
├── infra/    → Ansible, SRE
├── apps/     → Deckhouse SSI
├── cicd/     → CI/CD
└── users/    → Пользователи
```

Пример расчёта для одного контура:

| Потребитель                    | Условное количество | Как считать                     |
| ------------------------------ | ------------------- | ------------------------------- |
| Ansible automation identities  | 5                   | 5 при независимых identities    |
| SRE / администраторы           | 10                  | 10 активных пользователей       |
| Kubernetes-приложения          | 100                 | До 100 при отдельных identities |
| CI/CD identities               | 20                  | 20 при отдельных идентичностях  |
| Пользователи личного хранилища | 30                  | 30 пользователей                |
| Entities, предварительно       | 165                 | При отсутствии пересечений      |
| Non-Entities                   | 9                   | Примерно 5% от Entities         |
| Всего клиентов StarVault       | 174                 | Оценка, не факт учёта           |

Для Stronghold предварительно можно заложить 165 клиентов и отдельно согласовать обработку Non-Entities.

Если у StarVault подтвердится специальная модель «один Kubernetes-кластер — один клиент» именно для твоего SSI, расчёт может оказаться существенно меньше.

## 6. Как считаются три независимых контура

У тебя регуляторное требование — PROD, LT и TEST изолированы, один экземпляр хранилища не может обслуживать несколько контуров.

Для иллюстрации возьмём условные объёмы:

| PROD   | 165      | 9                        | 174   |
| LT     | 80       | 4                        | 84    |
| TEST   | 50       | 3                        | 53    |

### Stronghold EE

- 3 инсталляции — PROD, LT, TEST.
- Клиентов каждого контура согласно утверждённым правилам подсчёта.
- Техническую поддержку на выбранном уровне.

В доступных презентационных материалах Stronghold указано, что лицензия на инсталляцию включает 50 клиентов и существуют дополнительные клиентские пакеты. Однако актуальность этой пакетной схемы необходимо проверить в коммерческом предложении, поскольку публичная страница лицензирования не фиксирует эти размеры как обязательные условия.&#x20;

## 7. Как посчитать реальное количество Entities и Non-Entities в текущем Vault OSS

Это большое преимущество твоей ситуации: Vault уже развёрнут, поэтому не обязательно оценивать всё вручную.

Можно получить статистику клиентской активности за доступный период:

```
vault operator usage
```

Или использовать API:

```
vault read sys/internal/counters/activity
```

Для просмотра количества зарегистрированных Identity Entities:

```
vault list identity/entity/id
```

Но последний способ показывает зарегистрированные объекты, а не количество активных клиентов за период. Количество Entities в базе не равно автоматически лицензируемому потреблению.

Важные условия:

- Историческая статистика доступна только за период, когда сбор метрик был включён.
- Нужны соответствующие административные права.
- Non-Entity clients должны учитываться отдельно.
- Метрики нужно собрать для каждого Vault-кластера.
- При сравнении необходимо использовать одинаковый период наблюдения.

### Моя рекомендация

Для твоей инфраструктуры следующий практический шаг — снять client usage с трёх существующих Vault OSS, отдельно по Entities и Non-Entities. Эти данные станут проверяемой основой для лицензирования.

А затем попросить Orion soft и «Флант» рассчитать одну и ту же конфигурацию: три изолированных HA-инсталляции, пять KV v2 mounts в каждой, реальные клиентские метрики и Deckhouse SSI.

Особенно рекомендую получить письменный ответ Orion soft про один Kubernetes-кластер с множеством ServiceAccounts. Разница между одним клиентом на кластер и одним клиентом на workload может существенно изменить итоговую стоимость StarVault.
