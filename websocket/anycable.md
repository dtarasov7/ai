Да, AnyCable умеет решать значительную часть этих задач из коробки, а стандартный Action Cable — только базовую часть. Но даже с AnyCable некоторые гарантии надёжности должны оставаться на уровне приложения.

Причём важный нюанс: AnyCable-Go начиная с версии 1.4 поддерживает Reliable Streams и Resumable Sessions — это именно механизмы восстановления пропущенных сообщений и сессий, о которых говорится в твоей цитате.

## 1. Сравнение возможностей

| Возможность                             | Action Cable              | AnyCable-Go                        |
| --------------------------------------- | ------------------------- | ---------------------------------- |
| Автоматический reconnect                | Да, клиентская библиотека | Да                                 |
| Повторная подписка после reconnect      | Да                        | Да                                 |

| Восстановление состояния сессии         | Нет, создаётся заново     | Да, с broker                       |
| Хранение истории сообщений              | Нет                       | Да, ограниченная история           |
| Доставка пропущенных сообщений          | Нет                       | Да, Reliable Streams               |
| Offset / порядковый номер события       | Нет                       | Да                                 |

## 2. Что происходит при обрыве соединения

Предположим, клиент получает события:

```
event_101
event_102
event_103
event_104
event_105
```

После `event_102` соединение разрывается на несколько секунд.

### Стандартный Action Cable

101

102

103

104

105

После reconnect подписка восстановлена, но события 103 и 104 потеряны.

### AnyCable с Reliable Streams

101

102

103

104

105

Обычная доставка

Replay из истории

AnyCable восстанавливает 103 и 104 из короткой истории, если они ещё доступны.

Для этого AnyCable использует `offset` и `epoch` потока. Клиент запоминает последнюю позицию и после переподключения запрашивает пропущенные сообщения.

Если история уже удалена, сервер сообщает об этом через `reject_history`, чтобы приложение могло выполнить полную синхронизацию.&#x20;

## 3. Как включить в AnyCable

На сервере:

```
anycable-go --presets=broker
```

Клиент JavaScript:

```
import { createCable } from "@anycable/web"

const cable = createCable({
  protocol: "actioncable-v1-ext-json"
})
```

Для истории предусмотрены параметры:

```
ANYCABLE_HISTORY_LIMIT=1000
ANYCABLE_HISTORY_TTL=600
ANYCABLE_SESSIONS_TTL=600
```

В этом примере история ограничена 1 000 сообщениями на поток и временем хранения 10 минут; восстановление сессии также ограничено 10 минутами.

Но для Kubernetes есть принципиальная деталь: обычный Redis Pub/Sub и Redis broker для Reliable Streams — не одно и то же.

- OSS AnyCable поддерживает broker в памяти и через NATS.
- Память отдельного Pod не подходит для надёжного восстановления между репликами.
- Redis/Valkey broker для распределённого хранения истории доступен в AnyCable Pro.
- Для broker необходимо использовать совместимую схему broadcasting (`http` или `redisx`), а не просто включить обычный Redis adapter.

То есть при нескольких Pod'ах AnyCable-Go нужно заранее спроектировать общее хранилище истории.&#x20;

## 4. Чего AnyCable всё равно не гарантирует

Это самая важная часть с архитектурной точки зрения.

### Transport ACK ≠ Business ACK

Допустим, приложение отправило клиенту команду:

```
{
  "event_id": "evt-123",
  "type": "payment_confirmed",
  "payment_id": 456
}
```

AnyCable может гарантировать восстановление потока в пределах доступной истории и устранение дубликатов на уровне протокола.

Но он не может гарантировать, что клиент:

1. Прочитал сообщение.
2. Успешно обработал его.
3. Записал результат в локальную БД.
4. Выполнил необходимое действие.
5. Не выполнит это действие дважды.

Даже если клиент получил событие и обновил свой offset, приложение может упасть до завершения бизнес-операции.

Именно здесь нужен прикладной протокол.

## 5. Как я бы проектировал надёжную real-time систему

Для критичных событий я бы использовал такую архитектуру:

Rails / Backend

Бизнес-транзакция + Transactional Outbox

PostgreSQL

Durable events + event_id + sequence

AnyCable-Go

Мгновенная доставка + краткосрочный replay

Client

Deduplication + last_sequence + ACK при необходимости

При слишком большом разрыве истории

HTTP Recovery API

GET /events?after_sequence=102

Как это работает:

1. Rails изменяет бизнес-состояние и атомарно записывает событие в Outbox в той же транзакции.
2. Фоновый publisher отправляет событие через AnyCable.
3. Клиент получает событие и применяет его, проверяя `event_id` или `sequence`.
4. При кратком разрыве AnyCable восстанавливает сообщения из своей истории.
5. При длительном разрыве клиент обращается к HTTP API и догружает пропущенные события из PostgreSQL.
6. Если требуется гарантировать именно бизнес-обработку, клиент отправляет ACK, а сервер сохраняет подтверждённую позицию.

Пример ответа API восстановления:

```
{
  "events": [
    {
      "event_id": "evt-103",
      "sequence": 103,
      "type": "message_created",
      "payload": {}
    },
    {
      "event_id": "evt-104",
      "sequence": 104,
      "type": "message_updated",
      "payload": {}
    }
  ],
  "next_sequence": 104
}
```

Крайне важно, чтобы recovery API возвращал события в согласованном порядке и чтобы между загрузкой истории и переходом к live-потоку не возникало нового окна потери. Обычно это решается подпиской с буферизацией live-событий и последующим deduplication, либо серверным курсором/снимком состояния.

## 6. Не всем событиям нужны одинаковые гарантии

| Тип данных                    | Что использовать                                    |
| ----------------------------- | --------------------------------------------------- |
| Индикатор «печатает…»         | Action Cable, без истории                           |
| Presence / онлайн-статус      | AnyCable Presence или вычисление текущего состояния |
| Обновление счётчика           | AnyCable, при reconnect повторное чтение состояния  |
| Сообщения чата                | AnyCable Reliable Streams + история в БД            |
| Уведомления                   | AnyCable + persistent inbox                         |
| Изменения баланса             | БД как source of truth + пересинхронизация          |
| Финансовые операции / команды | Transactional Outbox + idempotency + бизнес-ACK     |

### Итого

Я бы разделил гарантии на три уровня:

- Transport reliability: reconnect, heartbeat, повторная подписка — есть в обоих решениях.
- Stream reliability: offset, короткая история, replay, resumable sessions — AnyCable умеет, Action Cable из коробки нет.
- Business reliability: durable events, подтверждение обработки, дедупликация бизнес-операций, восстановление после длительного offline — ответственность приложения.

Поэтому AnyCable действительно позволяет не писать собственный протокол восстановления WebSocket-потоков, но не заменяет долговременное хранение событий и бизнес-гарантии.

И отдельно: переход на AnyCable ради Reliable Streams может быть оправдан даже при 100–500 одновременных соединениях, если надёжность доставки существенно важнее масштабирования. Это независимая от производительности причина его использовать.

Документация: [Reliable Streams and Resumable Sessions](https://docs.anycable.io/anycable-go/reliable_streams?utm_source=chatgpt.com) и [Client-side Reliability](https://docs.anycable.io/js/reliability?utm_source=chatgpt.com).
