Промежуточные L7-прокси (Layer 7, Application Layer) — одна из самых важных тем при использовании WebSocket в production.

Причём проблема здесь не только в производительности. WebSocket может прекрасно работать в локальной среде, но в production неожиданно отключаться каждые 30–60 секунд, не проходить через корпоративный прокси или создавать проблемы при деплое.

Разберём, почему так происходит, как устроен WebSocket за L7-прокси и какие настройки действительно важны.

## 1. Где находится L7-прокси

Типичная архитектура выглядит так:

CDN/WAF и reverse proxy — потенциально два отдельных L7-посредника на пути одного WebSocket-соединения.

L7-прокси понимает прикладные протоколы, прежде всего HTTP. Поэтому он может:

- Анализировать HTTP-заголовки и URL.
- Выполнять TLS termination.
- Проверять авторизацию и применять WAF-правила.
- Маршрутизировать запросы на разные backend-серверы.
- Управлять таймаутами, лимитами соединений и буферами.
- Открывать отдельное соединение с upstream-сервером.

Важно: клиент не обязательно имеет одно непрерывное TCP-соединение непосредственно до backend. Между клиентом и сервером может быть несколько независимых TCP- и TLS-соединений.

## 2. Как WebSocket проходит через L7-прокси

Для классического WebSocket через HTTP/1.1 используется механизм `Upgrade`.

Клиент отправляет:

```
GET /ws HTTP/1.1
Host: api.example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: ...
Sec-WebSocket-Version: 13
```

Сервер подтверждает:

```
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: ...
```

После успешного переключения соединение используется для передачи WebSocket-фреймов, а не обычных HTTP-запросов и ответов.

Жизненный цикл через L7-прокси

При обычном HTTP/1.1 Upgrade-проксировании L7-прокси после ответа `101` обычно переходит в режим туннелирования: пересылает поток данных между клиентским и upstream-соединением.

Однако это не означает, что он перестаёт влиять на соединение. Он всё ещё контролирует:

- Сколько времени соединение может оставаться без активности.
- Как долго оно может существовать.
- Что происходит при закрытии upstream.
- Ограничения скорости и объёма трафика.
- Возможность отправки данных при перегрузке.

Также существует WebSocket поверх HTTP/2 через Extended CONNECT (RFC 8441) и HTTP/3 через аналогичный механизм (RFC 9220). Поддержка зависит от клиента, прокси и backend; обычный HTTP/1.1 `Upgrade` не используется между всеми участниками в этих вариантах.

## 3. Главная проблема — таймауты

Это, пожалуй, самая частая причина неожиданного отключения WebSocket за прокси.

Предположим:

- Клиент подключился к WebSocket.
- Соединение успешно установлено.
- Пользователь ничего не делает 60 секунд.
- Прокси считает соединение неактивным и закрывает его.

Например, Nginx по умолчанию использует `proxy_read_timeout 60s`: если от upstream-сервера не поступают данные в течение этого периода, соединение закрывается.&#x20;

### Разные виды таймаутов

| Таймаут                     | Что контролирует                                              |
| --------------------------- | ------------------------------------------------------------- |
| Connection timeout          | Время установки соединения                                    |
| Idle timeout                | Максимальный период без активности                            |
| Read timeout                | Ожидание данных от upstream                                   |
| Write timeout               | Ожидание возможности отправить данные                         |
| Maximum connection lifetime | Максимальная длительность соединения независимо от активности |
| Drain / shutdown timeout    | Время на завершение соединений при остановке сервера          |

Особенно важно различать idle timeout и maximum lifetime.

Heartbeat помогает бороться с idle timeout, но не отменяет ограничение максимальной длительности соединения.

### Решение: Heartbeat Ping/Pong

Сервер периодически отправляет WebSocket Ping, а клиент отвечает Pong.

Пример heartbeat с интервалом 25 секунд

Например, можно использовать:

- Ping interval: 25 секунд.
- Pong timeout: 10 секунд.
- Proxy idle timeout: 90 секунд.

Это пример параметров, а не универсальные значения. Их нужно подбирать под ограничения самого короткого таймаута во всей цепочке.

Нюанс: стандартный браузерный WebSocket API не позволяет JavaScript напрямую отправлять управляющие Ping-фреймы. Обычно их посылает сервер, а браузер автоматически отвечает Pong. Альтернатива — heartbeat в сообщениях приложения.

## 4. Настройка Nginx для WebSocket

Типичная конфигурация:

```
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}

upstream websocket_backend {
    server 10.0.0.10:8080;
    server 10.0.0.11:8080;
}

server {
    listen 443 ssl;
    server_name api.example.com;

    ssl_certificate /etc/ssl/cert.pem;
    ssl_certificate_key /etc/ssl/key.pem;

    location /ws {
        proxy_pass http://websocket_backend;

        proxy_http_version 1.1;

        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_set_header Host $host;

        proxy_read_timeout 90s;
        proxy_send_timeout 90s;

        proxy_buffering off;
    }
}
```

Это пример для HTTP/1.1 WebSocket Upgrade. Прокси должен явно передать `Upgrade` и `Connection`, потому что эти HTTP-заголовки относятся к конкретному соединению и не передаются автоматически.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://nginx.org\&sz=32)

Nginx



Разберём важные настройки:

| Параметр                 | Назначение                                                                                        |
| ------------------------ | ------------------------------------------------------------------------------------------------- |
| `proxy_http_version 1.1` | HTTP/1.1 на участке к backend, необходимый для классического Upgrade                              |
| `Upgrade`                | Передаёт намерение перейти на WebSocket                                                           |
| `Connection`             | Разрешает переключение протокола                                                                  |
| `proxy_read_timeout`     | Максимальный интервал без данных от backend                                                       |
| `proxy_send_timeout`     | Таймаут между операциями записи в upstream                                                        |
| `proxy_buffering off`    | Отключает обычную буферизацию проксируемых HTTP-ответов; после Upgrade действует туннельный режим |

Последняя настройка не является обязательной именно для WebSocket-туннеля, но может быть полезна, когда тот же endpoint поддерживает другие потоковые ответы.

## 5. Проблема: цепочка из нескольких L7-прокси

Представим более реалистичную конфигурацию:

```
Browser
   |
   | WSS
   v
Corporate Proxy
   |
   v
Cloudflare
   |
   v
AWS ALB
   |
   v
Nginx Ingress
   |
   v
WebSocket Server
```

У каждого компонента могут быть свои правила.

Например, гипотетические настройки:

| Компонент       | Idle timeout |
| --------------- | ------------ |
| Corporate Proxy | 45 с         |
| CDN             | 100 с        |
| Load Balancer   | 60 с         |
| Nginx           | 90 с         |
| Backend         | 120 с        |

Эффективное ограничение простоя — 45 секунд, потому что корпоративный прокси может закрыть соединение раньше остальных.

Даже если поставить в Nginx таймаут 24 часа, проблему это не решит.

Есть и более сложный случай: L7-прокси может иметь absolute timeout или принудительно закрывать соединения при обновлении конфигурации. В этом случае heartbeat не поможет.

Отсюда архитектурное правило: WebSocket-клиент всегда должен быть готов к разрыву соединения.

## 6. Что происходит при rolling deployment

Здесь возникает другая серьёзная проблема.

Представим, что у тебя 20 000 подключённых пользователей, а backend работает в Kubernetes.

Ты выкатываешь новую версию приложения:

1. Kubernetes начинает останавливать старый Pod.
2. У Pod всё ещё есть активные WebSocket-соединения.
3. При остановке эти соединения закрываются.
4. Клиенты одновременно начинают переподключаться.
5. Возникает резкий всплеск новых TCP/TLS-подключений и запросов авторизации.

Это называют reconnection storm.

Причём проблемы могут быть не только на backend: например, Cloudflare прямо предупреждает, что обновление программного обеспечения на edge-серверах может приводить к разрыву WebSocket-соединений.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://developers.cloudflare.com\&sz=32)

### Как решать

Нужна комбинация механизмов:

- Connection draining — перестать принимать новые подключения на выключаемый сервер.
- Graceful shutdown — дать старым подключениям время на завершение, при необходимости закрывая их с кодом `1001 Going Away`.
- Exponential backoff + jitter — клиенты переподключаются с увеличивающимися и случайно распределёнными задержками.
- Session resumption — после переподключения клиент передаёт последний полученный номер события и получает пропущенные данные.

Последний пункт особенно важен: переподключение само по себе ещё не означает восстановления состояния.

## 7. L7 Load Balancing и sticky sessions

Предположим, WebSocket-соединение клиента установлено с сервером A.

После успешного установления соединения все его фреймы идут по тому же выбранному upstream-соединению. Поэтому sticky sessions не нужны только ради того, чтобы сообщения одного уже открытого WebSocket не переключались между серверами.

Но после переподключения балансировщик может направить клиента на сервер B.

Если состояние пользователя хранится только в памяти сервера A, возникают проблемы.

Есть два подхода:

| Подход                                | Плюсы                                 | Минусы                                                             |
| ------------------------------------- | ------------------------------------- | ------------------------------------------------------------------ |
| Sticky sessions                       | Проще работать с локальным состоянием | Сложнее перераспределять нагрузку и восстанавливаться после отказа |
| Внешнее состояние (Redis, БД, брокер) | Упрощает переключение между серверами | Дополнительная инфраструктура и задержки                           |

Для масштабируемой системы я бы предпочёл stateless WebSocket gateway с внешним хранением важных состояний и событий. При этом информация о конкретном активном соединении всё равно остаётся локально на gateway.

## 8. Корпоративные прокси, WAF и TLS inspection

Есть ещё одна причина, по которой WebSocket может работать нестабильно: промежуточные устройства, не контролируемые разработчиком.

Например:

- Корпоративный forward proxy может запрещать WebSocket Upgrade.
- TLS-inspection proxy может расшифровывать и проверять `wss://`-трафик, если клиент доверяет его сертификату.
- WAF может заблокировать HTTP-запрос на этапе handshake.
- Некоторые политики безопасности запрещают длительные соединения.
- Сетевой посредник может оборвать соединение без корректного WebSocket Close frame.

Не каждый L7-прокси инспектирует WebSocket-фреймы после Upgrade. Например, Cloudflare документирует, что его WAF применяет проверки к начальному HTTP-запросу, но не инспектирует последующие сообщения уже установленного WebSocket.&#x20;

Это означает, что проверки доступа и валидация входящих сообщений на backend остаются обязательными.

## 9. Как диагностировать проблемы

Я бы начал с конкретных симптомов.

| Симптом                               | Что проверять                                                  |
| ------------------------------------- | -------------------------------------------------------------- |
| Ошибка подключения, отсутствует `101` | Upgrade headers, маршрутизация, WAF, авторизация               |
| Разрыв ровно через 60 секунд простоя  | Nginx, ALB или другой idle timeout                             |
| Соединения обрываются при деплое      | Draining, graceful shutdown                                    |
| Работает дома, не работает в офисе    | Корпоративный proxy, TLS inspection                            |
| Разрывы под высокой нагрузкой         | Лимиты соединений, file descriptors, CPU, память, backpressure |
| После reconnect теряются сообщения    | Event sequence, replay, session resumption                     |
| Браузер показывает `1006`             | Неожиданный разрыв транспорта; искать первопричину по логам    |

Полезно собирать метрики `active_connections`, `connection_duration`, `handshake_failures`, `abnormal_disconnects`, `reconnect_rate` и `ping_pong_rtt`, а также логи балансировщика и backend.

Особенно полезно отличать разрывы через фиксированный интервал после подключения от разрывов через фиксированный интервал после последнего сообщения. Первое часто указывает на ограничение длительности соединения, второе — на idle timeout.

## 10. L4 или L7 для WebSocket?

Это уже архитектурный вопрос.

| Критерий                    | L4 proxy              | L7 proxy    |
| --------------------------- | --------------------- | ----------- |
| Анализ HTTP                 | Обычно нет            | Да          |
| Маршрутизация по URL        | Нет                   | Да          |
| TLS termination             | Зависит от реализации | Часто       |
| WAF                         | Нет                   | Возможен    |
| Накладные расходы           | Обычно ниже           | Обычно выше |
| Управление HTTP handshake   | Нет                   | Да          |
| Гибкость HTTP-маршрутизации | Низкая                | Высокая     |

L4 может быть привлекателен для выделенного WebSocket-сервиса с очень большим количеством подключений, когда не нужны маршрутизация по HTTP-пути и инспекция handshake.

L7 удобнее, если REST API и WebSocket находятся на одном домене, нужна централизованная TLS-терминация, WAF и гибкая маршрутизация. При этом L4 тоже может иметь idle timeout и разрывать соединения.

## Итог: что обязательно предусмотреть

Для production WebSocket за промежуточными L7-прокси я бы заложил пять обязательных вещей:

1. Корректную поддержку WebSocket handshake на каждом HTTP-прокси.
2. Согласованные idle timeout и heartbeat.
3. Reconnect с exponential backoff и jitter.
4. Восстановление пропущенных событий после reconnect.
5. Graceful shutdown и connection draining при деплое.

Главный архитектурный вывод: постоянное WebSocket-соединение не следует считать вечным или гарантированно стабильным. Его нужно проектировать как временный транспорт, который может разорваться в любой момент, в том числе по инициативе промежуточного L7-прокси.

Именно поэтому для серьёзных real-time систем над WebSocket часто строят собственный прикладной протокол с идентификаторами событий, подтверждениями, повторной доставкой и восстановлением сессии.
