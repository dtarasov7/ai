WebSocket — это технология, которая позволяет клиенту (например, браузеру или мобильному приложению) и серверу обмениваться данными в реальном времени через одно постоянное двустороннее соединение.

В отличие от обычного HTTP, где клиент отправляет запрос и получает ответ, WebSocket позволяет серверу самостоятельно отправлять сообщения клиенту, не дожидаясь нового запроса.

## 1. Как работает WebSocket


Процесс выглядит так:

1. Клиент отправляет HTTP-запрос с предложением перейти на WebSocket.
2. Сервер подтверждает переход (обычно ответом `101 Switching Protocols`).
3. Устанавливается постоянное соединение.
4. Клиент и сервер независимо отправляют сообщения друг другу.
5. Соединение остаётся открытым до закрытия одной из сторон или разрыва связи.

WebSocket использует `ws://` или защищённый `wss://`. На практике почти всегда рекомендуется `wss://`.

## 2. Плюсы WebSocket

| Преимущество                   | Почему это полезно                                               |
| ------------------------------ | ---------------------------------------------------------------- |
| Низкая задержка                | Сервер отправляет данные сразу, без ожидания очередного запроса  |
| Двусторонняя связь             | Клиент и сервер могут инициировать обмен данными                 |
| Меньше HTTP-накладных расходов | Не нужно передавать HTTP-заголовки на каждое сообщение           |
| Постоянное соединение          | Нет необходимости постоянно устанавливать новое соединение       |
| Поддержка бинарных данных      | Можно отправлять не только JSON и текст, но и бинарные сообщения |
| Работа в реальном времени      | Подходит для чатов, игр, торговых терминалов и мониторинга       |

Например, если у тебя 10 000 пользователей, которым нужно получать обновления каждую секунду, WebSocket позволяет серверу отправлять изменения по уже открытым соединениям, без постоянных HTTP-запросов.

## 3. Минусы WebSocket

| Недостаток                             | В чём проблема                                                           |
| -------------------------------------- | ------------------------------------------------------------------------ |
| Постоянные соединения                  | Сервер должен удерживать соединение для каждого активного клиента        |
| Сложное масштабирование                | При нескольких серверах требуется координация доставки сообщений         |
| Переподключение                        | При потере сети клиент должен восстановить соединение                    |
| Нет гарантии доставки после разрыва    | Нужен собственный механизм подтверждений и повторной отправки            |
| Сложнее балансировка                   | Нужно учитывать длительно живущие соединения                             |
| Дополнительная безопасность            | Необходимо контролировать авторизацию, Origin, лимиты и размер сообщений |
| Нет встроенного восстановления истории | Пропущенные события нужно получать отдельно                              |

Важный момент: WebSocket работает поверх TCP, поэтому внутри одного соединения сообщения доставляются упорядоченно и надёжно, пока соединение функционирует. Но после разрыва WebSocket сам не восстанавливает пропущенные сообщения.

## 4. WebSocket vs REST API vs SSE

| Критерий                              | REST / HTTP                          | WebSocket                         | SSE                               |
| ------------------------------------- | ------------------------------------ | --------------------------------- | --------------------------------- |
| Постоянное соединение                 | Не обязательно                       | Да                                | Да, для потока событий            |
| Сервер отправляет события без запроса | Нет, в обычной модели                | Да                                | Да                                |
| Двусторонний обмен                    | Через запросы                        | Да                                | Нет, поток только сервер → клиент |
| Сложность                             | Низкая                               | Высокая                           | Средняя                           |
| Автопереподключение в браузере        | Не предусмотрено как единый механизм | Реализуется вручную               | Встроено в EventSource            |
| Основное применение                   | CRUD, API                            | Чаты, игры, интерактивные системы | Уведомления, потоки обновлений    |

REST и WebSocket обычно не конкурируют, а дополняют друг друга.

Например, приложение может использовать REST для загрузки истории сообщений, а WebSocket — для получения новых.

## 5. Пример WebSocket на JavaScript

Клиент:

```
const socket = new WebSocket("wss://example.com/ws");

socket.onopen = () => {
  console.log("Соединение установлено");

  socket.send(JSON.stringify({
    type: "subscribe",
    channel: "prices"
  }));
};

socket.onmessage = (event) => {
  const data = JSON.parse(event.data);
  console.log("Получены данные:", data);
};

socket.onclose = () => {
  console.log("Соединение закрыто");
};

socket.onerror = (error) => {
  console.error("Ошибка WebSocket", error);
};
```

После подключения сервер может отправлять клиенту обновления цен без дополнительных запросов.

## 6. Архитектура WebSocket в production

Допустим, у нас 100 000 подключённых пользователей.

Упрощённая схема масштабирования WebSocket через несколько серверов.

Здесь возникают дополнительные задачи:

- Load Balancer распределяет новые подключения между WebSocket-серверами.
- Redis Pub/Sub, NATS или Kafka могут использоваться для передачи событий между экземплярами приложения.
- Heartbeat (Ping/Pong) помогает определять разорванные соединения.
- Reconnect + resync восстанавливают работу клиента после обрыва.
- Backpressure защищает сервер, когда клиент получает данные медленнее, чем сервер их отправляет.

Redis Pub/Sub удобен для оперативной рассылки, но не обеспечивает долговременное хранение событий. Если критично не терять сообщения, стоит рассмотреть брокер с сохранением сообщений, например Kafka или Redis Streams, и реализовать подтверждения на уровне приложения.

## 7. Когда стоит использовать WebSocket

WebSocket подходит, когда требуется высокая интерактивность: чат, совместное редактирование документов, онлайн-игры, биржевые котировки, live-дашборды, обновления состояния устройств.

WebSocket избыточен, если приложение в основном выполняет CRUD-операции, пользователь редко получает обновления или достаточно загружать данные раз в несколько минут.

## 8. Что я бы рекомендовал

Для большинства современных веб-приложений разумна гибридная архитектура:

- REST API — авторизация, CRUD, загрузка истории и файлов.
- WebSocket — события в реальном времени и интерактивный обмен.
- Redis / брокер сообщений — координация между серверными экземплярами при масштабировании.

Ещё один важный выбор — использовать нативный WebSocket или библиотеку вроде Socket.IO. Socket.IO предоставляет переподключение, комнаты, подтверждения и другие возможности, но использует собственный протокол поверх транспорта и не является обычным WebSocket API.

Интересный вопрос для дальнейшего разбора: что происходит с WebSocket при 10 000–100 000 одновременных подключений, сколько он потребляет памяти и CPU и как правильно масштабировать сервер? Это одна из самых важных практических тем при использовании WebSocket в production.
